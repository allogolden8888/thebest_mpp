# A2P MPP — аудит оптимизации под слабое железо (весь код + все конфиги)

**Основание:** прямой запрос — пройтись по всему коду и всем конфигурациям `main` (41 сервис: 22 Go, 6 Rust, 11 Java, 2 Vue-фронтенда, плюс `k8s/`, `infra/`, docker-compose) и найти каждую точку оптимизации для работы на слабом/ограниченном железе, вплоть до архитектурных решений, с явным указанием компромиссов.

**Статус: ничего из этого документа НЕ применено.** Это отчёт находок, не патч. Каждая находка ниже — либо "free win" (без компромисса, можно применять сразу), либо "tradeoff" (явно расписано, чем придётся пожертвовать) — по прямому требованию запроса. Числа, помеченные как оценки, не измерены — как и в `capacity_model.md` ("Числа по-прежнему оценки, не измерения; каждая цифра подлежит подтверждению нагрузочным тестированием").

**Методология:** 4 параллельных агента (Go / Rust / Java / infra+k8s+data-layer), каждый предварительно прочитал `LATENCY_INVESTIGATION.md` и `LATENCY_INVESTIGATION_1500TPS.md` целиком, чтобы не переоткрывать уже найденное и не противоречить уже измеренному (например: разбиение Kafka-топиков на 8 партиций уже проверено и дало **регрессию в 239 раз** — этот путь помечен как тупиковый везде ниже, не предлагается повторно; `fetch.min.bytes=32768` тоже проверено и отменено — не предлагается). Каждый агент отчитался с точными `файл:строка`, разделением free-win/tradeoff и разделом "проверено — проблем не найдено", чтобы покрытие было реальным, не беглым.

**Важно, отдельно от этого аудита:** на момент написания `main` находится в незавершённом мёрже (`combined-api-gaps` → `main`, `git status` показывает `UU` на `pipeline-engine/lua/cas_transition.lua` и `pipeline-engine/src/redis_cas.rs`). Содержимое обоих файлов уже без конфликт-маркеров (разрешено руками), просто не сделан `git add`/`git commit` — не блокирует этот аудит (весь код читаем корректно), но стоит закрыть мёрж отдельно.

## Тир 1 — системные/архитектурные находки (наибольший эффект, затрагивают весь флот разом)

### 1.1. `k8s/generate_manifests.py`: плоский профиль ресурсов игнорирует собственный план платформы на пулинг control-plane сервисов

**Файлы:** `k8s/generate_manifests.py:70-74` (`INSTANCE_PROFILE`), `:307-323` (`replicas_for`/`_resources`), `:136-201` (список сервисов), `capacity_model.md:12,113`.

`INSTANCE_PROFILE` даёт **плоский профиль на язык** (Rust 4vCPU/8Gi, Java 8vCPU/16Gi, Go 2vCPU/4Gi лимит, реквест — половина), независимо от реальной нагрузки. Любой сервис без записи в `capacity_model.md` (`vcpu_total=None`) получает этот профиль на 50% (Burstable) × `MIN_REPLICAS=2` floor.

Подтверждено точным подсчётом: **16 из 36** сгенерированных сервисов (14 Go + 2 Java) — `vcpu_total=None`. Это `iam-service`, `incident-service`, `ops-visibility-service`, `credential-issuer-service`, `execution-control-service`, `configuration-service`, `config-event-publisher`, `config-cache-projector`, `consent-cache-projector`, `dlr-correlation-writer`, `partner-api`, `backoffice-api`, `replay-service`, `backoffice-ui`, `billing-outbox-publisher`, `billing-ledger-writer` — по факту административные/control-plane сервисы (аудит/RBAC/инциденты/конфиг-CRUD), не горячий путь сообщений.

Итог по этому тиру: **requests = 44 vCPU / 88Gi, limits = 88 vCPU / 176Gi** — только на реквесты (гарантированный резерв под планировщик), для сервисов, которые сам план платформы называет низконагруженными.

При этом `capacity_model.md:12,113` **уже явно** формулирует решение: "Мелкие Go control-plane сервисы... — из N независимых HA-флитов в общий пул VM", "суммарно ≈40 vCPU (общий пул из 3-4 VM)" — но это для *более узкого* списка из 7 сервисов (документ писался раньше, чем появились iam-service/credential-issuer-service/incident-service/ops-visibility-service/consent-cache-projector/backoffice-ui). **Уже одни только текущие requests (44 vCPU) превышают весь пуловый BURST-бюджет (≈40 vCPU) документа для более узкого набора** — `k8s/generate_manifests.py` никогда не реализовывал этот пулинг, просто плоско применяет паттерн Deployment-на-сервис ко всему.

**Усиление находки (KEDA):** 5 из 16 этих сервисов ещё и `kafka_consumer=True` → получают KEDA `ScaledObject` с `maxReplicaCount = replicas × 3`. Для двух Java (`billing-outbox-publisher`, `billing-ledger-writer`) это **48 vCPU / 96Gi лимит-потолок на сервис** — больше, чем весь пул документа на ВСЕ семь сервисов вместе. Потолок лимитов по всему тиру на полном KEDA-бёрсте: **176 vCPU / 352Gi** (4.4× заявленного пула).

**Усиление находки (Terraform):** `infra/terraform/variables.tf:29-54`, `k8s-cluster.tf:46-93` зеркалят тот же плоский `INSTANCE_PROFILE` 1:1 в размеры node pool — нет отдельного/меньшего пула под control-plane тир, нет переменной "профиль слабого железа" вообще. `node_pool_min_size=2` на пул → кластер **всегда** держит минимум 4 пула × 2 ноды = 8 нод ≈ **44 vCPU baseline**, даже полностью в простое.

**Предложение (конкретные числа, помечены как оценка, требуют эмпирической проверки — как и всё остальное в документах этого репозитория):**

Добавить 4-й, гораздо меньший профиль для тира `vcpu_total is None`, например `"go-control-plane": {"cpu": 0.5, "mem_gi": 1}` (реквест 0.25vCPU/512Mi) — большинство этих 16 сервисов I/O-bound (ждут Postgres/Redis), не CPU-bound. Это ~4× сокращение резерва этого тира одной правкой словаря, без изменения границ сервисов.

**Отдельно обсуждена и отклонена (с явной аргументацией) более радикальная альтернатива — консолидация нескольких бинарников в один процесс.** Аргументы против: (1) более рискованный и трудоёмкий путь для проблемы, которая решается однострочной правкой профиля; (2) у части этих сервисов уже построена изоляция безопасности на уровне процесса — например у `credential-issuer-service` отдельная Vault Kubernetes-auth роль, скоуплена на конкретный `bound_service_account_name` (`infra/terraform/vault-secrets.tf`) — консолидация размывает уже построенную границу аудита, не только оргструктурную; (3) тот же пользователь при планировании `partner-portal-ui` уже сознательно отверг объединение нескольких фронтендов в один "god-surface" — тот же аргумент применим к бэкенду с ещё большей силой (blast radius: баг в `replay-service` не должен трогать процесс `iam-service`). **Вывод: чинить профиль, не трогать границы сервисов.**

*Что придётся принести в жертву:* ничего при выборе меньшего профиля per se — но это **непроверенная оценка** (как и все числа в `capacity_model.md`), нужна реальная нагрузка/мониторинг (VPA в recommendation-режиме — хороший способ подтвердить цифру эмпирически, не гадая).

### 1.2. `infra/kafka/generate_kafka_topics.py`: партиционирование продакшена не имеет профиля "маленький деплой"

**Файл:** `infra/kafka/generate_kafka_topics.py:8-27,44-46,127`.

`partitions(topic) = ceil(max(replicas_for(consumer)) × HEADROOM(1.5))`, использует те же `replicas_for`/`SERVICES` из `generate_manifests.py`, что и k8s-сайзинг — то есть число партиций **всегда** выводится из тех же production-размеров под λ_peak=20 000 msg/s. `REPLICATION_FACTOR=3` захардкожен. **Нет вообще никакого понятия "маленький деплой"** — нельзя сгенерировать меньший топик-лейаут для слабого железа, не подделывая `vcpu_total` в `capacity_model.md` (что заодно ужмёт k8s-реквесты — не то, что нужно делать отдельно от партиционирования).

Это тот же класс проблемы, что `LATENCY_INVESTIGATION.md` уже измерил на **локальном** dev-скрипте (365 партиций на одном брокере → реальная задержка) — но здесь это тот же архитектурный пробел уже в **продакшен-генераторе**, не задокументированный ранее.

*Tradeoff:* RF=3 и headroom×1.5 существуют не просто так (реальный HA и запас на рост) — снижать их бездумно опасно. Нужен явный "small deployment profile" параметр (например RF=1 или 2, меньший headroom-множитель), выбираемый сознательно, не через подделку capacity-чисел.

### 1.3. JVM heap: `-XX:MaxRAMPercentage` нигде не используется + docker-compose не задаёт memory-лимиты вообще

**Комбинированная находка (Java-агент + infra-агент, независимо пришли к одному и тому же корню).**

`grep -r MaxRAMPercentage` по всему репозиторию — **0 совпадений**. `billing-service` хардкодит `-Xmx1500m`/`-Xms1g` (это абсолютное значение уже один раз давало реальный OOMKilled при переносе между машинами — см. `b713c53`, там же `Xmx3g` для AMD-сессии откатили до `1500m` для Mac). Остальные **9 из 11** Java-сервисов вообще не задают heap-флаг — JVM-эргономика по умолчанию берёт 25% от **видимой** памяти.

Усугубляющий фактор, найденный отдельно: **`infra/docker/docker-compose.yml` не задаёт `mem_limit`/`deploy.resources` НИ ОДНОМУ контейнеру** (0 совпадений по всему файлу). Это значит, что даже сервис с корректным `-XX:MaxRAMPercentage` сегодня считал бы процент от **всего хоста**, не честной доли контейнера — тот же урок про "Docker не изолирует ресурсы без явных лимитов", который `b713c53` уже применил к CPU-тредам (`BILLING_CONCURRENCY`/`DELIVERY_CONCURRENCY`), но так и не применил к памяти в первопричине — только откатил два конкретных симптоматичных числа.

**Предложение:** (а) `entrypoint: ["java","-XX:MaxRAMPercentage=65","-XX:InitialRAMPercentage=50",...]` вместо каждого хардкод-`-Xmx`/`-Xms`; (б) реально выставить `mem_limit`/`deploy.resources.limits.memory` в compose (сейчас отсутствует), чтобы процент считался от чего-то настоящего. 65% — отправная точка, оставляет запас под off-heap (JFR-буферы, RocksDB block cache — см. 2.6 ниже — они НЕ считаются в `-Xmx`).

*Tradeoff:* эмпирически безопасные абсолютные числа (1500m, работает сегодня на Mac) заменяются на невалидированное производное значение — нужен свежий нагрузочный тест, тот же класс риска, что уже дважды пройден с `*_CONCURRENCY`.

### 1.4. Java: `Executors.newFixedThreadPool(N)` — N хардкод-литерал, не производный от `availableProcessors()`

**Файлы:** `billing-service/.../KafkaIo.java:157` (`BILLING_CONCURRENCY`, default 128), `delivery-service/.../KafkaIo.java:168` (`DELIVERY_CONCURRENCY`, default 128), `operator-smpp-session-manager/.../Main.java:68,143` (`MAX_CONCURRENT_SUBMITS`, default 100).

Это ровно тот механизм, который `b713c53` пришлось откатывать вручную после многодневного цикла bin-search + JFR-профилирования на двух разных машинах (450→128 при переносе AMD→Mac). `grep -r availableProcessors` по всем 11 Java-сервисам — **0 совпадений**. Ни один путь кода нигде не выводит concurrency из реального числа ядер рантайма.

*Tradeoff, не free win:* bin-search в документах нашёл **резкий порог, не плавную деградацию** (200 потоков → p95=1811ms, 450 → p95=254ms) — наивная формула `cores×k` без свежего нагрузочного теста на новом производном значении рискует попасть не на ту сторону обрыва. Любая замена на формулу должна явно нести пометку "требует повторной валидации на целевом железе", как уже помечены существующие числа в этих же документах.

### 1.5. Istio sidecar: скрытый налог ~12.5 vCPU / 16Gi, отсутствует в capacity-математике целиком

**Файлы:** `infra/terraform/istio.tf` (весь файл), `k8s/generate_manifests.py:600-609`.

Namespace `mpp` помечен `istio-injection: enabled`, `PeerAuthentication STRICT` (обязательный mTLS) — каждый под получает Envoy-sidecar. `helm_release.istiod` не передаёт values/resources override — используются дефолты чарта. Реальный прогон генератора (`python3 k8s/generate_manifests.py`, идемпотентен, `git diff` пуст после) даёт **125 базовых подов** по 36 сервисам → консервативно **+12.5 vCPU / +16Gi чистого scheduling-резерва по кластеру**, который **не фигурирует нигде** в `capacity_model.md` или `generate_manifests.py`. Пропорционально тяжелее всего бьёт по и так переразмеренному control-plane тиру (32 из 125 подов).

*Tradeoff:* mTLS — реальное требование безопасности, не предлагается убирать; предлагается явно выставить `resources` sidecar'а в `istio.tf` (сейчас не задано вообще) и учесть эти ~12.5 vCPU в capacity-математике как постоянный налог, не игнорировать.

## Проверено — проблем не найдено (реальное покрытие, не беглый просмотр)

- **Баг "новое соединение на каждый запрос/сообщение"** (изначально найден и пофикшен в `partner-rest-receiver`, Rust): пересистемно проверен во ВСЕХ 22 Go, 6 Rust и (для 6 сервисов, не входивших в первоначальный локальный walking skeleton из 12) 11 Java сервисах — Redis, Postgres, gRPC, Kafka-клиенты, `http.Client`. Единственные новые находки того же класса — 3.4 (Java `RedisTokenBucket`). Везде остальное — клиент создаётся один раз в `main()`/конструкторе и переиспользуется.
- **Kafka producer `linger.ms`/`buffer.memory`/`max.block.ms`** (Rust): подтверждено применено во всех 5 продюсирующих Rust-сервисах.
- **`fetch.min.bytes`**: подтверждено НЕ переприменён нигде (уже был отменён с чистым измерением, не предлагается повторно).
- **Партиционирование Kafka как фикс**: 8-партиционный эксперимент — задокументированный тупик на single-broker/RF=1, не предлагается нигде в этом документе.
- **`exec:{message_id}` TTL-утечка**: подтверждена пофикшенной в `b713c53`.
- **`OperatorRouteRegistry` unregister/heartbeat race**: подтверждена пофикшенной в `b713c53`.
- **Aho-Corasick префильтр** (`template_matching.rs`, используется и `policy-service`, и `template-management-service`): автомат строится один раз на пересборку конфига, не на сообщение — подтверждено собственным тестом сервиса с 20 000 нерелевантных шаблонов.
- **`tokio::main` конфигурация рантайма**: все 6 Rust-сервисов на дефолтных `num_cpus::get()` worker threads — корректно, масштабируется под слабое железо само.
- **Утечки горутин / неограниченный спавн**: все 49 сайтов `go func()` — небольшой фиксированный набор долгоживущих циклов в `main()`, ни один не спавнится на сообщение/запрос. Kafka consumers обрабатывают записи строго последовательно в одной горутине.
- **go-redis pool sizing**: дефолт `10×GOMAXPROCS(0)` — cgroup-safe на Go 1.25+, в отличие от pgxpool (находка 2.3) — фикс не нужен.
- **JSON-vs-protobuf дублирование в горячем пути**: проверено во всех местах, где `encoding/json` соседствует с Kafka-публикацией/потреблением — ни одного случая, где те же данные уже доступны как protobuf и тратятся заново на JSON.
- **N+1 записи / построчные вставки**: все writer-сервисы (`lifecycle-writer`, `dlr-correlation-writer`, `analytics-writer`) корректно батчат (`pgx.Batch`/ClickHouse `PrepareBatch`).
- **GC-алгоритм (Java)**: осознанно не рекомендуется переключать на ZGC/Shenandoah — оба несут более высокий базовый memory/metadata оверхед, что прямо противоречит цели "слабое железо"; G1 (дефолт) уже правильный выбор здесь.
- **Kafka Streams `num.stream.threads`**: оставлен на дефолте библиотеки (1) в обоих scheduler-lane сервисах — уже правильный выбор для слабого железа, не менять.
- **Продакшен Postgres pooling**: подтверждён Yandex-managed PgBouncer на порту 6432, не проблема.
- **Продакшен `redis.tf` (persistence design)**: runtime=OFF (скорость рестарта, не durability), configuration=OFF, billing=ON/AOF — корректно обосновано и совпадает с `hld.md`; разрыв только в локальном `docker-compose.yml`, не отражающем этот же дизайн (находки 2.7/2.8).
- **Kafka broker `KAFKA_HEAP_OPTS`/`KAFKA_NUM_NETWORK_THREADS`**: уже плотно откалиброван под конкретную машину в `b713c53` — дальнейшие поднятия без такой же строгости нагрузочного теста не рекомендуются.

## Как читать приоритеты

Тир 1 — это то, что стоит решать в первую очередь: системные, архитектурные, затрагивают весь флот разом, и (кроме 1.4, которая требует нового нагрузочного теста) в основном однострочные-по-объёму правки с большим эффектом. Тир 2 — конкретные, почти все free win, безопасны для немедленного применения. Тир 3-4 — точечные, часть требует калибровки/измерения перед применением, часть тривиальны сами по себе, но полезны при систематическом проходе.

Ни одна находка в этом документе не помечена "сделать бездумно" — каждая либо free win с явно нулевым компромиссом, либо tradeoff с явно расписанной ценой, ровно по формату запроса.
