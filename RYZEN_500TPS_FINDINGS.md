# 500 TPS деградация на Ryzen-стенде — расследование и фикс

Машина: Ryzen 5 7600X, 12 CPU / 15.16GB Docker Desktop, Windows 11. Хост
подтверждённо тихий на момент всех замеров (`Get-CimInstance Win32_Processor`
LoadPercentage=10%, процесс Microsoft Defender MsMpEng не найден среди
запущенных) — тот же класс confound'а, что нашла предыдущая сессия на Mac
(host CPU contention), здесь исключён и перепроверен, а не просто
предположен.

## 0. Контекст

Продолжение `WINDOWS_TESTING_GUIDE.md`/`PLATFORM_STATE_FOR_REVIEW.md`: та
сессия перенесла ~107 коммитов на этот стенд (16 hot-path сервисов, 32
Kafka-топика по `create_topics.sh`, миграции V001-V035). Перед нагрузочным
тестом обнаружился и был закрыт реальный архитектурный пробел (см. §1), а
не просто обойдён.

## 1. Пробел: execution-control-service отсутствовал в docker-compose.yml

`pipeline-engine`/`partner-rest-receiver` fail-closed без
`ExecutionControlRecord` scope=GLOBAL в топике `execution.control`, а
самого `execution-control-service` не было ни в одном из ~39 сервисов
compose-файла вообще.

Хуже: у самого сервиса (`internal/kafkaio/publisher.go`,
`cmd/execution-control-service/main.go`) обнаружился реальный, не
специфичный для этого стенда бag холодного старта —
`runGlobalControlLoop` публикует GLOBAL только после УСПЕШНОГО тика
Prometheus (`sum(rate(errors))/sum(rate(processed))`), а на нулевом трафике
это `0/0=NaN`, тик пропускается НАВСЕГДА. Без sentinel — трафик не идёт;
без трафика — метрика невалидна; без валидной метрики — sentinel не
публикуется. Дедлок с абсолютно пустого состояния в ЛЮБОМ окружении, не
только здесь.

**Фикс** (не обход): `EnsureGlobalBootstrap` — при старте сервис проверяет,
есть ли уже запись для GLOBAL (читает топик с начала до тишины ~3с), и если
нет — публикует безопасный дефолт (ACTIVE, rate=1.0). Не трогает уже
существующее состояние (тёплый рестарт с легитимным DEGRADED/PAUSED не
затирается). Проверено дважды: полное удаление+пересоздание топика
`execution.control` → сервис сам себя bootstrap'ит без единого ручного
вмешательства.

Сервис заведён в `docker-compose.yml` (JMX на 9999 для последующей
диагностики Kafka, POSTGRES_*/KAFKA_BOOTSTRAP_SERVERS по стандартному
паттерну), `backoffice-api` получил `EXECUTION_CONTROL_SERVICE_ADDR`.

## 2. Статус основной цели: НЕ достигнута, но разрыв уже 9%, а не порядок

Цель всей работы — **300 TPS при e2e p99 < 350 мс**. На тихой 12-ядерной
машине, при честно измеренном e2e (`incoming -> терминальный статус`, не
`incoming -> DELIVERY`, см. ниже):

| конфигурация | p50 | p95 | **p99** | max | цель 350 мс |
|---|---|---|---|---|---|
| 300 TPS, один producer | 228 | 368 | **422** | 586 | не достигнута |
| 300 TPS, producer pool=4 | 213 | 332 | **381** | 453 | не достигнута |

Разрыв — около 9%, а не кратный. Это принципиально другая ситуация, чем
казалось раньше, но цель пока не выполнена, и документ ниже описывает
работу на 500 TPS, а не закрытие этой цели.

**Важная поправка к прежним документам.** `PLATFORM_STATE_FOR_REVIEW.md`
ссылался на «Ryzen давал p99=129 мс при 300 TPS» как на доказательство, что
код способен на целевые числа. Те 129 мс были старой, неправильно
определённой метрикой (`incoming -> DELIVERY`), которая обрывалась до
терминального статуса. Честный e2e на той же машине — 422 мс. Аргумент
«железо виновато, код готов» строился на числе, измерявшем не ту величину.

Оговорка по методике: числа для pool=4 на 300 TPS получены одним прогоном
на конфигурацию. Разница 422 -> 381 (девять процентов) одним прогоном не
устанавливается — в отличие от эффекта на 500 TPS (2.9x), который переживёт
любой разумный шум. Для 300 TPS нужны три прогона с чередованием порядка;
на Mac формально безупречное чередование A,B,A,B уже дало ложный
трёхкратный выигрыш, который отменился при обратном порядке
(`PLATFORM_STATE_FOR_REVIEW.md` § 13.3).

## 3. Baseline 300 TPS — валиден

`results/20260913T152001Z-baseline-run01/SUMMARY.md`: 72000/72000 принято,
100% совпадение по множеству message_id с `message_read_model`, exec:*
дренирует к нулю мгновенно, 23/23 контейнера чистые (0 OOM, 0 рестартов).

E2E (steady-state, n=49801): **p50=228ms, p95=368ms, p99=422ms, max=586ms**.

## 4. 500 TPS — резкая, нелинейная деградация

Rate вырос в 1.67 раза; p50 вырос пропорционально (1.8x), но p95/p99 — в
7.5-8x:

| | 300 TPS (n=49801) | 500 TPS (n=42502) |
|---|---|---|
| p50 | 228ms | 410ms |
| p95 | 368ms | 2934ms |
| p99 | 422ms | 3145ms |
| max | 586ms | 3401ms |

Суммарный CPU почти не менялся (766%→800%, +5% при росте нагрузки на 67%) —
сразу исключило "не хватает ядер" как объяснение.

## 5. Локализация причины

Разбивка по стадиям пайплайна (ClickHouse `stage_events`, инкрементальная
задержка на каждый хоп) показала: **каждый** хоп (policy/billing/routing/
delivery) прибавлял к p95 примерно одинаково выросшую (~20-25x) задержку
одновременно — не просадка в одном сервисе, а общий разделяемый ресурс на
грани насыщения.

Проверено и исключено по очереди, с реальными измерениями, а не
предположениями:

- **GC Kafka-брокера** — max=15ms что на 300, что на 500 TPS (kafkaServer-gc.log).
- **Host contention** — хост на 10% CPU, Defender не запущен.
- **cgroup-лимиты** — ни у одного контейнера нет `cpus:`/`mem_limit`, который бы ограничивал CPU.
- **Сам Kafka broker** — включил JMX (`KAFKA_JMX_PORT=9999`, раньше нигде не было), замерил `RequestMetrics,name=TotalTimeMs,request=Produce`: p99=5ms, max=29ms даже под 500 TPS. Брокер быстрый.
- **Redis (CAS/load в pipeline-engine)** — добавил замер времени прямо в `redis_cas::load`/`cas_advance`: **0 медленных вызовов** (>50мс) за весь 500 TPS прогон.

**Найдено**: `producer.send()` в `pipeline-engine::kafka_io::publish_dispatch`
(общая точка для АБСОЛЮТНО каждого перехода между стадиями):

| | 300 TPS | 500 TPS |
|---|---|---|
| Вызовов >50мс | 210 из ~90000 (0.23%) | 118344 из ~150000 (~79%) |
| p50 / p99 / max | — / 79ms (max) | 146ms / 347ms / 369ms |

Причина: **один** `FutureProducer` на весь сервис обслуживал одновременно
до ~768 конкурентных tokio-тасков (`PIPELINE_INCOMING_CONCURRENCY` +
`PIPELINE_COMPLETED_CONCURRENCY` + `PIPELINE_RETRY_TRIGGER_CONCURRENCY`).
librdkafka держит одно TCP-соединение и один внутренний I/O-поток на
брокер на клиента — это последовательная точка, которую клонирование
`FutureProducer` (Arc на тот же клиент) не размножает. Тот же класс
проблемы, что уже чинили раньше (`queue.buffering.max.messages` от
переполнения локальной очереди), но другой механизм — не переполнение
очереди, а последовательность одного соединения под конкурентным доступом.

Это прямой ответ на вопрос "почему не берётся больше CPU": простаивающие
ядра физически не могут распараллелить трафик, идущий через одно
соединение — упор в архитектуру конкурентности одного клиента, не в
вычисления.

## 6. Фикс: ProducerPool

`kafka_io::ProducerPool` — несколько независимых `FutureProducer` (каждый
свой `.create()`, свой нативный клиент, своё TCP-соединение), round-robin
выбор на каждый вызов. Размер — `PIPELINE_PRODUCER_POOL_SIZE` (дефолт 4).

Результат на 500 TPS (пул=4 против одного producer):

| | 1 producer | pool=4 |
|---|---|---|
| Вызовов >50мс | 118344 (79%) | 3227 (2.1%) |
| e2e p50 | 410ms | 409ms (не менялось — и не должно было) |
| e2e p95 | 2934ms | **940ms** (в 3.1 раза лучше) |
| e2e p99 | 3145ms | **1090ms** (в 2.9 раза лучше) |
| e2e max | 3401ms | 1480ms |

На 300 TPS с пулом=4 — не регресс, а небольшое доп. улучшение (p50
228→213ms, p95 368→332ms, p99 422→381ms, max 586→453ms).

**Пул=8 — регрессия, не улучшение**: вызовов >50мс выросло до 27129 (было
3227 при пуле=4), p95 producer.send() 157мс→665мс. `docker stats` показал
рост PID-ов контейнера pipeline-engine — больше нативных клиентов
librdkafka означает больше внутренних OS-потоков библиотеки, и после
какого-то порога это создаёт CPU-scheduling-контеншн внутри одного
контейнера, а не добавляет параллелизм. Тот же класс проблемы уже был
задокументирован для `MAX_CONCURRENT_SUBMITS` в
operator-smpp-session-manager (300 потоков хуже, чем 100). full e2e через
ClickHouse для пула=8 не считался — на уровне producer.send() деградация
уже была однозначной, откатили на 4 без дальнейшего замера e2e.

**Итог**: пул=4 — подтверждённое улучшение, зафиксирован как дефолт.
Остаточный разрыв на 500 TPS (p95=940ms против 368ms на 300 TPS) не
закрыт — значит, где-то рядом есть второй, более мелкий потолок.

## 7. ProducerPool в трёх Rust-сервисах стадий — измерено, оказалось РЕГРЕССИЕЙ

Следующая сессия перенесла тот же `ProducerPool` в `policy-service`,
`routing-service`, `destination-resolution-service` (по ОДНОМУ producer'у на
1024 конкурентных задачи каждый, default размер пула = 4) в предположении,
что это наиболее вероятное место остаточного разрыва на 500 TPS (p95 940
против 368 на 300 TPS). Гипотеза была правдоподобной — но проверка (честный
A/B на тихой машине, метод из §7.1 ниже) её не подтвердила.

**Результат A/B на 500 TPS** (все числа — Postgres `message_lifecycle_history`,
не ClickHouse, см. §7.1 почему):

| Конфигурация | p50 | p95 | p99 | max |
|---|---|---|---|---|
| pool=4 только в pipeline-engine, остальные =1 | 208 | 936 | 1092 | 1320 |
| pool=4 во ВСЕХ четырёх (pipeline-engine + policy + routing + destination-resolution) | 1217 | 3905 | 4165 | 4380 |

Включение тех же пулов ЕЩЁ в трёх сервисах одновременно — не улучшение, а
явная регрессия (p95 почти в 4 раза хуже). Правдоподобный механизм: 4
сервиса × 4 producer'а = 16 нативных librdkafka-клиентов системно (было 4),
каждый со своим внутренним OS-потоком — тот же класс проблемы, что уже был
измерен для пула=8 В ОДНОМ сервисе (§6): после какого-то порога больше
клиентов означает больше scheduling-контеншна между процессами/потоками на
общих 12 ядрах, а не больше реального параллелизма. Здесь порог оказался
ниже, потому что контеншн идёт МЕЖДУ контейнерами, не только внутри одного.

**Действие**: дефолты `POLICY_PRODUCER_POOL_SIZE`/`ROUTING_PRODUCER_POOL_SIZE`/
`DESTINATION_RESOLUTION_PRODUCER_POOL_SIZE` в `docker-compose.yml` откачены
на 1 (эффективно отключены). Код `ProducerPool` в этих трёх сервисах
оставлен (не удалён) — рабочий и может быть A/B-испытан отдельно (например,
пул в ОДНОМ из трёх, не во всех сразу), просто не должен быть включён по
умолчанию без более точечной проверки.

### 7.1. Побочная находка: ClickHouse `FINAL`-запрос ненадёжен как метод замера на растущей таблице

Первый прогон A/B (все четыре пула) дал через старый ClickHouse-запрос
(`analytics.stage_events FINAL`) абсурдные p50=17056мс/p95=19766мс — не
реальная деградация, а сам запрос упёрся в `Memory limit (total) exceeded`
на другом, похожем запросе к той же таблице (3.5M+ строк, накопленных за
день тестов). Проверка по Postgres `message_lifecycle_history` для
конкретного message_id тем временем показала честные 37мс. С этого момента
все замеры в этом документе (включая таблицу выше) считаются через Postgres
`message_lifecycle_history` (lifecycle_version=1 → терминальный статус), не
через ClickHouse `stage_events FINAL` — этот метод больше не считается
надёжным на разросшейся таблице без отдельного профилирования ClickHouse
самого по себе (не входило в скоуп этой сессии).

### 7.2. Побочная находка: O(n²) в policy-service::config_reload — реальный баг, исправлен

При восстановлении стенда после перезагрузки Docker Desktop полный replay
`config.changes` (намеренный дизайн — уникальный `group_id` на каждый
рестарт, чтобы гарантировать полный replay compacted-топика) занял **5.5
минут** у `policy-service` при том, что у остальных трёх сервисов — секунды.
Причина: `build_live_state()` пересобирает `CompiledRuleset` (Aho-Corasick
автомат по ВСЕМ ~6323 реальным шаблонам) и вызывался **на каждое
отдельное сообщение** replay, не один раз в конце — O(n) работы × n
сообщений = O(n²) (≈20 млн условных единиц). Пофикшено (debounce: помечать
"грязным" + пересобирать по таймеру 100мс, не на каждое сообщение,
`POLICY_LIVE_STATE_REBUILD_INTERVAL_MS`) — тот же replay теперь занимает
**13 секунд**. Commit `policy-service: debounce build_live_state rebuild —
O(n²)→O(n) на полном replay config.changes`.

## 8. Что ещё стоит проверить

Приоритет — от вероятного к менее вероятному:

1. **`num.network.threads=6` на самом Kafka broker.** Это следующий по
   масштабу разделяемый ресурс после устранения producer-серилизации —
   значение калибровалось на ДРУГОЙ машине (8 CPU/7.75GB, по истории в
   docker-compose.yml), не на этом 12-ядерном Ryzen. JMX теперь включён
   (`KAFKA_JMX_PORT=9999`) — можно A/B поднять до 8-10 и перемерить 500 TPS
   с тем же pool=4 producer, глядя на `RequestQueueTimeMs`/
   `NetworkProcessorAvgIdlePercent`.
2. **Промежуточные размеры пула pipeline-engine (5, 6)** — не проверялись;
   между подтверждённым улучшением на 4 и регрессией на 8 может быть
   локальный максимум выше 4. С учётом §7 — точечная настройка ОДНОГО
   сервиса выглядит более осмысленной, чем одновременное включение везде.
3. **Тот же паттерн в Java-сервисах** — billing-service, delivery-service,
   operator-smpp-session-manager тоже держат высокую конкурентность
   (`MAX_CONCURRENT_SUBMITS=100` и т.д.) через, предположительно, одного
   Kafka-клиента каждый. Не проверялось — pipeline-engine был найден и
   исправлен первым, потому что через него идут все 5 хопов. С учётом §7,
   переносить не включая по умолчанию, только с A/B на тихой машине.
4. **Настоящий 700-1000 TPS прогон** — узнать, где именно следующий потолок
   после producer pool, вместо того чтобы гадать по экстраполяции с 500.
5. **Docker Desktop / WSL2 storage overhead** — Kafka пишет в writable layer
   контейнера (нет `volumes:` для `/var/lib/kafka/data`), не в bind-mount с
   Windows-хоста, так что NTFS-транслирующий слой не должен быть виноват,
   но абсолютные величины BLOCK I/O не проверялись отдельным профилировщиком
   (`strace -T` внутри контейнера кафки не пробовался — нет strace в образе
   apache/kafka из коробки).
6. **Дальнейший рост партиций/топиков** — если план всё ещё включает 1500
   TPS, стоит заранее продумать, что "один shared producer" — не
   единственное узкое место такого рода, которое всплывёт на следующем
   пороге.
7. **Host memory pressure как confound** — WSL2 VM (`vmmemWSL`) разрослась
   до 13.4ГБ за долгую сессию тестов (свободно на хосте было 4.1ГБ из
   31ГБ), Windows включил Memory Compression. Три прогона подряд без
   рестарта Docker Desktop дали монотонно ухудшающиеся числа (p95
   1137→2145→3105мс) — не из-за кода, а из-за накопившегося давления на
   память хоста. После `wsl --shutdown` + рестарта Docker Desktop (свободно
   стало 15.5ГБ) числа снова стали воспроизводимыми. Для будущих сессий:
   если результаты внутри одной сессии дрейфуют без видимой причины —
   первым делом проверить `vmmemWSL` и свободную память хоста, не гадать на
   код.
