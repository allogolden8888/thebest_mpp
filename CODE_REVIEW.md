## TOP FINDINGS ACROSS BOTH BRANCHES (ranked)

Two services don't even compile, and several "safety gate" mechanisms turn out to be silent no-ops — those rank above ordinary logic bugs because nothing downstream can catch them.

1. **`configuration-service` (subagent-1) does not compile** — `go:embed` path points at a directory that doesn't exist. Every test in the service (`validate`, `store`, `grpcserver`) has never run despite the README's own claim otherwise.
2. **`pipeline-engine` (main) does not compile** — `cargo build` fails with 9 errors from a prost module-layout mismatch. Its own test suite has never run.
3. **`execution-control-service` (subagent-1): manual overrides for every scope except GLOBAL never reach Kafka.** Billing Reconciliation's fenced-recovery freeze/unfreeze mechanism is a complete no-op for PARTNER/STAGE/PARTNER_STAGE/OPERATOR_ROUTE — the RPC succeeds, the audit log is written, and nothing downstream ever learns about it.
4. **`scheduler-standard-lane` (subagent-1): `ControlSnapshot` only checks GLOBAL/STAGE scope.** A PARTNER- or OPERATOR_ROUTE-scoped `PAUSED` has zero effect on release — the documented "min of all applicable rate limits" contract is broken.
5. **`scheduler-standard-lane` (subagent-1): uncaught exception on any unset/unrecognized control state crashes the service in a permanent restart loop**, because the offending record is replayed from the beginning of a compacted topic on every startup.
6. **`scheduler-critical-sweep` (subagent-1): `BuildRetryCommand` never sets `stage_extension`, so every retry it publishes is deterministically rejected downstream instead of re-executing** — confirmed against the one real stage consumer in the repo. Retries silently become fake permanent rejections.
7. **`scheduler-critical-sweep` (subagent-1): 4 replicas sweep the same Redis keyspace with zero coordination** (no lock, no claim script) — guaranteed duplicate publishes under normal steady-state operation, not an edge case.
8. **`config-event-publisher` (subagent-1): a `COALESCE(cv.status,'active')` bug makes consent-revocation events structurally impossible to publish as revocations** — a subscriber's opt-out revocation can never propagate through this pipeline; it's silently treated as a re-addition. Compliance-relevant.
9. **`billing-service` (main): `commitAsync()` semantics drop a failed message permanently**, not just "retry twice" — one bad record in a batch causes the following successful record's commit to skip past it forever. Zero test coverage for this code path.
10. **`billing-service` (main): TOCTOU race in `BillingAccountStore` silently loses charges** under horizontal scale-out (which the consumer-group setup implies is expected) — epoch fencing doesn't cover ordinary concurrent charges, only freeze/unfreeze.
11. **`pipeline-engine` (main, once compiling): no idempotency on redelivered messages** — Kafka at-least-once redelivery can rewind a message's pipeline state and cause duplicate billing.
12. **`pipeline-engine` (main, once compiling): stage-completion events are applied without checking they belong to the currently in-flight stage** — a stale/duplicate event under ordinary Kafka redelivery silently skips a real pipeline stage (e.g. skips Policy checks entirely).
13. **`policy-service` (main): `parse_pattern` panics on any multi-byte UTF-8 character** (Cyrillic, Uzbek Latin apostrophe, emoji) in a template pattern — a real crash risk on this platform's actual text domain.
14. **`policy-service` (main): time-of-day enforcement compares UTC directly against config documented as Asia/Tashkent local time** — a 5-hour offset bug in a documented compliance control (ad-hour restrictions).

Full detail for every finding, plus lower-severity items, test-coverage notes, and cross-service consistency observations, is in the per-service sections below.

## PART 2 — new services added after the original review (2026-07-27)

Both branches grew substantially: 6 new services in `main`, 13 new services + a frontend in `subagent-1`. Reviewed below.

### TOP FINDINGS FOR PART 2 (ranked)

Two clusters dominate: **authorization is missing end-to-end on the entire admin/replay control plane**, and **the same "clear local state / commit offset before the write is confirmed" data-loss pattern recurs independently in at least 6 different services across both languages** — this is now clearly a systemic house style issue, not isolated bugs.

1. **Backoffice control plane has zero authorization, front to back.** `backoffice-api` checks only that a JWT is validly signed (no role/scope check) before allowing config CRUD, execution-control override (can pause the whole platform), or force-scheduler-command; internal gRPC calls to Configuration/Execution-Control/Replay Service are plaintext with no mTLS. `backoffice-ui` compounds this — the frontend has no role concept either, shows every privileged menu item to any authenticated user, and has no confirmation dialog on any destructive action. `replay-service`, the third leg, also has zero authentication on its gRPC surface. Any staff member with any valid token — or any workload that can reach these internal ports directly — can pause message processing platform-wide or mass-replay the DLQ.
2. **`replay-service` has a TOCTOU race enabling double-replay.** No atomic claim step between loading a DLQ record, checking idempotency (charge-exists/DLR-correlation-exists), and republishing — two concurrent replay requests for the same record both pass the checks and both republish, which can mean two real SMS deliveries or two independent billing charges for one DLQ'd message. It also never re-checks `execution.control` before republishing, so a replay can slam a stage that was intentionally paused mid-incident.
3. **`partner-smpp-gateway`'s inbound `deliver_sm` gRPC endpoint has zero authentication** — any workload that can reach the pod's gRPC port can inject a forged delivery receipt or MO message into a partner's live SMPP session.
4. **`delivery-reconciliation-service` never consumes the evidence topics it needs — every ambiguous delivery case is guaranteed to resolve as "not submitted," 100% of the time, regardless of what actually happened.** The evidence-gathering code is fully built and tested but never wired into the running service. Net effect: the platform systematically fails to charge for (or mis-reports as failed) messages that were, in fact, delivered.
5. **`billing-reconciliation` can freeze an account on drift but has no automated path to ever unfreeze it** — the recovery code exists and is tested, but isn't called. A drift event (even a false positive, and the drift math itself has a real false-positive risk from conflating an absolute balance with a full-history ledger delta) permanently sidelines a paying partner's account.
6. **`billing-outbox-publisher` permanently drops any ledger event whose Kafka publish fails or is interrupted** — no XCLAIM/XAUTOCLAIM/retry logic exists, so a transient Kafka blip silently and permanently under-represents an account in "the final accounting source of truth."
7. **`billing-ledger-writer` combines default Kafka auto-commit with swallow-on-error, and never re-establishes its single JDBC connection** — once Postgres drops the connection once, every subsequent ledger event is silently lost forever while the service reports itself healthy indefinitely.
8. **The same "clear buffer / advance offset before the write is confirmed" pattern independently recurs in `lifecycle-writer` and `analytics-writer`** (Go) — a transient Postgres/ClickHouse outage or an ordinary pod restart permanently and silently drops buffered rows, including DLQ records that `replay-service` would later need.
9. **`delivery-service` has no idempotency guard around the real operator submit call** — a Kafka-publish failure *after* a message was already accepted by the operator causes a redelivery that submits it to the operator a second time, i.e. a real duplicate SMS to a subscriber.
10. **`message-state-resolver`'s in-memory lifecycle store isn't rolled back on Kafka transaction abort** — an entirely ordinary, non-crash error path (one poison message in a batch) permanently and silently drops another, valid message's lifecycle update.
11. **`operator-http-gateway`'s public DLR webhook has no auth-before-read and no body-size/timeout limit** — a trivial, credential-free memory-exhaustion DoS reachable by anyone on the internet; separately, multi-segment SMS submission loses per-segment tracking data and can duplicate delivery of an already-accepted segment on partial failure.
12. **`operator-smpp-session-manager` never reconnects after a post-startup disconnect** — a routine SMSC restart or network blip permanently black-holes all submits for that operator until a human manually restarts the pod, with `/readyz` never reflecting the outage.
13. **`dlr-manager`'s DLR correlation lookup has no time-bound on `smsc_message_id` reuse**, and the retention job that would limit the collision window is never invoked anywhere in the repo — an operator reusing a message ID (a real-world occurrence the HLD itself acknowledges) can cause a delivery outcome to be silently reported to the wrong partner, and this only gets worse over time.
14. **`partner-notification-service` has an unvalidated SSRF-capable webhook URL and no mTLS on its internal gRPC leg** — a misconfigured or malicious `notification_callback_url` causes the platform to make outbound authenticated-looking HTTP calls into its own internal network.
15. **`partner-rest-receiver`, as currently wired for deployment, cannot authenticate a single real partner request** — there is no secrets pipeline anywhere in the repo that populates the credential env vars its auth verifier requires, so it fails closed on every request. Separately (should this get fixed), rate-limiting/admission checks are skipped entirely on the auth-failure path, enabling unthrottled credential brute-forcing, and there's no partner-retry idempotency protection.

Full detail for all of the above, plus lower-severity items, test-coverage notes, and cross-service consistency observations, is in the per-service sections below.

## main / delivery-service + message-state-resolver (Java)

Both services correctly implement their documented core mechanism at the API level (real transactional `KafkaProducer` in message-state-resolver; real bounded-timeout gRPC client in delivery-service; real byte-level GSM-7/UCS-2 segmentation) — but both have the same shape of bug: a locally-mutated piece of state isn't actually gated on the outcome of the transactional/at-least-once boundary meant to make it safe, so ordinary error-handling paths (transaction abort, Kafka-publish retry) produce outcomes worse than a clean crash.

### delivery-service

1. **CRITICAL — no idempotency guard around the operator submit call; a local Kafka-publish failure after a successful operator submit causes a real duplicate SMS dispatch.** `KafkaIo.java:135-184` — `submitClient.submit(...)` (the real gRPC call that hands a message to the operator) happens, then `producer.send(...).get(10s)` publishes `stage.completed` afterward. If that publish throws (broker blip, timeout), the outer per-record `catch` (lines 90-97) marks the record failed **without committing the offset**, so the exact same `StageExecuteCommand` is redelivered and `submitClient.submit(...)` runs a second time for a submission the operator already accepted. Compounding it: `queueMsgId` (line 160) is a fresh `UUID.randomUUID()` on every invocation including this retry, so the one plausible dedup key changes every time — the stable `stage_execution_id` the architecture designates for this purpose (`hld.md §21`: "duplicates prevented by combination of stable stage_execution_id + no automatic resubmission on UNKNOWN") is never actually enforced locally. Concrete scenario: operator accepts a real SMS submission, then a transient Kafka blip on the `stage.completed` publish causes redelivery — **two real SMS submissions reach the subscriber for one logical message**, with nothing in the codebase able to detect or prevent it. Zero test coverage for this exact property despite it being an explicit platform invariant.
2. **HIGH — malformed input or missing Redis context creates a permanent poison-pill, unlike the gracefully-handled "gateway not found" case.** `KafkaIo.java:143,154-157` — a corrupt `StageExecuteCommand` or a missing `msgctx:{message_id}` throws and is caught by the generic per-record handler with the offset never advanced — no DLQ escape valve, no attempt cap, so the same record is retried forever, permanently head-of-line-blocking every message behind it on that partition. Inconsistent with the adjacent "gateway registry has no entry" path (lines 165-170), which deliberately publishes `SUBMISSION_OUTCOME_UNKNOWN` and lets Scheduler decide instead of throwing. Concrete trigger: `msgctx:{message_id}` has a TTL: if Scheduler retries a delivery after a long operator outage, the context can expire before the retry lands, wedging that message's partition indefinitely.
3. **MEDIUM — GSM7→UCS2 segmentation fallback can silently dispatch more segments than Billing charged for.** `SegmentMessage.java:73-82` — when body content forces a UCS-2 fallback (fewer chars/segment than GSM-7), the actual segment count dispatched to the operator can exceed what was billed, with nothing downstream notified of the mismatch. The fallback correctly avoids wire-byte corruption but doesn't reconcile the cost divergence.
4. Medium — new Redis TCP connection opened and torn down per message in `MessageContextStore.java:26-39` / `GatewayRegistry.java:31-41` — connection churn on the hot path of every delivery (self-documented as a known compromise, but affects throughput/availability under load).
5. Low — `ControlSnapshot.check()` (`ControlSnapshot.java:11-21`) is a permanent stub always returning `ADMIT` — once Execution Control Service actually publishes `OPERATOR_ROUTE` scope pauses, this is the last gate before real operator dispatch and currently has no effect.
6. Test quality — all 30 tests exercise pure functions/`OffsetTracker` in isolation; there is no test exercising `KafkaIo.run()`/`processRecord()` end-to-end, so none of findings #1-#3 are reachable by the existing suite.

### message-state-resolver

1. **CRITICAL — in-memory store mutation is not rolled back on Kafka transaction abort, silently and permanently dropping partner-visible lifecycle events.** `KafkaIo.java:84-168` — `store.put(messageId, result.state())` (line 163) happens synchronously inside the `beginTransaction()`/`commitTransaction()` block, before the transaction actually commits, and is never undone on `producer.abortTransaction()` (lines 109-112). Concrete scenario: a poll batch has record A (valid, `m1`→SUBMITTED) and record B (corrupt bytes, `m2`). Processing A does `store.put(m1, SUBMITTED)` and enqueues A's writes inside the transaction; processing B throws; the whole transaction aborts, discarding A's Kafka writes too, and offsets never advance so both A and B redeliver — but `store` for `m1` was never rolled back. On redelivery, `TransitionValidator.apply` sees the same `event_id` already applied and returns `DUPLICATE`, so A's write is never retried — **A's lifecycle update is permanently lost**, with no crash required, from a completely ordinary transaction-abort path. The same corruption triggers if `commitTransaction()` itself throws (broker timeout, fencing during rebalance) after several `store.put()` calls already ran earlier in the batch loop. This is materially worse than the documented "state doesn't survive a restart" limitation — it's silent, non-crash, permanent data loss.
2. **HIGH — malformed input is a whole-batch poison pill with no per-record isolation** (contrast with delivery-service, which does isolate per-record). `KafkaIo.java:90-119` — a single unparseable event aborts the whole batch's transaction; since offsets never commit, the identical batch (poison record + any valid co-batched records) replays forever, stalling the partition and — per finding #1 — actively corrupting local state for any valid record that shared the batch.
3. **HIGH — the "no RocksDB / no restore-from-changelog" gap (flagged in `development_plan.md` 3.5 as an open item) is a real correctness risk under a routine restart, not just a durability nice-to-have.** `MessageStateStore.java` (plain in-memory `ConcurrentHashMap`) is wiped on every pod restart, but Kafka offsets are already committed past previously-processed events (they were part of the same transaction) — so those events are never redelivered to repopulate the store. Post-restart, `TransitionValidator` (`TransitionValidator.java:63-69`) sees `status()==null` for any previously-resolved message and treats it as a fresh entry point rather than "state we lost track of." Concrete scenario: `m1` reaches real terminal `DELIVERED` pre-restart; pod does a routine rolling deploy; a later genuinely-anomalous `UNDELIVERABLE` DLR for `m1` arrives — instead of being rejected as `REGRESSION` per `state_machines.md §1.3` ("late DLR contradicting an already-issued DELIVERED/UNDELIVERABLE must NOT be allowed"), it's silently accepted and republished to the partner as the message's apparent first-ever status. `lifecycle_version` also resets to 1 instead of continuing to increment, breaking the monotonic-version invariant the same spec section says protects against out-of-order apply — every restart silently rewinds versioning for every in-flight message.
4. Medium — `transactional.id` fencing depends entirely on `MSR_INSTANCE_ID` uniqueness (`KafkaIo.java:61-82`, `Main.java:20-24`) rather than partition-ownership-tied fencing (e.g. Kafka Streams' `group.instance.id` pattern); nothing prevents two live replicas from momentarily holding overlapping transactional identity during a bad rollout — self-documented as unsolved, but compounds directly with finding #1 and should be weighed before any real multi-replica deployment.
5. Test quality — all 28 tests exercise pure functions (`TransitionValidator`, `CandidateTransitionResolver`, bare `MessageStateStore` get/put) in isolation; there is no `KafkaIoTest` at all, so none of findings #1-#3 (the entire "transactional guarantee" claim from the commit history) are exercised by any test — only verifiable by code inspection, as done here.

## main / dlr-manager + dlr-correlation-writer + partner-notification-service (Go)

Wire format and correlation-key agreement between the two DLR services is sound (both use `(operator_id, smsc_message_id, segment_id, submitted_at)`, and both correctly commit Kafka offsets only after a durable write/publish succeeds using deterministic idempotency keys) — the failures below are elsewhere.

### dlr-manager

1. **HIGH — correctness/security: a DLR can be correlated to the wrong message when an operator reuses `smsc_message_id`.** `internal/correlation/store.go:48-66` — `Lookup` selects `ORDER BY submitted_at DESC LIMIT 1` for `(operator_id, smsc_message_id, segment_id)` with no bound tying the result to the DLR's `received_at`. The primary key legitimately allows multiple rows per key over time (`migrations/V009__dlr_correlation.sql:15`) because operators can reuse `smsc_message_id` once their ID space wraps — `hld.md §14` acknowledges this directly. Concrete scenario: message A submitted at T0 gets `smsc_message_id="00042"`; A's DLR is delayed (slow operator / retry loop). Before it arrives, the same operator issues `"00042"` again for unrelated message B submitted at T1>T0, within the 48h retention window. A's real DLR, when it finally arrives, resolves to B's row (higher `submitted_at`) — B's partner receives A's delivery outcome. This gets **worse over time**, not better: `dlr.drop_old_correlation_partitions` (`migrations/V015__partition_maintenance.sql:87`) is defined but never invoked anywhere in the repo (confirmed by grep, and self-documented in dlr-correlation-writer's own README), so the collision window only grows. No test constructs two rows sharing a correlation key at different `submitted_at` — the exact ambiguity this design is exposed to is untested.
2. **MEDIUM — malformed `operator.dlr` records are silently and permanently dropped, not "stuck" as the README claims.** `cmd/dlr-manager/main.go:145-156` — each record is committed individually right after `handleRecord`; if `DecodeOperatorDlr` fails, the callback logs and returns without committing, but the *next* successfully-processed record on that partition still advances the committed offset past the unprocessed poison one. In continuous traffic this happens almost immediately — the malformed DLR (and its message's delivery status) is lost forever with no DLQ or alert.
3. **MEDIUM — unrecognized `raw_status` codes are dropped with no DLQ/alert/fallback.** `internal/dlr/parser.go:44-54` hardcodes exactly 5 standard SMPP v3.4 codes; any vendor-specific/quirky code (common in real SMSC integrations) is logged and dropped. An operator whose gateway uses non-standard codes for a large share of DLRs will systematically never have those messages resolve.
4. Low — `pending.Store` (Redis) is TTL-bounded but has no count cap; a sustained burst of uncorrelated DLRs can grow it unbounded for up to 48h.
5. Low — per-record synchronous Kafka commit (throughput/latency concern, not correctness).

### dlr-correlation-writer

1. **MEDIUM — same silent-permanent-loss pattern as dlr-manager, on `operator.submit.accepted`.** `cmd/dlr-correlation-writer/main.go:92,137-151` + `internal/kafkaio/consumer.go:107-124` — `latestByPartition` only updates on successful decode; the next good record's flush commits an offset past any failed one, silently and permanently losing the correlation row that record would have produced. Bounded downstream impact (the corresponding DLR just falls into dlr-manager's `NotFound → retry → DLQ` path), but a real silent-loss path with no alert.
2. **Low — the retention job for `dlr.dlr_correlation` partitions doesn't exist anywhere in the repo.** `dlr.drop_old_correlation_partitions` is defined in migrations but never called by any cron/scheduler/application code; `EnsurePartition` only ever creates partitions. Not a bug in this service's own logic, but it directly widens the collision window behind dlr-manager finding #1 above.
3. Low — `EnsurePartition` does two round-trips (current + next hour) on every non-empty flush — minor overhead only.

### partner-notification-service

1. **HIGH — SSRF: the outgoing partner webhook URL is used with zero validation or allowlisting.** `internal/notify/rest_client.go:38-78`, config source `internal/config/partner.go:90-106`, schema `config_schemas/partner.schema.json` (`notification_callback_url` only requires `format: uri`). No scheme allowlist, no DNS/IP check against RFC1918/loopback/link-local/cloud-metadata ranges. A partner application record (managed via Configuration Service/Backoffice, or simply misconfigured) pointing `notification_callback_url` at an internal cluster address or `169.254.169.254` causes this service to issue authenticated-looking internal HTTP POSTs carrying message data to that target, indefinitely, from inside the cluster network, for every terminal lifecycle event on that application.
2. **HIGH — spec violation: gRPC to Partner SMPP Gateway uses `insecure.NewCredentials()` although mTLS is explicitly mandated.** `internal/notify/grpc_client.go:41-53` (line 47). `hld.md:410,623,1038` and `service_io_contracts.md:46,534` both require mTLS for exactly this call. As implemented there is no TLS at all — any host reachable at the registry-resolved endpoint string is trusted blindly, plaintext on the wire. If the Runtime Redis registry entry is ever poisoned or a rogue pod claims that address, this service hands it partner delivery data with no way to detect it.
3. **MEDIUM/HIGH — no signature/HMAC/nonce on outgoing REST callbacks.** `internal/notify/rest_client.go:21-27` — a bare JSON body, no `X-Signature`/shared-secret/timestamp+nonce. A partner has no cryptographic way to verify a webhook actually came from the platform. Combined with finding #1, an SSRF-redirected request also carries no verifiable provenance for whoever ends up receiving it.
4. **MEDIUM — retry storm: fixed 30s retry interval with no backoff/jitter/circuit-breaker, only a flat 24h TTL cutoff.** `cmd/partner-notification-service/main.go:123-124`, `internal/schedule/schedule.go:25-30` — every failed delivery retries every 30s for up to ~2,880 attempts during a sustained partner outage, amplifying load against an already-struggling endpoint instead of backing off.
5. **MEDIUM — `FirstApplication` can route a notification to the wrong application's channel/URL within a partner.** `internal/config/partner.go:63-80`, used at `internal/kafkaio/kafkaio.go:157` — `msgctx:{message_id}` only carries `partner_id`, not `application_id`, so channel resolution always uses the partner's first configured application regardless of which application actually submitted the message. For a partner with two applications with different `auth.type`/callback URLs, a message from application B can have its delivery-status pushed to application A's URL/SMPP bind — a real cross-application misdelivery of delivery-status data, self-documented as a known limitation but a live functional bug.
6. **MEDIUM — a transient Redis failure after a successful retry-path delivery causes a duplicate webhook/deliver_sm.** `internal/kafkaio/kafkaio.go:171-176` — if `attemptDelivery` succeeds but `PendingStore.Delete` fails afterward, the caller doesn't commit the Kafka record, the task redelivers, and the cached event (delete never completed) triggers a second delivery attempt for the same lifecycle event, with no documented idempotency contract for partners to dedupe on.
7. Low/Medium — `SmppClient.conns` (`internal/notify/grpc_client.go:31-53`) grows unbounded for the process lifetime, keyed by endpoint string and never evicted; since gateway instances are addressed by pod/instance endpoint via a registry that changes on every restart/rescale, a long-running process steadily accumulates stale idle `grpc.ClientConn`s with their own keepalive goroutines.
8. Low — inconsistent poison-message policy vs. the two DLR services: malformed `message.lifecycle`/`notification.retry` records are silently acked here (`internal/kafkaio/kafkaio.go:118-123,135-141`) rather than blocking the commit — no DLQ, no retry, no alert.

**Test quality**: `rest_client_test.go`/`grpc_client_test.go` cover only happy-path/status-code branching against real local servers — no test for a malicious/internal callback URL, no TLS/mTLS test, no signature test, no retry-storm test, and no test reproducing the `FirstApplication` misdelivery or the delete-after-success duplicate-delivery race.

**Cross-service note**: the DLR correlation *read* gap (dlr-manager #1) combined with the *absent* retention job (dlr-correlation-writer #2) together form the most severe finding in this group — each service individually behaves as documented, but together they leave an unbounded, growing window where `smsc_message_id` reuse can silently misroute delivery outcomes to the wrong partner.

## subagent-1 / backoffice-api + partner-api + operator-http-gateway (Go)

Three externally/internally-reachable API surfaces, reviewed with extra weight on authz/authn since two are externally reachable and one is the platform's admin control plane.

### backoffice-api

1. **CRITICAL — no authorization at all: any valid Keycloak token can perform every destructive admin action.** `internal/auth/jwt.go:1-12`, `internal/httpapi/router.go:42-61` — the middleware only checks JWT signature and that `sub` is non-empty; there is no role/scope/permission check anywhere before config CRUD/archive, `ApplyOverride`/`ClearOverride` on execution control, or force-scheduler-command handlers. `hld.md §25` explicitly requires RBAC in Backoffice. As implemented, any staff member with any valid token for the realm (e.g. a read-only support account) can `POST /v1/execution-control/override` with `scope=GLOBAL,state=PAUSED` and halt platform-wide message processing, or force-timeout/force-retry arbitrary stage executions, or archive production config versions. Only an after-the-fact audit trail exists — no privilege check beforehand.
2. **HIGH — internal gRPC calls to Configuration/Execution-Control/Replay Service are plaintext, not mTLS.** `cmd/backoffice-api/main.go:74-76,120-136` — `insecure.NewCredentials()`, contradicting `hld.md §25`'s mTLS-between-internal-services requirement. Anyone reachable on that internal network (e.g. a compromised neighbor pod) can impersonate Backoffice API and call `ApplyOverride`/`CreateVersion`/`RequestReplay` directly with an arbitrary spoofed `requested_by`, bypassing the one audit control that exists.
3. **MEDIUM — destructive endpoints have no confirmation/second-factor and don't require a non-empty `reason`.** `internal/httpapi/executioncontrol.go:32-94`, `scheduler.go:22-67`. Combined with #1, one HTTP call from any valid token is sufficient to pause/freeze the platform with a potentially blank audit reason.
4. **MEDIUM — `/readyz` never reflects real dependency health.** Static ready-flag set once at startup, never checks Postgres/ClickHouse/Kafka/the three gRPC backends.
5. Low — internal error strings (raw SQL/gRPC/driver text) leaked to HTTP callers across `dlq.go`, `reconciliation.go`, `report.go`, and the 502 paths elsewhere.
6. Low — no request body size cap on any mutating endpoint (`json.Decode` with no `http.MaxBytesReader`).
7. Low — no HTTP server timeouts (`ReadTimeout`/`WriteTimeout`/`IdleTimeout`) — Slowloris-class exposure.
8. Low — negative `offset` isn't validated, surfaces as a raw DB error via #5.

### partner-api

1. **HIGH — JWT validation checks signature only, no `aud`/`iss` verification.** `internal/auth/jwt.go:37-61` — if the same Keycloak realm/key is reused for other clients (common setup), a token minted for a different audience but signed by the same key is accepted here — a token-confusion/cross-service replay risk.
2. **MEDIUM — no rate limiting on any partner-facing endpoint** (`/v1/messages/status`, `/v1/messages/search`, `/v1/reports`) — a partner or leaked token can hammer Postgres/ClickHouse with unbounded volume via non-trivial filtered queries.
3. Medium — no HTTP server timeouts (externally reachable, so more directly exploitable than the equivalent gap elsewhere).
4. Medium — `/readyz` never reflects real DB health (same static-flag pattern as backoffice-api).
5. Low — internal error strings leaked to *external* partner callers (`status.go:68,87`, `search.go:69`, `report.go:57`) — more sensitive here since the caller is outside the org.
6. Low — negative `offset` not rejected, same class as backoffice-api.
7. Low — neither validator enforces `exp` presence (`jwt.WithExpirationRequired()` unused) — a token omitting `exp` is accepted as never-expiring.

**Test quality note (partner-api):** the store layer does correctly scope every query by `partner_id` (including the `LifecycleHistory` ownership check), which is good — but no test ever asserts partner A can't read partner B's data (all tests use a single partner "acme"), so this multi-tenant-isolation invariant — the single most important property of this API — has zero regression protection. All Postgres/ClickHouse integration tests silently skip when no local DB is reachable, so in CI without provisioned databases this logic may never execute at all.

### operator-http-gateway

1. **CRITICAL — unauthenticated memory-exhaustion DoS on the public DLR webhook.** `internal/webhook/webhook.go:61-66` — `io.ReadAll(r.Body)` runs *before* `Authenticate`, with no `http.MaxBytesReader` and no `ReadTimeout`/`MaxHeaderBytes` on the server. Since this endpoint must be internet-reachable for real operators, any unauthenticated caller can POST an arbitrarily large or slow-trickling body and force unbounded in-memory buffering with no timeout to abort the read — a trivial, credential-free DoS.
2. **HIGH — `webhook_auth` is one hardcoded shared secret for all operators, compared non-constant-time.** `cmd/operator-http-gateway/main.go:107` (default `"demo-webhook-token"`), `internal/webhook/webhook.go:24-30` (`==` comparison). Spec calls for a per-operator secret delivered via `config.changes`; here it's one static secret for the whole deployment. Anyone who obtains it can forge DLR callbacks for any tracked message, corrupting delivery status and feeding false data into reconciliation/billing.
3. **HIGH — multi-segment submit loses per-segment tracking data.** `internal/grpcserver/server.go:61-96` — loops per segment issuing real HTTP submits, but publishes only one `OperatorSubmitAccepted` afterward with `segmentID` hardcoded to `0` and `smscMessageID` overwritten each iteration. A 3-segment SMS silently drops segments 1 and 2's `smsc_message_id`; a later DLR for either lands in `operator.dlr.unresolved`, and reconciliation treats those segments as `UNKNOWN` even though the operator accepted them.
4. **HIGH — partial multi-segment failure causes duplicate real-world delivery.** Same loop: if segment 1 is accepted (already sent to the handset, irreversible) but segment 2 is rejected, `Submit` returns failure without ever publishing acceptance for segment 1 — the caller retries the whole message, very likely resending segment 1, and the subscriber receives it twice.
5. **MEDIUM — `config.changes` isn't consumed at all, and `endpoint_url` has zero SSRF validation.** All per-operator settings (`tps_limit`, `endpoint_url`, `webhook_auth`, retry/reconnect policy) are static env vars, not the documented per-operator local-snapshot mechanism. Separately, outbound submits POST to `endpointURL` with no scheme/host allowlist and no private-IP/metadata-endpoint blocking — not yet exploitable since it's deploy-time-only today, but must be closed before `config.changes`-driven endpoint updates (the intended architecture) land, not after.
6. Medium — `OperatorDlr.segment_id` is never populated, compounding #3 — per-segment DLR correlation for the HTTP path is effectively unimplemented.
7. **MEDIUM — TPS is checked once per gRPC `Submit` call, not per outbound HTTP request**, so a message with N segments consumes 1 rate-limit token but generates N real operator-facing requests — actual submit rate can exceed the configured limit by up to Nx on multi-segment traffic.
8. Low — `/readyz` reports ready unconditionally; a failed Redis route registration at startup is only logged, not fatal, and doesn't block readiness.
9. Low — no timeouts/mTLS on the internal gRPC server or the webhook HTTP server.

**Test quality:** no test in operator-http-gateway exercises a multi-segment `SubmitRequest` (every test uses exactly one segment) — findings #3/#4/#7 are invisible to the existing suite despite being real, reproducible-in-production bugs.

### Cross-cutting (all three services)
- Identical `/readyz` implementation across all three: a static boolean set once at startup, never tied to actual dependency health — systemic, not one-off.
- None of the three externally-reachable HTTP servers set `ReadTimeout`/`WriteTimeout`/`IdleTimeout` — all open to slow-client connection exhaustion.
- `partner-api` and `backoffice-api`'s JWT validators are structurally identical and share the same two gaps: no `aud`/`iss` check, no enforced `exp` presence.

## subagent-1 / operator-smpp-session-manager + partner-smpp-gateway (Java, SMPP protocol)

Both services independently implement the same hand-rolled SMPP 3.4 codec (Netty-based) — one as an inbound SMPP server (partner-facing), one as an outbound SMPP client (operator-facing). The codec is shared logic with copy-pasted divergence, which is why some defects appear on one side but were independently fixed (or not) on the other. Both correctly bound the wire frame to 64 KiB and cap `short_message` length via the unsigned-byte `sm_length` field — the classic "PDU claims huge length → huge allocation" DoS is mitigated by construction.

### partner-smpp-gateway

1. **CRITICAL — the gRPC `PartnerDeliverSmService` has zero authentication, contradicting the documented mTLS requirement.** `Main.java:58-59` builds the gRPC server with no TLS, no mTLS, no interceptor at all. `platform_contracts.md` explicitly specifies mTLS for exactly this call (Partner Notification Service → Partner SMPP Gateway `deliver_sm`). `DeliverSmServer.java:36-67` authorizes purely on non-secret request fields (`partner_id`, `system_id`, `session_epoch`). Any workload that can reach the pod's gRPC port (a compromised/misconfigured neighbor pod, absent a NetworkPolicy) can forge a `DeliverSmRequest` and inject it as a genuine `deliver_sm` into a partner's live, bound SMPP session — forged delivery receipt / MO injection with no authentication check at all.
2. **HIGH — `submit_sm_resp=ESME_ROK` is returned before the Kafka publish is known to succeed; publish failures are silently discarded, producing a false ack over real data loss.** `server/SmppServerHandler.java:120,123` — `incomingSink.accept(incoming)` fires-and-forgets into `producer.send()` (`kafkaio/IncomingPublisher.java:39-42`, `Future` result discarded, no callback) immediately followed by an unconditional `ESME_ROK` response. A transient Kafka unavailability after the ack causes the message to never reach `incoming.messages`/Pipeline Engine — permanently lost, with the partner told it was accepted.
3. **HIGH — no `exceptionCaught` handler; malformed PDUs are silently dropped with the connection left open, and the documented GENERIC_NACK-for-unknown-command_id path is dead code.** `server/SmppServerHandler.java` has no exception handler at all; `codec/PduCodec.java:135` throws for any unrecognized command_id *before* the switch that would route to `GENERIC_NACK` ever runs. Separately, `codec/SmppStrings.java:19-26`'s `readCString` loops with no length cap — a `system_id` field missing its NUL terminator reads across field boundaries until the 64 KiB frame buffer is exhausted, throwing `IndexOutOfBoundsException`. Both exceptions propagate to Netty's default tail (logged, ignored) — no NACK, no connection close, the peer hangs with no response. The operator-side equivalent (`OperatorSmppClientHandler.exceptionCaught`) does handle this — the more-adversarial, partner-facing side is the one missing the safety net.
4. **HIGH — no idle/read timeout and no connection cap on the SMPP listener — trivial connection-exhaustion DoS.** `server/PartnerSmppServer.java:66-69`'s pipeline has no `IdleStateHandler`/`ReadTimeoutHandler` and no max-connections guard. A peer opening many raw TCP connections and sending nothing consumes a channel+FD indefinitely.
5. Medium — non-constant-time password comparison (`server/StaticAuthenticator.java:20`, `.equals()`), a real timing side-channel combined with no IP allowlist/connection cap — documented as a placeholder but the exact shape likely to get copy-pasted into the real implementation.
6. **MEDIUM — `check_admission`/`execution.control` backpressure is entirely unimplemented, and unlike other simplifications, not disclosed in the README** — suggesting an unintentional gap. Only a fixed local token bucket gates traffic; it cannot react to a platform-wide PAUSED/DEGRADED state.
7. Medium — no TLS anywhere (SMPP socket or gRPC) despite `hld.md §25` mandating it; credentials and message bodies travel in cleartext on both legs; not disclosed in the README.
8. **MEDIUM — data corruption: message bodies are decoded with the JVM platform-default charset regardless of `data_coding`, silently mangling UCS2 text.** `core/IncomingMessageBuilder.java:41,433-438` correctly *labels* `data_coding=8` as UCS2 but never actually decodes as UTF-16BE. Cyrillic/Uzbek text (the exact alphabet this platform's Policy layer is built to handle) becomes mojibake, silently breaking downstream banword/template matching, not just display.
9. Low — `SubmitValidator` only validates `destination_addr` length and `short_message` size; `source_addr`/`service_type` are unbounded and unvalidated before flowing into `SmsPayload.sender`, which Policy's `validate_sender` depends on.
10. Low — heartbeat is never scheduled (self-disclosed in README) — a live session's Redis registry entry TTLs out even while the TCP connection stays healthy.

**Test quality:** existing PDU/integration tests only exercise well-formed PDUs produced by the same encoder — no malformed/truncated PDU, no unterminated C-string, no unknown command_id, no mid-flight disconnect test. Findings #3 and #8 would have been caught by a single adversarial-input test.

### operator-smpp-session-manager

1. **CRITICAL — no reconnect on a post-startup disconnect; a dropped operator connection is never recovered, and `/readyz` never reflects it.** `Main.java:98-118` runs the connect-and-bind sequence exactly once, at startup; nothing hooks a later disconnect back into a reconnect attempt, and `health.setReady(true)` is set once and never re-evaluated against `client.isActive()`. A graceful SMSC restart or a network blip permanently black-holes all submits for that operator until someone manually restarts the pod — directly contradicting the documented `reconnect` responsibility for this service.
2. **HIGH — the `pendingResponses` correlation map leaks an entry forever on every submit/bind that times out or fails before a response arrives — unbounded memory growth under exactly the operator-slowness conditions this service must survive.** `client/OperatorSmppClientHandler.java:21` — an unbounded `ConcurrentHashMap` with no expiry; entries are only removed on a genuine matching response or a full channel-level exception (which clears everything). A congested/slow SMSC exceeding the 5s submit timeout, or silently dropping individual responses (a real-world SMSC failure mode), leaks one `CompletableFuture` per such submit — a slow, operator-triggerable memory leak under sustained load.
3. **HIGH — no real SMPP "window" (bounded outstanding un-acked PDUs); `submit()` blocks a gRPC thread for up to 5s per segment, per call.** Only TPS is rate-limited, not concurrent-outstanding count; combined with #2, a congested operator can drive many concurrent blocked gRPC threads and leaked map entries simultaneously, risking gRPC thread-pool exhaustion that can starve other, healthy routes co-located on the same instance (per the platform's per-instance route-ownership model).
4. Medium — a single malformed/adversarial PDU from the operator (or a MITM, since this leg is also cleartext) tears down the entire operator session; combined with #1, one bad PDU permanently kills the route until manual restart.
5. Medium — no TLS on the operator SMPP connection or the internal gRPC servers, despite `hld.md §25`.
6. Low — multi-segment submits aren't atomic: a mid-message timeout/rejection on segment N aborts the loop without compensating for already-accepted segments 1..N-1, and typical retry-on-ambiguous semantics can then duplicate segment 1 on the subscriber's phone.
7. Low — DLR `raw_status` decoded via platform-default-charset `new String(bytes)` — same class of bug as partner-side #8, lower real-world impact since DLR text is normally ASCII.

**Test quality:** README explicitly admits `reconnect` is untested ("needs a real TCP disconnect"); no test kills the fake SMSC connection mid-submit, sends a malformed PDU, or inspects `pendingResponses` size after a timeout — any of which would have surfaced findings #1, #2, or #4 immediately.

### Cross-cutting (both SMPP services)
The shared `readCString`/unknown-command_id fragility manifests differently on each side (silent-drop on the partner side because `exceptionCaught` is missing there; session-teardown-with-no-reconnect on the operator side because reconnect is missing there) — fixing both requires the same shared codec fix plus per-side wiring (exceptionCaught on the partner side, reconnect-on-disconnect on the operator side, bounded `pendingResponses` eviction on timeout). Neither service implements TLS/mTLS despite `hld.md §25` requiring it, and this gap is disclosed in neither README, unlike other explicitly-acknowledged simplifications.

## subagent-1 / billing-ledger-writer + billing-outbox-publisher + billing-reconciliation + delivery-reconciliation-service (Java)

Overall shape: every low-level pure-function component (state machine, drift classifier, evidence resolver, mappers) is well-written, uses fixed-point integer/BigDecimal money correctly, and is decently unit-tested. The systemic problem is entirely in the four `Main.java` orchestration classes: default Kafka auto-commit is left on everywhere data loss matters, and in both reconciliation services the fully-built recovery/evidence-gathering code exists and is tested — but is simply never wired up, so the running system silently does less than half of what its own docstrings and tests describe.

### billing-outbox-publisher — Critical

1. **Failed/interrupted stream entries are never retried — silent, permanent loss of ledger events (worse than config-event-publisher's poison-message bug: silent drop, not queue-block).** `redisio/OutboxStreamReader.java:73-77` always reads via `XREADGROUP ... STREAMS key >` (never-before-delivered entries only); `Main.pollAndPublish` (`Main.java:46-61`) only acks on success — on any exception (Kafka publish failure, malformed data, transient broker unavailability) it logs and moves on, and there is no `XCLAIM`/`XAUTOCLAIM` logic anywhere in the service. That entry sits in the consumer group's PEL forever and is never retried by anyone. Since the charge was already atomically applied against the hot Redis balance before being written to the outbox stream (per `hld.md §15.4`), it will now never reach `billing.ledger` → never reach Postgres — the ledger (documented as the final accounting source of truth) permanently under-represents this account. If billing-reconciliation's recompute-from-ledger path (see below) is ever wired up, it would compute a lower "true" balance than reality and could force-apply that wrong, lower balance during fenced-CAS recovery — silently erasing real revenue. Also applies across restarts: entries delivered-but-unacked to a consumer that crashes/restarts under a new `HOSTNAME` are permanently orphaned in the old consumer's PEL name. No metric exposes PEL depth (`/metrics` is a hardcoded placeholder in all four services), so this is invisible until reconciliation flags drift days later.
2. Medium — ungraceful shutdown (`Main.java:36-41`) can race an in-flight publish/ack, leaving an already-Kafka-published entry pending forever in the PEL — bounded by ledger-writer's `ON CONFLICT DO NOTHING` idempotency downstream, but the entry still rots unacked.

### billing-ledger-writer — Critical

3. **Default Kafka auto-commit + swallow-and-continue exception handling silently and permanently loses ledger events on any transient failure — and the outage window is unbounded, not just the length of the failure.** `Main.java:39-43` never sets `ENABLE_AUTO_COMMIT_CONFIG` (defaults to `true`, 5s interval); the per-record catch only `System.err.println`s. Because the single JDBC `Connection` (`Main.java:32`) is created once at startup and never re-established or pooled, if the Postgres TCP connection drops for any reason, **every subsequent record forever** fails the same way — the process keeps running, `/readyz` stays `200` forever (one-shot, never re-evaluated), and Kubernetes has no signal to restart the pod. Concrete scenario: Postgres fails over for 30 seconds (routine); every ledger event in that window is dropped via auto-commit, and the consumer then keeps "successfully" failing indefinitely afterward too, since the same broken connection object is reused — so the real outage window is unbounded, not 30 seconds.
4. Low — the JDBC connection is never closed on shutdown (no shutdown hook, no try-with-resources).
5. Low/Medium, self-documented — `LedgerEntryMapper.java:17-21,34-35` hardcodes a 2-decimal-digit minor-unit assumption for every currency; a future non-2-decimal currency would silently produce a wrong ledger amount rather than fail loudly.

### billing-reconciliation — Critical (functional) / High (concurrency, unit correctness)

6. **The service can freeze an account but has no automated path to ever unfreeze it — every real drift event permanently sidelines the account.** `Main.reconcileOne` (lines 86-113) implements detect→classify→(maybe)freeze→audit only. It never calls the fully-implemented-and-tested `BalanceRecomputer`-driven recompute-then-unfreeze, `BillingRedisClient.applyFencedUnfreeze`, or `ExecutionControlClient.triggerUnfreeze` — steps 5-9 of the documented recovery flow (`state_machines.md §3.3`, `hld.md §15.5`) simply don't exist in the orchestration layer. A drift-triggered freeze (even a false positive — see #7) leaves the account FROZEN forever absent manual out-of-band intervention — an availability incident every time reconciliation fires, not the self-healing behavior the design describes.
7. **HIGH — drift computation compares an absolute Redis balance against a full-history ledger *delta*, not a balance — a real false-positive/false-negative risk.** `Main.reconcileOne:96` builds the drift report from `ledgerDelta = SUM(compensating) - SUM(charge)` over the account's entire ledger history — only equivalent to the true balance if the account started at exactly 0 and every balance-affecting event was captured as charge/compensating. The code's own docstring flags there's no ledger entry type for a top-up/initial credit, so any account ever provisioned with a starting balance shows permanent phantom drift. Combined with #6 (no auto-unfreeze), a single historical top-up could permanently freeze an account the first time reconciliation runs against it. Also: no currency-consistency check between the Redis balance and summed ledger rows — mixed-currency ledger data (an upstream config bug) would be summed meaninglessly with no error raised.
8. **HIGH — freeze and triggerFreeze are two separate side effects with no atomicity or retry on partial failure.** `Main.reconcileOne:104-110` — Redis freeze runs first, then a gRPC call to Execution Control; if the gRPC call throws, the audit persist (last line of the method) is never reached, and on the next run the account is no longer ACTIVE so the whole block is skipped — `triggerFreeze` is never retried. Net effect: the account is frozen at the billing layer (charges rejected) but the partner-level Execution Control pause was never applied and never will be automatically, with no audit trail of why.
9. Medium — `partnerId = accountId` is a live TODO (`Main.java:106`), not just a comment; if account_id and partner_id are ever different identifier spaces, freeze/unfreeze calls silently no-op against Execution Control or target the wrong partner scope.
10. Medium — no leader election/distributed lock for multi-replica deployment; the 60s scan reads its account list from a static env-var CSV with no coordination if >1 replica runs (normal for HA) — two replicas racing on `triggerFreeze` would send duplicate control calls, and (once #6 is wired up) racing on `applyFencedUnfreeze` is exactly the "two reconciliation runs on the same account" scenario, though the fenced CAS itself is safe.

### delivery-reconciliation-service — Critical

11. **The service never consumes the evidence topics it needs — every ambiguous case is always resolved with zero evidence, systematically misclassifying delivered messages as "not submitted."** `Main.main` subscribes only to `stage.delivery-reconciliation` (case-opening); there is no consumer anywhere for `operator.submit.accepted` or `delivery.status`, despite `data_infrastructure_spec.md` explicitly listing both as required inputs. `QuerySmClient`/`QuerySmPolicy` and `ReconciliationStore.persistEvidence` are fully implemented and unit-tested but never instantiated/called from `Main`. As a direct result, `sweepDeadlines` always calls `OutcomeResolver.resolve(Evidence.empty(), ...)` — never real evidence — and the service's own test (`OutcomeResolverTest.noEvidenceAtAllAtDeadlineIsConfirmedNotSubmitted`) proves this produces `CONFIRMED_NOT_SUBMITTED` for every case regardless of actual outcome. Concrete impact: a message actually delivered by the operator times out and is reported via `stage.completed` as "not submitted" — the exact signal billing/replay uses to decide not to charge — so the platform will systematically under-charge for (or mis-report as failed) messages that were, in fact, delivered, for 100% of cases this service is invoked for (since `SUBMISSION_OUTCOME_UNKNOWN` — the trigger for this stage — is by definition the ambiguous case). This mirrors billing-reconciliation finding #6 almost exactly: the recovery/evidence code is built and tested, but never wired into the running orchestration.
12. **HIGH — dual-write race between closing a case and publishing its outcome can permanently strand a message.** `sweepDeadlines` calls `store.closeCase(...)` (Postgres) *before* `publisher.publish(...)`, and the returned `Future` is never awaited/checked (unlike billing-outbox-publisher, which does call `.get()`). If the Kafka publish silently fails, the case is already marked closed in Postgres; `findExpiredOpenCases` only looks at `status='open'`, so the case is never revisited and the `stage.completed` event the rest of the pipeline needs to unblock that message's lifecycle simply never arrives — the message is permanently stuck.
13. Medium — `handle_reconciliation_execute`'s create-if-absent (`Main.runExecuteConsumer:97`) isn't atomic, and per the schema `message_id` has only a non-unique index, not a unique constraint (unlike `billing_ledger`'s `charge_id UNIQUE`+`ON CONFLICT DO NOTHING` elsewhere in this codebase). Concurrent processing of the same `message_id` (rebalance overlap, rolling deploy) can create two open rows for one message, each later independently resolved and published as separate `stage.completed` events with different outcomes — a duplicate-processing hazard downstream.
14. Medium — same default-auto-commit + swallow-on-error pattern as billing-ledger-writer (`Main.runExecuteConsumer:80-105`) — a transient Postgres failure while creating a case silently drops the case-open request, and (combined with #11 already making resolution meaningless) that message's ambiguous status is simply never investigated at all.

### Test quality, cross-cutting
All four "real backend" test classes silently `assumeTrue(false, ...)`-skip when Postgres/Redis aren't reachable at `localhost` — in CI without those services running, they report skipped/green with false confidence. No test anywhere exercises the actual `Main.java` orchestration loops — the freeze-without-unfreeze gap, the evidence-never-collected gap, the close-before-publish race, and the auto-commit data-loss patterns are all invisible to the existing (otherwise well-written) unit-test suites, which is exactly why the wiring gaps went unnoticed. `/metrics` is a hardcoded placeholder in all four services, so none of these failure modes are visible from monitoring — they'd only surface as downstream reconciliation alarms or customer complaints.

### Ranking within this group
1. delivery-reconciliation-service never gathers evidence — every case resolves "not submitted" regardless of reality (#11).
2. billing-outbox-publisher permanently drops failed/interrupted stream entries with no retry/reclaim (#1).
3. billing-ledger-writer's auto-commit + swallow-on-error loses ledger events unboundedly once the DB connection breaks (#3).
4. billing-reconciliation freezes accounts on drift with no automated unfreeze — a one-way door (#6).
5. delivery-reconciliation-service can lose a case's outcome permanently via close-before-publish (#12).
6. billing-reconciliation's drift math conflates balance and delta with no top-up/currency handling, risking false-positive freezes (#7); non-atomic freeze/triggerFreeze (#8).
7. Everything else — missing unique constraints, account/partner ID conflation, no leader election, ungraceful shutdown races, hardcoded currency-decimals assumption — medium/low.

## subagent-1 / analytics-writer + lifecycle-writer + replay-service (Go)

All three build clean (`go build ./...`), `go vet` clean apart from cosmetic test-only warnings. The two writer services share one systemic architectural flaw; replay-service has the two most consequential findings of this whole group.

### replay-service — most severe in this group

1. **CRITICAL — no authorization/authentication inside the service itself.** `cmd/replay-service/main.go:78` builds a plain `grpc.NewServer()` — no TLS, no interceptor, no auth check of any kind. `RequestReplay` (`internal/grpcserver/server.go:53-118`) never validates `requested_by`, a free-text string only stamped into the audit table. `hld.md:632-634` states Backoffice API → Replay Service should be gRPC+mTLS; nothing in the repo (no k8s manifests for replay-service exist at all) shows that applied. Cross-checked the caller: `backoffice-api/internal/auth/jwt.go:8` explicitly documents that it only checks for *any* valid JWT, deferring the full RBAC model to a separate LLD that doesn't exist yet (consistent with the backoffice-api authz finding above). Concrete failure: any authenticated Backoffice user, including a read-only support role, can trigger a replay of any `stage_execution_id`; worse, any workload/pod that can reach `replay-service:9000` directly (no NetworkPolicy in the repo preventing this) can call `RequestReplay` with zero authentication and mass-replay the entire DLQ backlog.
2. **CRITICAL — TOCTOU race enables double-replay / double-processing.** `internal/grpcserver/server.go:53-118` + `internal/store/store.go:30-63` (`LoadDlqRecord`, a plain `SELECT`, no `FOR UPDATE`) + `store.go:86-91` (`MarkReplayed`, a separate `UPDATE` issued only after Kafka publish succeeds) — there is no atomic claim step before the checks/republish. Two concurrent `RequestReplay` calls for the same `stage_execution_id` (Backoffice UI double-click, client-side gRPC retry after timeout, two Backoffice API pods proxying the same action) both load the record while `replay_status='pending'`, both pass idempotency checks (`ChargeExistsInLedger`/`DlrCorrelationExists` — the very checks designed to prevent double-billing/double-delivery — both return "not found" because neither's republish has landed yet), and both successfully republish. A `DELIVERY`-stage DLQ record can produce two physical SMS submissions to the subscriber; a `BILLING`-stage record can produce two independent charge attempts hitting the pipeline concurrently.
3. **HIGH — `MarkReplayed` failure silently reopens the record for re-replay.** `server.go:114`: `_ = s.dlq.MarkReplayed(ctx, stageExecutionID)` — error explicitly discarded. If the republish succeeds but the subsequent status UPDATE fails (transient PG blip, pool exhaustion), `replay_status` stays `'pending'` and a later, entirely sequential (non-concurrent, no race needed) `RequestReplay` call republishes a second time.
4. **HIGH — no re-check of Execution Control/pause state before republishing.** `server.go:100-112` republishes directly onto any of the six `stage.*` topics with no `execution.control` check, inconsistent with the codebase's own established pattern elsewhere (Scheduler Critical Sweep and Standard Lane both explicitly re-check `execution.control` before releasing/retrying). Concrete scenario: Billing is intentionally frozen mid-incident via `PARTNER_STAGE=BILLING,PAUSED`; an operator working the same incident replays a backlog of BILLING-stage DLQ records, and Replay Service republishes them straight onto `stage.billing`, bypassing the very pause put in place to stop billing activity during the incident.
5. Medium — no test coverage at all for `server.go`'s orchestration logic (self-acknowledged in the README); the fake-able interfaces (`DlqLoader`/`LedgerChecker`/`CorrelationChecker`/`AuditWriter`) exist but no fakes/tests were written — both Critical bugs above are exercised by zero tests.
6. Low, self-documented — `Republish` (`internal/kafkaio/republish.go:58-73`) republishes `original_command` verbatim without incrementing `attempt`, flagged as an open question in the README.

### lifecycle-writer

1. **HIGH — silent, permanent data loss on write failure: the buffer is cleared before the write is confirmed successful.** `cmd/lifecycle-writer/main.go:174-187` (`flush`) reads and resets `buf.history`/`buf.dlq` to `nil` under lock *before* calling `BatchInsertLifecycleHistory`/`BatchInsertDlq` — if either fails, the error is only logged and the already-cleared records are gone with no retry/DLQ/requeue. Compounding this: the Kafka client has no `DisableAutoCommit`/`AutoCommitMarks` set, so franz-go's default 5s autocommit applies regardless of whether the buffer flush actually succeeded. Concrete scenario: Postgres has a transient outage for a few seconds — the buffered rows for that window are dropped while the consumer keeps polling and committing forward; on restart, those DLQ records (needed later by replay-service!) and lifecycle-history rows are permanently unrecoverable. The same buffer-then-write-then-log-only pattern also applies to the synchronous per-record `InsertReadModel`/`UpdateReadModel` calls.
2. **HIGH — graceful shutdown drops buffered-but-unflushed data on every restart.** `main.go:94-103` — SIGTERM cancels the loop context and shuts down only the health server, with no `sync.WaitGroup`/drain step to flush remaining buffered rows first. Every normal rolling deploy loses up to ~1s of buffered rows and risks `pool.Close()` racing an in-flight `Exec`/`SendBatch`.
3. **MEDIUM — `UpdateReadModel` has no ordering guard against out-of-order/duplicate redelivery.** `internal/store/store.go:41-51` unconditionally overwrites `current_status`/`terminal` with no `lifecycle_version` check (the schema doesn't even carry that column). A partition rebalance causing an older `SUBMITTED` event to redeliver and reprocess after a newer `DELIVERED` was already applied regresses the partner-facing read model backward — a status regression visible to partners via Partner API.
4. Medium — read-model writes are synchronous per-event rather than batched with the other two tables as the spec describes (`service_internal_methods.md:346-352`), risking consumer lag under documented production load.
5. Low, self-documented — `operator.dlr.dlq` isn't consumed despite being a documented input (`service_io_contracts.md §6.1`), so DLR-driven failures never populate the read model/DLQ table via this path.

### analytics-writer

1. **HIGH — same silent-data-loss pattern as lifecycle-writer.** `cmd/analytics-writer/main.go:141-165` clears `buf.records` before `db.FlushBatch` runs; failures are logged only, and the same default-autocommit-decoupled-from-flush-success issue applies. A brief ClickHouse outage produces permanent gaps in `analytics.stage_events` and its hourly materialized-view aggregates with no operator-visible signal beyond a log line.
2. **HIGH — no shutdown drain**, identical pattern to lifecycle-writer — every graceful restart loses up to ~2s of buffered analytics events.
3. **MEDIUM/HIGH — no de-duplication of redelivered events; ClickHouse aggregates get corrupted by duplicates.** `internal/store/store.go:20-33` uses a plain `MergeTree()` with no `ReplacingMergeTree`/version column/dedup key, and `FlushBatch` is an unconditional `INSERT`. Combined with franz-go's own documented duplicate-processing-during-rebalances behavior, redelivered events after any rebalance/restart (routine in Kubernetes) get inserted again as new rows, silently inflating `count()` aggregates surfaced to Backoffice/Partner API report queries, with no way to detect or reconcile after the fact.
4. Low — fetch-level errors from `PollFetches` are never inspected/logged (broker/partition auth failures, out-of-range offsets silently swallowed); unbounded in-memory buffer growth during extended ClickHouse downtime (OOM risk, compounding the data-loss issue once it does die).

### Cross-cutting (this group)
Both writer services share the identical architectural flaw: batch buffering with no crash-safe/at-least-once-with-retry design — buffer-clear-before-write-confirmed, combined with default Kafka offset autocommit, means every transient downstream outage or ordinary process restart is a silent, permanent data-loss event, not just a delay. This is the single most consequential finding across the two writer services. replay-service's two Critical findings (no authorization, no atomic claim in load→check→publish→mark) are the most consequential in the whole group given the described blast radius (double SMS delivery, double billing charge, or unauthorized mass-replay of the DLQ) — and neither is mentioned in the service's own self-documented "open questions" list.

## main / partner-rest-receiver (Rust)

The platform's partner-facing REST ingress — the trust boundary where external traffic first enters the system. Strengths first, since they matter for calibration: no panic-capable call is reachable from untrusted request data anywhere in the per-request path; the "ACK only after confirmed Kafka publish" contract is correctly implemented (202 only follows a successful publish, 503 with a generic body on failure, real error text only goes to server-side logs); unknown-partner and wrong-API-key both map to the same response, avoiding partner-ID enumeration; the one piece of shared mutable state (the rate limiter) is handled correctly for async/Tokio. The findings below are real gaps on top of that solid foundation.

1. **HIGH — `sender_id` has no length/character validation → resource-amplification vector into Kafka.** `src/request.rs:74-76` only checks non-empty, unlike `msisdn` (length+digit validated) and `body` (1600-char cap). It's forwarded verbatim into the full `IncomingMessage` protobuf and published to Kafka, bounded only by axum's default 2MB body limit (no override anywhere). A real SMPP `source_addr` is ≤21 octets. An authenticated partner sending a ~2MB `sender_id` per request turns each request into a ~2MB Kafka message instead of a few hundred bytes; at the example config's 300 TPS for one application, that's up to ~600MB/s of amplification from a single partner — dwarfing the platform's stated ~20k msg/s capacity assumptions and bloating Pipeline Engine's Redis message-context cache accordingly.
2. **HIGH — no idempotency protection: partner-side retries cause duplicate publish / duplicate billing / duplicate SMS.** Nothing in the REST contract gives partners an idempotency-key mechanism, and `generate_message_id` always mints a fresh UUIDv4 regardless of request content — the platform's only downstream dedup key (Billing's `charge_id = stage_execution_id`) is derived from *this* message's own execution and can't detect that two different `message_id`s represent the same logical partner submission. Concrete scenario: a partner's TCP connection drops after this service successfully publishes and returns 202 but before the ACK reaches the client (or the client's own timeout fires first, given up to ~10s worst-case Kafka path latency, see #6); the partner's retry logic re-POSTs the identical payload, and it's treated as an entirely new message — the end user receives, and the partner is billed for, the SMS twice.
3. **HIGH — rate limiting and admission control are skipped entirely for any request that fails authentication.** `src/http.rs:48-81` runs auth *before* admission/rate-limit checks, both of which short-circuit on failure — a request with a wrong or brute-forced API key never touches the token bucket at all, since the per-`(partner_id, application_id)` limiter is only consulted on the success path. There's also no IP-based or global request-rate limiter anywhere (`tower_http` isn't even a dependency). Since `partner_id`/`application_id` are non-secret customer identifiers sent as plain headers, an attacker who knows/guesses a valid pair can send unlimited API-key-guess requests per second against all replicas with zero application-level throttling — an unmitigated credential-brute-force and CPU-flood vector on the auth path itself.
4. **HIGH — as wired for deployment, the auth verifier can never succeed in the real cluster: the ingress is non-functional end-to-end (fails safe/closed, but completely dead).** `src/auth.rs:30-42` (`EnvAuthVerifier::verify`) requires a `PARTNER_CRED_*` env var to be set, else it denies. But `k8s/generate_manifests.py:163`'s secret dependencies for this service list only `redis-runtime`/`redis-configuration`; the rendered manifest injects no `PARTNER_CRED_*` variable; and `infra/secrets/generate_external_secrets.py` has no Vault path for any partner-credential category — there is no pipeline anywhere in the repo that could populate these env vars. Net effect: every partner authentication attempt in the currently-described deployment hits the deny branch and gets rejected with 401. Safe direction, but it means the literal entry point of the whole platform cannot admit a single real message as currently deployed — an infra/wiring gap, not a Rust logic bug, but a total functional block.
5. **MEDIUM — `X-Forwarded-For` IP-allowlist trust has no defense-in-depth.** `src/http.rs:114-131` unconditionally trusts the left-most entry of a client-supplied `X-Forwarded-For` for the IP-allowlist check, safe only because ingress-nginx's default `use-forwarded-headers: false` overwrites (not appends to) the header — a behavior never explicitly pinned in the Terraform ingress config, just relied on as a Helm default. All four externally-exposed services share one ingress-nginx installation; if it's ever reconfigured to trust forwarded headers (e.g. to support a CDN/WAF in front of a different one of the four), every partner's IP allowlist here silently becomes bypassable via a self-set `X-Forwarded-For` header, with no error or log signal and nothing in this codebase to catch the regression.
6. **MEDIUM — no HTTP request timeout, body-size override, or concurrency limit at the app layer.** No `tower_http` timeout/concurrency/body-limit layers exist anywhere (`tower_http` isn't even a dependency). Kafka publish is configured with a 5s producer-queue wait + 5s delivery timeout, both awaited inline in the request handler, so a degraded/unreachable Kafka can hold each in-flight request for up to ~10s with no circuit breaker and no bound on concurrent held requests — and no app-level protection against a slow-body-write (Slowloris-class) client either.
7. Low — health/readiness probes run on an independent listener/task from the business `/v1/messages` port; if the business accept loop or handler pool wedges while the health task keeps running fine, Kubernetes can't detect a "process alive but ingest broken" failure mode.
8. Low — `/metrics` is a static placeholder with no real counters (request volume, status-code breakdown, rate-limit rejections, publish failures) — for an internet-facing ingress this leaves operators blind to abuse patterns like findings #1 and #3 without external log tooling.
9. Low — test suite is happy-path-plus-single-negative-field only: no test exercises a Kafka publish failure through the real async handler (no trait seam on `FutureProducer`), no oversized/adversarial `sender_id` test, no retry/idempotency test, no test asserting rate-limiting still applies on the auth-failure path.
10. Info, self-documented — partner config loads once at startup from a static file; live revocation of a compromised credential or abusive partner requires redeploying all replicas rather than the intended `config.changes` hot-reload — a real incident-response gap at this specific trust boundary, though explicitly acknowledged as a known simplification.

## subagent-1 / backoffice-ui (Vue 3 frontend)

This directly compounds the backoffice-api authorization finding above: the backend has no RBAC, and this UI turns out to have none either — the two gaps together mean the only check anywhere in the whole path from browser to platform-pausing side effect is "does this person have any valid Keycloak token at all."

1. **CRITICAL — zero client-side authorization concept; this UI is the entire control surface for pausing the platform and gates nothing but "has a JWT."** `src/router/index.ts:21-28`'s only nav guard checks `auth.isAuthenticated` (non-null token), nothing about role/claims; `src/App.vue:10-17`'s menu is a static array shown identically to every authenticated user — no branch anywhere hides Execution Control or Force Scheduler Command by role. Confirmed via grep: the string "role" appears nowhere in `src/` except an unrelated field name. Any staff member with any valid token (or anyone who reuses a leaked one — see #3) can open Execution Control and PAUSE the entire platform, or force-replay a stage execution, via a UI that grants full menu access on login. This isn't a UI-only permission gate masking a real backend check (the concern the review was watching for) — it's the reverse: there is no check anywhere, front or back.
2. **HIGH — no confirmation step on any destructive/irreversible action.** "Apply Override" (can set GLOBAL PAUSED), "Clear Override", "Archive config version", and DLQ "Replay" all fire on a single click with no confirmation dialog anywhere in the codebase (verified: no `confirm(`/`NPopconfirm`/`useDialog` pattern exists at all). Per the backend review, backoffice-api itself has no server-side confirmation/reason enforcement either — this UI was the only remaining place in the whole system such a safeguard could exist, and it doesn't.
3. **HIGH — auth token stored in plain `localStorage`, unencrypted, indefinitely reusable, with no in-memory-only or HttpOnly-cookie option.** `src/stores/auth.ts:7,11,19,23`. The code's own comments acknowledge this is a stopgap pending a real OIDC redirect flow, not an accepted risk with compensating controls. Any future XSS (a compromised transitive dependency, or a later dev adding `v-html` to "render DLQ payload nicely") could exfiltrate a token that — per #1 — has zero role restriction and can pause the platform. No XSS sink exists in the codebase today (see positive notes below), but the storage choice removes the one mitigation that would have contained exactly this blast radius if one is ever introduced.
4. **HIGH — no token expiry/refresh handling; expired tokens are sent silently forever, and the resulting failure is unreadable** (compounds #5). `src/api/client.ts:10-24` attaches the bearer token if present but has no response interceptor for 401/403, no redirect-to-login. An ops engineer with a long-lived tab open during an incident will have every subsequent mutating action silently fail with an opaque error once the token expires, with no signal to re-authenticate — exactly the wrong moment for this tool to be confusing.
5. **MEDIUM/HIGH — every error path renders `String(err)` on a JSON object, guaranteed to print the literal string `"[object Object]"` instead of the real reason.** Confirmed across `ConfigView.vue`, `ExecutionControlView.vue`, `SchedulerForceCommandView.vue`, `DlqBrowseView.vue`. Root cause: `openapi.yaml` defines zero 4xx/5xx response schemas for any operation — only success responses — so the actual error object's shape is untyped and `String({...})` always yields `"[object Object]"`. During an active incident (precisely when this tool gets used), staff cannot tell "invalid input" from "server down" from "malformed response."
6. **MEDIUM — no security headers served at all.** `nginx.conf` has no CSP, no `X-Frame-Options`/`frame-ancestors`, no `X-Content-Type-Options`, no HSTS. This admin console can be iframed for a clickjacking attack against a logged-in staff member, and there's no CSP defense-in-depth should an XSS sink ever be introduced later (which would matter enormously here per #3).
7. **MEDIUM — the single most dangerous form has the least input constraint in the app.** `ExecutionControlView.vue:46-54`'s `scope`/`state` fields are plain free-text inputs, unlike the sibling `SchedulerForceCommandView.vue`, which deliberately uses an enum dropdown "for the same open-redirect-style protection as the backoffice-api side" per its own code comment. This is the one form that can set `PAUSED` at `GLOBAL` scope, yet requires typing the exact enum string from memory with no autocomplete or validation — a typo either silently no-ops or behaves unpredictably against loose backend matching.
8. **MEDIUM — the shipped `nginx.conf`/Dockerfile has no proxy route to the API it depends on, and no infra manifest wires one up.** `nginx.conf` serves only static files with SPA fallback; there's no `location /v1 { proxy_pass ... }`, and no file under `infra/ingress`/`infra/terraform` references `backoffice-ui` at all. Deployed as-is without separately wiring an ingress rule, every API call resolves against the nginx container itself, falls through to `index.html` (200 HTML), and `openapi-fetch` fails to parse it — every view breaks identically, an easy trap for whoever wires up the deployment next.
9. Low/Medium — no pagination UI despite the API supporting it (`ConfigView`, `DlqBrowseView`, `ReconciliationView` all use server defaults with no `page_token`/`limit`/`offset` control, self-disclosed in the README) — during a large DLQ backlog (the exact scenario this tool exists for), staff could see only the first page with no indication more records exist.
10. Low — config payload is validated only as "is it JSON," not against the entity's actual JSON Schema that already exists in the main repo (`configuration-service/internal/validate/schemas/*.schema.json`) — semantically wrong config is only caught after submission, if at all.
11. Low — test suite (11/11 passing) covers only auth/router/login plumbing; zero tests exist for any of the six actual views, meaning the exact destructive-action code paths this audit is concerned about (override request bodies, replay rejection handling) have no regression protection at all.
12. Info, self-disclosed — README documents 8 high-severity `npm audit` findings, all transitive dev-dependencies assessed as not exploitable in this build-time-only context, a reasonable call left visible rather than silently ignored.

**Positive findings worth stating explicitly** (the review looked hard for these and did not find them): no XSS sink anywhere (no `v-html`/`innerHTML`, all server data rendered through Vue's default escaping or naive-ui's default table cell renderer); no CSRF exposure (bearer token via header, never a cookie, no state-changing GET); no manual URL/path injection (all filter values go through `openapi-fetch`'s typed query-param encoding); no hardcoded secrets or production URLs anywhere in source.

Note: `services/destination-resolution-service` in `subagent-1` is byte-identical (confirmed via `diff -r`) to the copy in `main` — no separate review needed, findings below apply to both.

## main / billing-service (Java)

Reviewer compiled and ran the test suite (`mvn -o test`) as part of the review — 21/21 pass. Money is modeled correctly as `int64` minor units throughout (no float rounding bugs), and `BillingAccountState` is a clean, genuinely well-tested state-machine core — the strongest part of this service. The rest has real money-safety gaps.

### Critical

1. **`KafkaIo.java:70-87` — offset-commit bug drops messages permanently, not just "may retry twice".** `consumer.commitAsync()` (no args) commits the *whole current fetch position* for the poll batch, not "offset of the record just processed." If record B in a 3-record batch `[A, B, C]` throws (Redis timeout, malformed protobuf, unknown tariff category) and is caught/skipped by the per-record `try/catch { continue; }`, the commit issued after A already advanced past the *entire batch position*— B is never revisited, even on restart. The `stage.billing` command for B is silently dropped forever: no charge, no `stage.completed`, and Pipeline Engine waits forever for that `stage_execution_id`. The inline comment claiming "offset doesn't get committed" is factually wrong for this batch shape. **Zero test coverage for `KafkaIo` at all** (no `KafkaIoTest.java`) — the single worst bug in the service is completely untested.
2. **`TariffResolver.java:55-65` / `BillingAccountState.java:78-92` / `BillingService.java:56-70` — negative `segment_count` is never validated and inverts a charge into a credit.** `segment_count` is a wire `int32` (`stage_contract.proto:68`) flowing unchecked into `perSegment * segmentCount` then `balance - amount`. A negative value (corrupted/malformed/malicious upstream command) makes `applyCharge` *credit* the account instead of charging it, and reports `OUTCOME_SUCCEEDED` with negative `Money.minor_units`. No validation, no test.
3. **`BillingAccountStore.java` (whole class) — read-then-write TOCTOU race across concurrent replicas silently loses charges.** The class javadoc already flags this as a known gap vs. the intended atomic Redis Lua/Function, but the epoch-fencing does **not** protect against it: ordinary ACTIVE charges never bump `epoch` (only freeze/unfreeze do), so two concurrent charges to the same `account_id` from two consumer-group members both pass the epoch check, both read a stale balance, and `save()` is a plain `hset` overwrite (not CAS) — the second writer clobbers the first. Since `billing-service`'s consumer group implies horizontal scale-out is expected (`Main.java:27`), this is a live risk, not theoretical, and the lost charge isn't even detectable later (its `charge_id` never lands in `processedChargeIds`).

### High

4. **`BillingAccountState.java:88-90` + `BillingAccountStore.java:46-48,61` — `processedChargeIds` (dedup set) grows unbounded for the life of an account.** Full `HashSet` copy on every charge, serialized as one comma-joined Redis hash field, no TTL/window/eviction anywhere. At platform-stated scale (~20k msg/s) a long-lived account's dedup set grows into the millions, degrading every fetch/save and eventually risking Redis's 512MB string-field ceiling — a slow-motion outage.
5. **`Main.java` — no graceful shutdown anywhere.** `KafkaIo.run()` is an unconditional `while(true)` with no shutdown hook: no `consumer.close()`/`producer.close()` on SIGTERM, no `health.stop()`, and `BillingAccountStore`/its Lettuce `RedisClient` has no `close()` method to even call. Standard Kubernetes termination leaks connections and abandons in-flight sends.
6. **`KafkaIo.java:80` — synchronous, unbounded-timeout `producer.send(...).get()` per record inside the poll loop.** A slow/partitioned broker can stall the loop past `max.poll.interval.ms`, triggering a mid-processing rebalance, which raises the odds of finding #3 firing.

### Medium

7. `BillingAccountStore.java:35-64` — a brand-new Redis TCP connection is opened/torn down on *every* `fetch()`/`save()` call (2 per message); no pooling, and the `RedisClient` itself is never closed.
8. `TariffResolver.java:29-42` — missing `currency`/`price_per_segment` keys in the tariff JSON throw a raw unwrapped `NullPointerException` (only the `BLOCKED` key is defensively checked); `Main.main` has no catch around `TariffResolver.fromFile`, so a bad ops-pushed tariff file crashes the process with a cryptic stack trace.
9. `TariffResolver.java` — schema-required `default_category` fallback (`data_infrastructure_spec.md §1.6a`) is never read/used; unrecognized categories unconditionally throw instead of falling back, so an unrecognized-category message aborts the whole stage instead of degrading gracefully.
10. `BillingService.java:56-70` — the `ALREADY_PROCESSED` (duplicate-delivery) path re-resolves tariff price fresh rather than echoing the price actually charged the first time; balance safety is fine (dedup check protects that), but the reported `BillingResult.amount` on retries can silently disagree with what was truly charged if tariff config is hot-reloaded between deliveries — and `TariffResolver` ignores `StageExecuteCommand.config_versions` entirely, which exists for exactly this case.
11. `HealthServer.java:19-53` / `Main.java:19-21` — `/readyz` flips true as soon as the HTTP server starts, *before* the Redis store or Kafka consumer/producer are constructed; none of those constructors verify connectivity (lazy clients). A k8s readiness probe can mark the pod ready while Redis/Kafka are unreachable.
12. `BillingAccountStore.java:53-64` — no `currency` stored/checked alongside balance; benign today (single currency) but a silent-corruption trap if a second currency is ever introduced.
13. `BillingAccountState.java:78-92` — no overdraft/minimum-balance check; every charge unconditionally succeeds regardless of resulting balance. Possibly intentional postpaid design (freeze is triggered by reconciliation drift, not balance sign) but undocumented — worth an explicit confirm.

### Low / quality
14. `HealthServerTest.java:24` — binds to a pseudo-random port instead of port `0`; flaky-test risk under CI port contention.
15. `HealthServerTest.java:52` — method named `metricsReturns200NotFound` actually asserts `200` — copy-paste residue, confusing name.
16. `BillingServiceTest.java:19-22`, `TariffResolverTest.java:12-15` — locates the real tariff file via `user.dir`-relative `../../config_schemas/...`, brittle to test-runner working directory.
17. `HealthServer.java:43` — `server.stop(0)` uses a zero-second grace period, can cut off an in-flight response.
18. `KafkaIo.java:73-84` — one broad `catch (Exception e)` treats network errors, malformed-protobuf errors, and genuine programming bugs identically as "skip and log," amplifying #1's blast radius.
19. `BillingService.java:65-66` — `"ACCOUNT_FROZEN"`/`"STALE_EPOCH"` reason codes are hand-typed string literals rather than derived from the `ChargeOutcome` enum — silent-drift trap on a future rename.

## subagent-1 / config-cache-projector, config-event-publisher, consent-cache-projector (Go)

### Cross-cutting (all three services — shared template, shared defects)

- **Kafka autocommit is decoupled from processing success — silent, permanent data loss on any transient error, no retry, no DLQ.** None of the three `NewConsumer()` calls pass `kgo.DisableAutoCommit()`; franz-go's default autocommits the poll position every 5s *regardless of handler success*. A failed `WriteProjection`/`ApplyConsentChange` (e.g. a Redis timeout) is only logged — the record is never retried, and its offset commits on the next 5s tick anyway. If no later update ever arrives for that entity, the projected cache is **permanently stale/missing with no automatic recovery** (consent-cache-projector's own README admits full resync isn't implemented either). This is the single most consequential bug in these three services — it silently breaks the "eventually consistent projection" guarantee the whole design depends on.
- **No `sync.WaitGroup` around the background goroutine before `Close()` on shutdown**, in all three `main.go`s. SIGTERM cancels the context and `main()` returns immediately into deferred `Close()` calls without waiting for the goroutine to observe cancellation — a rolling deploy can race an in-flight `Publish`/`WriteProjection` against connection teardown ("use of closed connection", dropped in-flight work).
- **`/readyz` never reflects real downstream health after startup.** All three `internal/health/health.go` implementations flip ready=true once, unconditionally, right after starting the Kafka goroutine — before confirming the broker connection works, and never flipped back false if Kafka/Redis/Postgres dies later. A k8s readiness probe keeps routing to a pod doing nothing. `/metrics` is a hardcoded placeholder (`..._up 1`) in all three, never real.
- No test in any of the three exercises the actual Kafka consume/produce loop (`Consumer.Run`, `runPollLoop`, `Publisher.Publish`) — only pure decode/build helper functions are unit-tested. The autocommit, poison-message, and shutdown-race bugs above are all real but untestable-in-principle against the current suite, since no test invokes the code paths that exhibit them. Where Redis is exercised, it's via `miniredis` and is genuinely solid (not superficial).

### config-event-publisher

1. **Critical, compliance-sensitive — `PollOutbox`'s `COALESCE(cv.status, 'active')` makes consent-revocation events structurally impossible to publish as revocations.** `internal/outbox/outbox.go:36-44` LEFT JOINs `config.config_versions cv` to get `status`, but `migrations/V002__config_versions.sql`'s own comment states `policy_template` and `subscriber_consent` never populate `config_version_id` (they use their own tables) — so the join always misses for consent rows and `COALESCE` always resolves to `'active'`, for every subscriber_consent outbox row, opt-out or revocation alike. Downstream, `consent-cache-projector.ApplyConsentChange` (`internal/projector/projector.go:80-83`) branches on `status=="archived"` to `SRem` from the blacklist — a branch that can never be hit through this pipeline as coded. **A subscriber revoking an opt-out can never actually be removed from the Redis blacklist; revocations are silently treated as (re-)additions.** Caveat noted by reviewer: the actual writer of these outbox rows lives in `configuration-service`, not yet implemented in this repo, so this can't be 100% confirmed end-to-end — but as coded today this query is the load-bearing piece and it contradicts the migration's own documented invariant.
2. **Poison-message head-of-line blocking, no bound, no DLQ.** `cmd/config-event-publisher/main.go:109-122` — a row whose `entity_type` `Publish` can't build (or any other permanent error) is logged and skipped but never marked published; since polling is `ORDER BY created_at ASC LIMIT N`, it's re-selected forever as the oldest row, and once poison rows accumulate to match `POLL_BATCH_SIZE` (default 100) they crowd out real pending rows from ever being selected.
3. **No `SELECT ... FOR UPDATE SKIP LOCKED`** in `PollOutbox` (`internal/outbox/outbox.go:36-44`) — if more than one replica runs (typical for HA), both poll overlapping unpublished rows and both publish them, with no coordination.
4. `runPollLoop` continues past a `PollOutbox` error with no backoff (`cmd/config-event-publisher/main.go:110-113`) — a genuinely down Postgres gets hammered every `pollInterval` (500ms default) forever.
5. Postgres-backed outbox tests skip silently when no test DSN is configured — CI without live Postgres shows green while exercising zero SQL.

### config-cache-projector

1. **`subscriber_consent` events aren't filtered out and get written into Configuration Redis, contradicting the documented architecture and duplicating consent PII into the wrong store.** `internal/kafkaio/consumer.go:18-27` (`DecodeConfigChangeEvent`) only checks `entity_id != ""`, unlike its sibling `consent-cache-projector` which explicitly filters (and whose own comment assumes config-cache-projector filters on its side — it doesn't). `data_infrastructure_spec.md §1.9c` explicitly states consent data must project into Runtime Redis, not Configuration Redis (sized for a small bootstrap dataset, not per-subscriber volume). ### consent-cache-projector

The most careful of the three (explicit entity_type filter with doc-comment, README self-discloses known limitations), but:

### pipeline-engine — most severe findings in the whole review

### policy-service

1. **HIGH — `parse_pattern` panics on any multi-byte UTF-8 character in a template pattern.** `src/template_matching.rs:32-63` scans byte-by-byte (`i += 1`) but slices the string at `i` (`pattern[i..]`) to test prefixes — Rust string slicing panics on a non-char-boundary index. LOW/MEDIUM — `RuntimeState.spam_history` (`src/policy_engine.rs:116-121`) never evicts a key once created, even after all its timestamps age out — unbounded memory growth keyed by every distinct (msisdn, category) ever seen. ## subagent-1 / scheduler-critical-sweep (Go)

This is the "critical lane" safety-gated sweep service, and it has the most severe correctness issues found in the subagent-1 branch — several go straight to the core retry/DLQ/pause guarantees the service exists to provide.

### Critical

1. **Republished retry commands are missing `stage_extension`/`payload_ref` — verified to be rejected by downstream stage consumers, not retried.** `internal/kafkaio/builders.go:27-39` (`BuildRetryCommand`), triggered from `cmd/scheduler-critical-sweep/main.go:185-191`. It never sets `StageExtension`/`PayloadRef` on the outgoing `StageExecuteCommand`. Cross-checked against the one real stage consumer in the repo (`destination-resolution-service/src/kafka_io.rs:46-52`): a command with `stage_extension = None` is deterministically rejected with `outcome=REJECTED, retryable=false` — a terminal status, not a retry. Every retry Critical Sweep publishes for a timed-out stage is guaranteed to bounce back as a permanent rejection instead of re-executing. With `MaxAttempts=3`, a message that timed out once churns through 3 fake "rejected" attempts and lands in DLQ with the wrong terminal reason ("policy rejected" instead of "timed out") — a data-correctness problem for anything reading `stage.completed`/lifecycle downstream. Self-flagged as an "open question" in the README, but confirmed 100%-reproducible against the one real consumer available to check it against, not speculative.
2. **The same missing-extension defect also corrupts `DlqRecord.original_command`, plus a wrong-attempt-number bug.** `main.go:200-202` synthesizes the DLQ record's "original command" via the same broken `BuildRetryCommand`, which always sets `Attempt: state.Attempt+1` — one higher than the attempt that actually exhausted retries — and again omits `stage_extension`/`payload_ref`/`traceparent`. `platform_contracts.md:45` requires `DlqRecord` to carry a full, replayable original command; if Replay Service republishes this verbatim, it replays with the wrong attempt count and hits the same rejection as finding #1.

### Severe

3. **Four-plus replicas sweep the same Redis keyspace with zero coordination — guaranteed duplicate publishes, not a rare race.** `internal/redisio/client.go` has no leader election, distributed lock, Lua claim script, `WATCH`/`MULTI`, or `SETNX` anywhere. `k8s/generate_manifests.py:97-100` sizes this service to 4 fixed replicas (no KEDA). Every replica independently polls the same buckets every ~1s and only calls `ZREM` *after* successfully publishing — so any replica that polls before another finishes `ClearDeadline` independently republishes the same expired entry with its own fresh `event_id`. With 4 fixed replicas and a 1s poll interval, this is expected steady-state behavior for every expired item, not an edge case: duplicate retry commands, duplicate DLQ alerts, duplicate `TIMED_OUT` completions.
4. **The `execution.control` safety-gate consumer uses a partitioned Kafka consumer group instead of a full local mirror — the pause gate can be silently incomplete per replica.** `main.go:128` joins `execution.control` via `kgo.ConsumerGroup("scheduler-critical-sweep")`, unlike the "compacted, local full-mirror snapshot" pattern documented ~10 times across `service_io_contracts.md`. With a real consumer group, `execution.control`'s partitions are divided across the 4 replicas — any pod not assigned the partition holding a given `(scope, scope_id)` key never sees it, and `IsPaused()` (`internal/controlsnapshot/snapshot.go:45-53`) treats a missing key as "not paused" (fail-open, explicitly tested that way). Concrete failure: GLOBAL is set to `PAUSED`, but the pod that doesn't own that partition keeps firing retries as if nothing were paused — defeating the entire "critical lane must fail safe" requirement.
5. **Compounding #4: the manual-command consumer and the control-snapshot consumer share the same literal consumer-group ID for two different topic subscriptions.** `main.go:107` and `main.go:128` both use `"scheduler-critical-sweep"` for `scheduler.critical.commands` and `execution.control` respectively — two separate `kgo.Client`s (×4 replicas = 8 members) joining one group with mismatched subscriptions, which is undefined/fragile behavior for standard consumer-group assignors, independent of and compounding #4.
6. **Readiness flips true before the control snapshot has any chance to warm up, with no reconnect/backoff if it fails at startup.** `main.go:83-87` starts all three loops as fire-and-forget goroutines and calls `SetReady(true)` immediately after; `NewControlSnapshotConsumer` errors are only logged and the goroutine just returns, leaving `snapshot` permanently empty for the pod's whole lifetime with no retry. Combined with fail-open `IsPaused()` (#4), a rolling restart during an active pause incident brings up fresh pods that pass `/readyz` and immediately sweep/retry blind to the pause, potentially for the pod's entire lifetime.

### Moderate

7. `main.go:185-211` — if publish succeeds but the subsequent `ClearDeadline` fails, the entry is silently left in the ZSET and gets reprocessed from scratch next tick with a brand-new `event_id` — no idempotency token ties the two publishes together beyond `stage_execution_id`, which isn't a documented dedup key for `StageCompletedEvent`/`DlqRecord`.
8. `main.go:167-177` — entries with an unresolvable `stage_exec_index` or missing `exec:{message_id}` are never cleared from the ZSET (no `ClearDeadline` call on this path) — they're retried every tick forever with no backoff/dead-lettering/alerting. The service's own README/code comments acknowledge that without a real `stage_exec_index` writer in Pipeline Engine, `ResolveMessageID` "will always error" — meaning in the currently-documented state, *every* expired entry falls into this permanent busy-loop.
9. `internal/sweep/decision.go:49-52` — held (paused) entries aren't backed off; by design `deadline` isn't advanced on `ActionHold`, so every already-expired entry for a paused stage is re-fetched/re-decided on every single ~1s tick for the whole pause duration, adding sustained Redis load exactly when the system is already degraded.
10. `main.go:106-123` — `FORCE_TIMEOUT`/`FORCE_RETRY` manual commands are decoded and logged but never acted on (self-documented in README, but worth flagging: an operator's emergency force-timeout/force-retry via Backoffice API currently has zero effect).
11. `main.go:80-98` — no `sync.WaitGroup` around the three background goroutines before `defer redisClient.Close()`/`publisher.Close()` fire on shutdown — can race an in-flight publish/`ClearDeadline` pair, reproducing finding #7's duplicate-on-restart scenario on every rolling deploy.
12. `main.go:160-161` / `redisio/client.go:43-44` — local wall-clock is the sole time source for "due" comparisons; no use of Redis's own `TIME`, no skew detection between the node running this service and the node(s) setting deadlines in Pipeline Engine.
13. `main.go:67` — `DEADLINE_BUCKETS` (default 16) is a locally-configured constant with no verification it matches Pipeline Engine's actual bucket count; a mismatch silently drops some fraction of deadlines into buckets this service never scans, with nothing detecting or alerting on it.

### Test quality
`decision_test.go`/`snapshot_test.go` are solid (real boundary cases, `miniredis` for real Redis semantics). But **there is no test file at all for `main.go`** — `processTick`, the function that orchestrates publish→clear ordering where findings #3/#7/#8 live, takes concrete `*redisio.Client`/`*kafkaio.Publisher` types rather than interfaces, so it can't be unit-tested with fakes in its current form; the highest-risk logic in the service is completely untested. `builders_test.go` never asserts `StageExtension`/`PayloadRef` presence on `BuildRetryCommand`'s output — the suite would not have caught findings #1/#2 even in principle.

## subagent-1 / execution-control-service (Go)

Reviewer ran `go build ./... && go test ./... && go test -race ./...` — all pass cleanly (unlike configuration-service). The hysteresis state machine itself (`hysteresis.go`/`ramp.go`/`scope.go`) is a faithful, line-by-line-verified port of the Python reference `state_machines/execution_control_hysteresis.py`, and its tests reproduce the Python reference tests' exact edge-case assertions. This core is solid — the problems are in how it's wired into the rest of the service.

### Critical

1. **Manual overrides for every scope except GLOBAL are never published to Kafka.** `internal/grpcserver/server.go`'s `Server` holds only a `registry` and `audit` persister — **no reference to `kafkaio.Publisher`**, and never calls `Publish`. The only place `Publish` is ever invoked is `runGlobalControlLoop` (`cmd/execution-control-service/main.go:75-99`), which hardcodes `Scope: ScopeGlobal` and evaluates/publishes only that one key on a 10s ticker. Concrete failure, matching a documented core workflow (`state_machines.md §3.3`, `hld.md §15.5`): Billing Reconciliation calls `ApplyOverride(scope=PARTNER_STAGE, scope_id="acme:billing", state=PAUSED)` to freeze a partner's billing stage during fenced recovery. The RPC succeeds, the in-memory registry updates, an audit row is written — and that's the entire effect. No `ExecutionControlRecord` is ever produced to `execution.control` for that scope, so none of its documented consumers (Partner REST Receiver, Pipeline Engine, Billing, Routing, Delivery, Scheduler — `hld.md:823`) ever learn about the freeze. Billing keeps charging the partner as if nothing happened. No error, no log — the caller believes the freeze is live because the RPC returned success. This silently defeats the entire billing-freeze/fenced-recovery mechanism.

### High

2. **Registry mutation is never rolled back when audit persistence fails.** `grpcserver/server.go:85-105` (`ApplyOverride`) / `:116-137` (`ClearOverride`) — the registry mutation executes unconditionally *before* `PersistOverrideAudit` is attempted; if the audit insert fails, the RPC returns an error but the in-memory state change is never undone. Scenario: `ClearOverride` (unfreeze) succeeds in the registry but audit fails → caller sees an error and assumes the unfreeze didn't happen and won't proceed to the next fenced-recovery step — meanwhile the scope is already unfrozen in memory (and for GLOBAL, resumes dispatching on the next tick). The mirror case (freeze) is equally dangerous in the other direction. No compensating action; no test covers this path (the test fake for `PersistOverrideAudit` never returns an error).
3. **Automatic per-scope hysteresis evaluation is only wired for GLOBAL — and understated in the README relative to its real impact combined with finding #1.** `main.go:69-99` only ever evaluates `Scope: ScopeGlobal`; STAGE/PARTNER/PARTNER_STAGE/OPERATOR_ROUTE never get a periodic metrics→hysteresis loop, so automatic circuit-breaking at those scopes — the primary stated purpose of the multi-scope registry — never triggers from metrics at all. The README discloses "control loop only for GLOBAL" but frames it as merely "no automatic evaluation," without acknowledging that (per finding #1) the *manual* path for those same scopes also doesn't propagate — i.e., these scopes have no live effect on the rest of the system at all, metric-driven or manual.

### Medium

4. **`version` never increments for metric-driven state changes.** `internal/registry/registry.go:104-126` returns `Version: e.version` but never increments it in the metric-driven path; only `ApplyOverride`/`ClearOverride` do. Since `version` flows straight into the published `ExecutionControlRecord.Version`, every purely metric-driven record for a scope with no manual-override history carries `version=0` forever, even as state legitimately flips ACTIVE→DEGRADED→PAUSED→... repeatedly — a consumer trusting `version` (the codebase's own convention elsewhere, e.g. `account_epoch`) rather than raw Kafka-offset ordering will never observe a change. Untested.
5. **No bounds validation on override `AdmissionRate`.** `grpcserver/server.go:70-111` accepts any `float64` (negative, or >1.0) with no clamping, flowing directly into the published record that gates real downstream admission decisions.
6. **NaN/Inf from Prometheus silently freezes hysteresis evaluation.** `internal/signals/prometheus.go:43-66` parses sample values with `strconv.ParseFloat`, which accepts `"NaN"`/`"Inf"`; the exact query used in `main.go:86` (`sum(rate(errors[1m]))/sum(rate(processed[1m]))`) legitimately returns `NaN` for `0/0` during low/zero-traffic windows. A `NaN` tick makes every hysteresis comparison false, so a scope stuck `PAUSED` during a quiet period can never confirm recovery — every `NaN` tick silently short-circuits to "no change," with nothing logged to indicate the metric is garbage rather than genuinely still-bad.

### Low
7. Unbounded registry growth (`internal/registry/registry.go:52-78`) — `scopeEntry` map entries are created on first access and never evicted, combined with unvalidated `scope_id` strings accepted from RPC requests.
8. Same generic-error/no-gRPC-status-code pattern as configuration-service (`server.go:72,118`).
9. No retry/backoff on Kafka publish failure (`kafkaio/publisher.go:108-122`) — a failed `ProduceSync` is just logged and dropped; self-heals within 10s for GLOBAL via the next tick, but (per finding #1) there's no publish path at all for non-GLOBAL scopes for this to even matter.

### Test quality
`hysteresis_test.go`/`ramp_test.go`/`scope_test.go` are excellent (exact reproduction of the Python reference tests, solid scope-composition coverage). `registry_test.go` covers override precedence/expiry/isolation well but misses version-on-metric-transition (#4) and audit-failure rollback (#2). `signals/prometheus_test.go` has no NaN/Inf case (#6). `store/audit_test.go` does real Postgres round-trips, skips cleanly without DB. Unlike configuration-service, this all genuinely runs, `-race` clean.

### Ranking across both services
1. execution-control-service: manual overrides for non-GLOBAL scopes never reach Kafka (#1) — the billing-freeze/fenced-recovery path is a silent, untested no-op end-to-end.
2. configuration-service: does not compile (#1) — nothing in `validate`/`store`/`grpcserver`/`main` has ever run, contradicting the README's own claim.
3. execution-control-service: no rollback of registry mutation on audit-persist failure (#2) — caller belief about freeze/unfreeze state diverges from reality.
4. execution-control-service: automatic per-scope hysteresis entirely unwired outside GLOBAL (#3), understated by the README given its combined impact with #1.
5. Everything else (status codes, version non-increment, NaN handling, first-version race, input validation gaps, unbounded registry) — medium/low.

## subagent-1 / scheduler-standard-lane + scheduler-background-lane (Java, Kafka Streams)

Standard Lane is materially riskier than Background Lane — it has two distinct crash-loop bugs and a scope-blindness bug that defeats a core safety mechanism. Background Lane has no crash-class bugs.

### scheduler-standard-lane

#### Critical

1. **Uncaught `IllegalArgumentException` in the global-store control processor crashes the entire instance, deterministically, on every restart.** `topology/ControlUpdateProcessor.java:39-52` — `ControlSnapshot.State.valueOf(rec.getState().name().replace(...))` only handles `ACTIVE/DEGRADED/PAUSED`, but `ExecutionControlState` has a 4th value `UNSPECIFIED` plus an implicit `UNRECOGNIZED` for version-skewed additions; `Enum.valueOf` on either throws `IllegalArgumentException`, which is **not** caught by the surrounding `catch (InvalidProtocolBufferException)`. This runs on Kafka Streams' single `GlobalStreamThread` with no uncaught-exception handler registered in `Main.java` — an uncaught exception there kills the whole client. Because `addGlobalStore` replays the entire compacted `execution.control` topic from scratch on every startup, one record with an unset/default state (a plausible producer bug or version-skew scenario) puts the service into a **permanent crash loop** — it can never reach `RUNNING`, `/readyz` never returns 200, and recovery requires manual intervention.
2. **`ControlSnapshot` only ever evaluates GLOBAL/STAGE scope; PARTNER, PARTNER_STAGE, and OPERATOR_ROUTE pauses are silently ignored, so scoped pauses never block release.** `core/ControlSnapshot.java:34-59` — `isPaused(stageName)` only checks `GLOBAL` and `STAGE` keys. `hld.md §8.1` documents 5 scopes with `effective_rate = min(all applicable rate limits)`, and `HoldCommandProcessor.releaseTick()` (`topology/HoldCommandProcessor.java:82,88`) only ever calls `snapshot.isPaused(stageName)`/`rampRate(stageName)` — never passing the held item's own `scope`/`scopeId` (captured on `HeldItem` at construction). A PARTNER- or OPERATOR_ROUTE-scoped `PAUSED` record is correctly stored in `byKey` (the store-update side handles all 5 scopes generically) but **never read back** by the release path. Concrete failure: ops pauses a single misbehaving partner during a fraud/billing-dispute incident (`scope=PARTNER, scope_id=partner-42, state=PAUSED`) while GLOBAL/STAGE stay `ACTIVE` — `releaseTick()` releases that partner's held items anyway, every second, with zero effect from the pause. Completely untested: neither `StandardLaneTopologyTest` nor `ControlSnapshotTest` ever constructs a PARTNER/PARTNER_STAGE/OPERATOR_ROUTE record.

#### High

3. **Poison-pill crash: an unmapped `StageName` throws inside the sink's `TopicNameExtractor`, and the offending item is never cleared, so it crashes every subsequent tick and restart.** `Topics.stageNameFromString()` silently falls back to `STAGE_NAME_UNSPECIFIED` for unrecognized strings, but `Topics.stageTopic()`'s switch has no `UNSPECIFIED` case and throws instead. `HoldCommandProcessor.process()` never validates `stage_name` before storing it. On the next `releaseTick()`, `publishRelease()` → `context.forward()` invokes the extractor, which throws — **before** `store.delete(...)` is reached, so the bad item is never removed and the changelog-backed state re-triggers the same crash on every restart. One malformed hold command becomes a sustained crash loop.
4. **Held items are never sorted by `heldAtEpochMs` before fair scheduling — the claimed FIFO/no-starvation guarantee doesn't hold in production.** `FairScheduler`'s own javadoc assumes pre-sorted input, but `HoldCommandProcessor.groupByStage()` builds its lists directly from `store.all()`, and RocksDB-backed Kafka Streams stores iterate in **key order** (keyed by `stageExecutionId`, unrelated to hold time) — release order within a group is effectively arbitrary w.r.t. hold time, so newer items can jump ahead of older ones. Masked entirely by tests: `FairSchedulerTest`/`ReleaseBatchSelectorTest` only ever hand-construct already-time-ordered lists.
5. **Per-stage token bucket is fragmented per Kafka Streams partition, multiplying the effective release rate beyond its documented "short-term overshoot" tradeoff.** `bucketsByStage` (`HoldCommandProcessor.java:41`) is a plain instance field, and Streams creates one `HoldCommandProcessor` per assigned partition of `scheduler.standard.commands` — a topic not partitioned by `stage_name`. The intended "one bucket per stage" limit actually exists once **per partition**; with Standard Lane sized at 16 vCPU (`capacity_model.md:110`, implying multiple partitions/instances), the real aggregate rate can be a multiple of the configured limit — a sustained structural effect, not the transient overshoot the `TokenBucket` javadoc explicitly frames it as.

#### Medium

6. `topology/ControlUpdateProcessor.java:39-52` — `expires_at`/`version` on `ExecutionControlRecord` are parsed but never used. `hld.md §8.3` documents `expires_at` as the mechanism for a manual pause to auto-lift; without it, a time-boxed PAUSED/DEGRADED override never expires here and stays in effect until an operator manually publishes a superseding record. `version` is likewise never consulted (no protection against out-of-order/stale updates for the same key).
7. `topology/ControlUpdateProcessor.java:35-38` — tombstones on `execution.control` are correctly identified in a comment but not acted on: the corresponding `ControlSnapshot`/backing store entry is never cleared, so a deleted scope's last-known (possibly restrictive) state keeps applying indefinitely, including across restart-replay.
8. `topology/HoldCommandProcessor.java:106-111` (`reconciliationDeadlineTick`) publishes unconditionally every 30s for all `DELIVERY_RECONCILIATION` holds with no `isPaused`/`rampRate` check at all, contradicting `hld.md:933`'s stated invariant that Standard Lane re-checks `execution.control` before publishing on delayed retry/controlled release — a GLOBAL/STAGE pause mid-incident doesn't stop reconciliation re-queries. Self-acknowledged in the README as an unconfirmed interpretation.

#### Low
9. No SLF4J binding declared in `pom.xml` (only `slf4j-api` transitively via `kafka-streams`) — the bulk of Kafka Streams' own diagnostics are NOP-logged at runtime. Same gap in scheduler-background-lane's `pom.xml`.
10. `HeldItemSerde` (hand-rolled `DataOutputStream`/`DataInputStream` format) has no schema/version tag — a future field change to `HeldItem` will silently misread or throw on old changelog/RocksDB data during a rolling upgrade.
11. Parse failures (`HoldCommandProcessor.java:71-73`, `ControlUpdateProcessor.java:49-52`) are dropped with only a stderr log, offset still committed under EOS — no DLQ, no metric, silent unrecoverable loss of that command.
12. Per-partner/per-task-type quotas from `hld.md §8.5` aren't implemented — only a single per-stage bucket + fairness ordering exist (self-disclosed in the README).

### scheduler-background-lane

Materially safer than Standard Lane — no crash-on-poison-pill class of bug, and unknown-enum handling degrades gracefully instead of throwing.

1. **Medium — full O(n) store scan every second with no due-time index.** `topology/BackgroundCommandProcessor.java:67-74` — `tick()` iterates the entire `background-tasks-store` every second regardless of size; no secondary sorted-by-due-time structure. Not a correctness bug but a real scalability concern for a backlog that grows (retry storms, DLR correlation spikes — a risk `hld.md:943` itself calls out).
2. **Low/Medium — unknown `task_type` is silently dropped with no DLQ/metric.** `topology/BackgroundCommandProcessor.java:80-92` logs to stderr and unconditionally `store.delete(...)`s the task — a version-skewed/unrecognized `task_type` is silently, permanently lost with no alerting.
3. Low — `BackgroundTask.isExpired()` is implemented and unit-tested but never called from the dispatch path; deadline enforcement is fully delegated to the upstream producer. Self-disclosed in the README, but reads as an oversight without that context.
4. Low/Medium — no SLF4J binding (same as Standard Lane, above).
5. Low — `BackgroundTaskSerde` has no schema/version tag (same concern as `HeldItemSerde`, above).
6. Info — `targetTopic` on `BackgroundTask` is described as an allow-list but never actually validated against — `tick()` routes purely by `task.taskType()`. Harmless today (1:1 mapping), but the "allow-listed" framing implies a check that doesn't exist.

### Cross-service consistency
Background Lane's "unknown enum value" path degrades gracefully (log + drop); Standard Lane's structurally analogous path (`StageTopicNameExtractor` on `STAGE_NAME_UNSPECIFIED`) throws and crashes the thread — two sibling services from the same design diverging in fault-handling philosophy in a way that looks like accidental drift, not an intentional difference. Standard Lane should adopt Background Lane's defensive pattern.

### Test quality
Standard Lane's unit tests (`ControlSnapshotTest`, `FairSchedulerTest`, `ReleaseBatchSelectorTest`, `TokenBucketTest`) are reasonable for the narrow paths they cover, but collectively never exercise a PARTNER/PARTNER_STAGE/OPERATOR_ROUTE record (hides #2), always hand pre-sorted lists to the fairness logic instead of routing through the real store (hides #4), and never send an `UNSPECIFIED`/`UNRECOGNIZED` state or stage name through the topology (hides #1 and #3) — no concurrent-access test for `TokenBucket`/`ControlSnapshot` despite both being reachable from multiple Streams threads, no tombstone test. Background Lane's `BackgroundTaskTest`/`DueTaskSelectorTest` cover due/expired boundaries well; gaps are a duplicate-`source_event_id` test, a malformed-protobuf test, and an unknown-`task_type` test.
