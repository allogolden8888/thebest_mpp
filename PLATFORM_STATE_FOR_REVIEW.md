# MPP — состояние платформы и сводка измерений

**Для чего этот документ:** передать другому агенту полную картину без необходимости переоткрывать диагностику. Все числа ниже — результат прямых измерений на живой системе, а не оценки. Где число не проверено, это сказано явно.

**Цель работы:** 300 TPS на локальном стенде с e2e p99 < 350 мс.

---

## 1. Железо и стенд

Docker Desktop VM на Mac: **8 CPU, 7.75 ГБ RAM, 1 ГБ swap**. VM делится с остальными задачами машины.

Для сравнения: тот же код на другой машине (AMD Ryzen 5 7600X, 12 CPU / 15.16 ГБ) давал при 300 TPS **p50=105 / p95=119 / p99=129 мс**. Это важный ориентир: код способен на целевые числа, вопрос в ёмкости стенда.

В горячем пути 15 контейнеров. Полный compose содержит ~40 сервисов; остальные погашены — при всех поднятых Kafka получала OOM-kill под нагрузкой.

---

## 2. Архитектура пути сообщения

### 2.1 Основной конвейер

```
POST /v1/messages
  -> partner-rest-receiver (Rust)          пишет msgctx:{message_id} в Runtime Redis
  -> incoming.messages (Kafka)
  -> pipeline-engine (Rust)                создаёт exec:{message_id}, CAS-переходы
       |
       +-> stage.destination-resolution -> destination-resolution-service (Rust)
       +-> stage.policy                 -> policy-service (Rust)
       +-> stage.billing                -> billing-service (Java)
       +-> stage.routing                -> routing-service (Rust)
       +-> stage.delivery               -> delivery-service (Java)
       +-> stage.delivery-reconciliation -> delivery-reconciliation-service (Java)
       |
       каждая стадия публикует StageCompletedEvent в stage.completed,
       pipeline-engine его читает и решает следующий шаг по графу
```

Граф пайплайна — `config_schemas/examples/pipeline.valid.json`. Ключевой факт: **`DELIVERY: SUCCEEDED` ведёт НЕ в конец, а в `n6_reconciliation`**, и терминальны только исходы этого узла. То есть пайплайн не завершается доставкой.

При терминальном исходе pipeline-engine вызывает `finalize_pipeline` (Lua, `services/pipeline-engine/lua/finalize.lua`), который атомарно удаляет `exec:` и `msgctx:`.

### 2.2 Путь доставки

```
delivery-service --gRPC--> operator-smpp-session-manager (Java)
   -> пейсер (HTB, приоритетные очереди) -> SMPP submit_sm -> SMSC
   -> публикует operator.submit.accepted
```

SMSC — реальный, в одной сети со стендом: **172.30.19.206:8275**, ping min 3.6 / avg 12.3 / max 64.6 мс.

### 2.3 Путь квитанций (DLR)

```
SMSC -> deliver_sm -> operator-smpp -> operator.dlr (Kafka)
   -> dlr-manager (Go)  ищет корреляцию smsc_message_id -> message_id
        попадание -> delivery.status -> delivery-reconciliation-service закрывает case
        промах    -> scheduler.background.commands -> scheduler-background-lane -> повтор

Корреляция пишется параллельно:
   operator.submit.accepted -> dlr-correlation-writer (Go) -> PostgreSQL dlr.dlr_correlation
   (+ быстрый путь в Redis dlrcorr:*, добавлен в ходе работы, см. §5.4)
```

### 2.4 Хранилища состояния

**Runtime Redis** — 4 ключа на сообщение:

| префикс | владелец | освобождение |
|---|---|---|
| `exec:{message_id}` | pipeline-engine | `finalize_pipeline` при терминале, TTL 24ч как страховка |
| `msgctx:{message_id}` | partner-rest-receiver | то же (добавлено в ходе работы) |
| `dlvsubmit:{stage_execution_id}` | delivery-service | **только TTL 24ч — не освобождается по терминалу** |
| `dlrcorr:{op}:{smsc_id}:{seg}` | delivery-service | TTL 15 минут |

**PostgreSQL** — `dlr.dlr_correlation` (RANGE-партиции по часам), `reconciliation.reconciliation_cases`, `messaging.message_lifecycle_history`.

**ClickHouse** — `analytics.stage_events`, пишет analytics-writer. Важно для методики: `occurred_at` берётся из **payload-таймстампа продюсера**, а не из времени вставки, поэтому 2-секундный флаш analytics-writer НЕ искажает измерения латентности.

### 2.5 Языки

Rust: pipeline-engine, policy, routing, destination-resolution, partner-rest-receiver.
Java: billing, delivery, operator-smpp-session-manager, delivery-reconciliation, scheduler-background-lane.
Go: dlr-manager, dlr-correlation-writer, analytics-writer.

## 3. Методика измерений

Генератор нагрузки — открытый цикл (offered rate держится независимо от деградации системы), запускается **контейнером внутри docker-сети**, чтобы часы совпадали с VM. Профиль: `rate=300, duration=60s, warmup=30s, msisdns=100000`.

Латентность считается как `occurred_at стадии − время отправки loadgen`, обе величины по часам VM.

**Пул msisdn обязателен большой:** при 8000 анти-спам policy-service отклонял ~17% трафика и искажал счёт.

### Ловушки, которые реально сработали (важно для следующего агента)

1. **Часы VM отстают после сна Mac** — наблюдалось расхождение ~26 минут. Postgres показывал 04:49 при реальном 05:16. Из-за этого диагностический запрос показал «0 просроченных case'ов», и работающая система выглядела сломанной.
2. **Образ может быть старше коммита.** Правка в git ≠ правка в работающем контейнере. Трижды приводило к неверным выводам.
3. **Стенд деградирует по ходу серии.** Runtime Redis растёт, своп забивается, и 3-й прогон несравним с 1-м. Перед серией нужен сброс Redis, иногда полный epoch-reset (свежий том Kafka + Redis + ClickHouse + топики созданы явно ДО старта сервисов).
4. **Порядок старта важен.** После сброса Redis первым надо поднимать `operator-smpp-session-manager` — он регистрирует `operator_route:*`. Иначе все доставки уходят в `SUBMISSION_OUTCOME_UNKNOWN`.
5. **Ни один сервис не переживает рестарт Redis** — закэшированные соединения отдают `broken pipe` вечно. Нужен перезапуск всех потребителей.
6. **zsh-подвох:** `docker build -t mpp/$s:test` молча даёт тег `mpp/<имя>est:latest` из-за модификатора `:t`. Тег всегда в кавычках.
7. **Контекст сборки различается:** у Go-сервисов это каталог сервиса, у Java — корень репозитория. Смотреть шапку Dockerfile, не гадать.

## 4. Сводка измерений

### 4.1 Начало и конец

| | baseline | сейчас (полный контур) |
|---|---|---|
| DELIVERY p50 | 4086 мс | **266 мс** |
| DELIVERY p99 | 6070 мс | **1161 мс** |
| достигнутый TPS | 300 | 300.0, 0 ошибок |

Три последних прогона подряд (чистый старт, полный контур): p99 = 7556 / 4617 / **1161**. Тренд вниз — прогрев JIT и page cache; третий показателен.

Разбивка последнего прогона:

```
DESTINATION_RESOLUTION  p50  30  p95  288  p99  878   (первый прогон)
...
ROUTING                 p50 102  p95  549  p99  774   (третий прогон)
DELIVERY                p50 266  p95  980  p99 1161
```

Весь остаток — в DELIVERY-хопе: +164 мс на p50 и +387 мс на p99. Все стадии до него укладываются в бюджет.

### 4.2 Ключевое измерение: почему хопы дорогие

JFR-профиль delivery-service под 300 TPS. Доминирует `jdk.ThreadPark`: 59 513 событий, 2435 с на воркерах. `jdk.SocketRead` — всего 126 событий (Lettuce/Netty асинхронные, поток паркуется в ожидании колбэка).

```
1473.6с (60%)  gRPC submit -> operator-smpp   ср 53.8 мс
 359.0с (15%)  Kafka sendCompletedEvent       ср 30.0 мс
 138.2с ( 6%)  Redis recordOutcome            ср 28.3 мс
 115.9с ( 5%)  Redis claim                    ср 24.3 мс
  87.7с ( 4%)  Redis fetch                    ср 25.6 мс
  58.2с ( 2%)  Redis resolve                  ср 24.5 мс
```

**186 мс блокировки на сообщение в шести последовательных round-trip'ах.** При пуле 32 потока это ёмкость 172 сообщ/с — ниже целевых 300.

Главный вывод: **локальный Redis отвечает за ~25 мс вместо долей миллисекунды**. Ни сеть, ни сам Redis (1200 оп/с — для него ничто) этого не объясняют. Это задержка **пробуждения потока** при контеншене за CPU. Тот же эффект маскировался под «паузы GC» у Kafka: эвакуация 45 МБ занимала 597 мс, что физически невозможно для работы GC.

Следствие для оптимизации: платить надо за **число** блокирующих хопов, а не за их содержание. Ускорять отдельный хоп бессмысленно.

## 5. Найденные и исправленные дефекты

### 5.1 Память как корневая причина

Kafka дважды получала OOM-kill (`Exited 137`) под нагрузкой; своп был забит (1009 из 1023 МБ) при 50% простоя CPU. Исправлено: урезаны пулы/кэши ClickHouse (803 → 247 потока, RSS 872 → 408 МБ), heap Kafka 2G → 1G, лимиты четырёх Java-сервисов. Свободная память 289 МБ → 1736 МБ.

### 5.2 Poison-pill: вечная остановка коммита

В `pipeline-engine` и `policy-service` отсутствие состояния/контекста давало `return false` (офсет не коммитить, ждать переобработки). Но эти ошибки **неисправимы** — повтор не поможет никогда. `OffsetTracker` двигает коммит сплошным watermark'ом, поэтому ОДНА такая запись пиннила офсет навсегда.

Измерено: `stage.completed` застрял на офсете 864133 при LOG-END 995208 (лаг 131075 не двигался часами), `policy-service` — 406353 при 457357. После исправления накопленный лаг 1 140 208 записей ушёл в 0 за 45 секунд.

Для policy простого skip недостаточно — пайплайн ждёт именно POLICY, поэтому сообщение завершается терминальным REJECTED с reason_code.

### 5.3 Путь DLR был разорван в трёх местах

Это оказалось корнем остаточной проблемы с памятью и латентностью.

1. **`delivery-reconciliation-service` не разворачивался НИКОГДА** — его не было в docker-compose.yml вообще. При этом граф на `DELIVERY:SUCCEEDED` ведёт именно в него. Без консьюмера ни одно сообщение не доходило до терминала: 373 821 запись в топике при НУЛЕ consumer group'ов.
2. **`dlr-correlation-writer` 18 суток стоял** с `SQLSTATE 23514: no partition found`. `EnsurePartition` создавал секции только на текущий/следующий час, а при отставании/replay `submitted_at` попадал в прошлые часы.
3. **`scheduler-background-lane` лежал мёртвым 3 суток** (OOM-kill, RocksDB вне heap не подчиняется `MaxRAMPercentage`). Именно он возвращает DLR-задачи на повтор; накопилось 190 139 необработанных.

Результат: `delivery.status` был пуст, реконсиляция не разрешалась, `finalize_pipeline` не вызывался, Redis держал 4 ключа на сообщение.

### 5.4 Гонка корреляции DLR

**Измерено:** соседние записи `operator.submit.accepted` и `operator.dlr` по одному `smsc_message_id` имеют **одинаковый CreateTime** — квитанция доступна в ту же миллисекунду, что и подтверждение отправки. А корреляция писалась флашем раз в 2 секунды. `Lookup` промахивался практически всегда.

Исправлено быстрым путём в Redis: `delivery-service` пишет `dlrcorr:*` тем же round-trip'ом, что уже делал (`recordOutcome`), без новых хопов. `dlr-manager` читает Redis, при промахе — PostgreSQL. Путь retry оставлен как сетка безопасности.

Защита от reuse `smsc_message_id` сохранена: быстрый путь отдаёт запись только если `submitted_at <= received_at`.

**Результат: корреляция 8% → 99.5%.**

### 5.5 Отставание sweep'а реконсиляции

Sweep выдавал ~45 сообщ/с против 300 входящих. Три причины: одно JDBC-соединение на 4 потока (у pgJDBC `Connection` — канал под локом, sweep стоял в очереди за ~2700 запросов/с консьюмеров), два блокирующих round-trip'а на каждый case, интервал 30 с.

Исправлено: соединение на поток, публикация пачкой с одним ожиданием, интервал 2 с. Гарантия «publish до closeCase» сохранена.

**Результат: 45/с → 100/с, рост Redis 4.0 → 2.0 ключа на сообщение.**

### 5.6 Прочее

- Java-сервисы умирали насмерть при отказе брокера (`Exception in thread "main"`), а контейнер показывал `Up` — сервисы-зомби. Rust-сервисы то же переживали.
- Kafka писала в `/tmp/kafka-logs` внутри writable layer вместо смонтированного тома; topic-level retention отсутствовал (действовал дефолт 168ч вместо 6ч).
- Самокалибрующийся пул потоков фиксировался, **не получив ни одного сэмпла** (в логе нетронутый `Double.MAX_VALUE`), потому что окно калибровки проходило на простое. Результат зависел от того, попал ли трафик в стартовое окно: три прогона одной сборки дали 32, 192 и 72 потока — каждый прогон физически шёл на своей конфигурации.
- `max.poll.records` был 1000: цикл `poll -> дождаться ВСЕЙ пачки -> commitSync` давал head-of-line blocking, латентность равнялась позиции записи в дренаже. 1000 → 256 дало DELIVERY p50 1566 → 164 мс.
- `DELIVERY_CONCURRENCY`/`BILLING_CONCURRENCY` были мёртвой настройкой — нигде не читались, но в compose описаны как рабочие.

## 6. ОТРИЦАТЕЛЬНЫЕ РЕЗУЛЬТАТЫ — не повторять

Все проверены замером, все дали регрессию.

| попытка | результат |
|---|---|
| Пол пула 32 → 128 (калибратор дорос до 192) | p50 134 → 429 мс |
| Пул delivery 32 → 64 | p99 554/571 → 809/732 мс |
| `max.poll.records` 256 → 64 | p99 617-1192 → 2860-5162 мс |
| Непрерывный poll с bounded in-flight вместо батча | p99 758-838 (ровнее, но медианно хуже) либо 1582-6623 |
| Kafka heap 1G + `MaxGCPauseMillis=20` | e2e p50 ~1.5с → 78с |

**Четыре независимых подтверждения одного вывода:** увеличение конкурентности на этой машине очередь не сокращает, а переносит. Причина — контеншен за CPU: каждый лишний поток удорожает park+wakeup для всех.

Отдельно про GC: уменьшение heap Kafka с 2G до 1G **само по себе полезно** (young GC p50 72.8 → 12.9, p99 337.8 → 90.7 мс). Вредил именно `MaxGCPauseMillis=20`, заставлявший G1 собирать постоянно. Переменные надо разделять — я один раз откатил обе разом и списал вину не на ту.

## 7. Что осталось открытым

1. **`dlvsubmit:*` освобождается только по 24-часовому TTL.** Главный оставшийся потребитель Redis. Закрывается той же схемой, что уже сделана для `msgctx` — освобождение по терминальной стадии.
2. **Четыре блокирующих хопа в DELIVERY** из шести исходных. Убраны: параллельные `fetch`+`resolve` и неблокирующая публикация `stage.completed` (ожидание перенесено в цикл дренажа перед коммитом офсета). Осталось: gRPC submit, `claim`, `recordOutcome`, плюс сам Kafka-ack.
3. **Окно реконсиляции** выставлено в 2 минуты на стенде (было 30). Оно задаёт пол удержания памяти: при 300 сообщ/с окно 30 минут само по себе держит ~540 000 сообщений «в полёте». В проде подбирать под реальную задержку DLR оператора.
4. **Разброс между прогонами** остаётся заметным (p99 7556 / 4617 / 1161 на одинаковой конфигурации). Часть — прогрев, часть — деградация стенда.
5. Латентный дефект: `time.Duration(retainHours) * time.Hour` в dlr-correlation-writer переполнится при абсурдном значении конфига и молча даст отрицательную длительность.

## 8. Главный вопрос для оценки

**Достижима ли цель p99 < 350 мс на этом железе?**

Мой вывод — вероятно нет, и не из-за кода. Аргументы:

- Тот же код на 12 CPU / 15 ГБ давал p99 = 129 мс при 300 TPS.
- Измеренная стоимость park+wakeup ~25 мс обусловлена контеншеном за CPU, а архитектура принципиально требует нескольких блокирующих хопов на сообщение.
- Все четыре попытки купить производительность конкурентностью дали регрессию — запаса по CPU нет.
- Полный контур с обработкой квитанций фактически удваивает поток событий через платформу.

Но вывод не окончательный: осталось убрать 4 хопа из DELIVERY и освободить `dlvsubmit`. Если после этого p99 не опустится ниже ~500 мс, ответом будет ёмкость железа, и это измеренный ответ, а не отговорка.

**Отдельно стоит перепроверить мою интерпретацию** про 25 мс на пробуждение потока — это ключевой вывод всей работы, и он построен на JFR-профиле одного сервиса.
