# MPP — состояние платформы, изменения и измерения

**Для чего документ:** передать другому агенту полную картину без переоткрывания диагностики. Все числа — прямые измерения на живой системе. Где число не проверено или отозвано, это сказано явно.

**Цель работы:** 300 TPS на локальном стенде, e2e p99 < 350 мс.

**Краткий статус:** цель по латентности **не достигнута** (воспроизводимый p99 ≈ 2700 мс). Зато устранены три класса дефектов корректности, из которых один был порчей данных, а также вскрыта и исправлена ошибка в самом определении измеряемой величины — предыдущие «e2e»-числа мерили не то.

## 1. Железо и стенд

Docker Desktop VM на Mac: **8 CPU, 7.75 ГБ RAM, 1 ГБ swap**, делится с остальными задачами машины.

Ориентир: тот же код на AMD Ryzen 5 7600X (12 CPU / 15.16 ГБ) давал при 300 TPS **p50=105 / p95=119 / p99=129 мс**. Код способен на целевые числа.

**Стенд структурно переподписан по памяти:** сумма объявленных `mem_limit` — **7650 МБ при 7936 МБ физической памяти**, то есть 96% роздано контейнерам, а Kafka критически зависит от страничного кеша, которого не остаётся. Это, вероятно, объясняет прежние OOM-kill'ы Kafka, которые лечились точечным урезанием лимитов без взгляда на сумму. Систематически **не исправлено** — см. §7.

В горячем контуре 16 сервисов (добавлены `message-state-resolver` и `lifecycle-writer`, см. §5.5).

## 2. Архитектура пути сообщения

### 2.1 Основной конвейер

```
POST /v1/messages
  -> partner-rest-receiver (Rust)          пишет msgctx:{message_id}
  -> incoming.messages (Kafka)
  -> pipeline-engine (Rust)                создаёт exec:{message_id}, CAS-переходы
       +-> stage.destination-resolution -> destination-resolution-service (Rust)
       +-> stage.policy                 -> policy-service (Rust)
       +-> stage.billing                -> billing-service (Java)
       +-> stage.routing                -> routing-service (Rust)
       +-> stage.delivery               -> delivery-service (Java)
       +-> stage.delivery-reconciliation -> delivery-reconciliation-service (Java)

       каждая стадия публикует StageCompletedEvent в stage.completed,
       pipeline-engine читает его и решает следующий шаг по графу
```

Граф — `config_schemas/examples/pipeline.valid.json`.

**ИЗМЕНЕНО.** Узел `n5_delivery` был инвертирован относительно собственного контракта:

```json
// было — в reconciliation уходили ВСЕ успешные отправки,
//        а ветки SUBMISSION_OUTCOME_UNKNOWN не было вовсе
"next": { "SUCCEEDED": "n6_reconciliation", "FAILED": null,
          "TIMED_OUT": "n6_reconciliation", "RETRY_EXHAUSTED": "n6_reconciliation" }

// стало — как в platform-contracts/common/stage_contract.proto
"next": { "SUCCEEDED": null, "SUBMISSION_OUTCOME_UNKNOWN": "n6_reconciliation",
          "FAILED": null, "TIMED_OUT": "n6_reconciliation", "RETRY_EXHAUSTED": "n6_reconciliation" }
```

`DeliveryReconciliationExtension.triggering_outcome` в контракте прямо говорит: «сегодня всегда SUBMISSION_OUTCOME_UNKNOWN». `DeliveryService.java:42` этот исход эмитит. Но ключа в графе не было, и `resolve_next_stage` падал в `_ => Decision::Terminal` — **неизвестный исход отправки молча терминировался**, а reconciliation получал 100% успешных.

Проверено, что движок ключ матчит: `outcome_key()` в `execution_state.rs:170` строит имя без префикса `OUTCOME_`, тем же механизмом, что уже работающие `TIMED_OUT`/`RETRY_EXHAUSTED`.

Финальный статус партнёру при этом **не теряется**: `DELIVERED` приходит из реального DLR через `delivery.status`, переход `SUBMITTED → DELIVERED` явно разрешён в `TransitionValidator.java:51`. Reconciliation вернулся к своей роли — разбору неизвестного исхода, а не обязательному хопу каждого сообщения.

### 2.2 Путь доставки

```
delivery-service --gRPC--> operator-smpp-session-manager (Java)
   -> пейсер HTB -> SMPP submit_sm -> SMSC
   -> operator.submit.accepted
```

SMSC реальный, в одной сети со стендом: **172.30.19.206:8275**, ping min 3.6 / avg 12.3 / max 64.6 мс. Отсюда ключевой факт для всех гонок ниже: **DLR приходит через 20–70 мс после submit**, часто раньше, чем система успевает записать состояние.

### 2.3 Путь квитанций (DLR)

```
SMSC -> deliver_sm -> operator-smpp -> operator.dlr
   -> dlr-manager (Go)  корреляция smsc_message_id -> message_id
        попадание -> delivery.status -> message-state-resolver -> lifecycle
        промах    -> scheduler.background.commands -> повтор

Корреляция пишется параллельно:
   operator.submit.accepted -> dlr-correlation-writer (Go) -> PostgreSQL
   (+ быстрый путь Redis dlrcorr:*, TTL 15 мин)
```

### 2.4 Хранилища состояния

**Runtime Redis** — было 4 ключа на сообщение, стало 2 живущих дольше терминала:

| префикс | владелец | освобождение |
|---|---|---|
| `exec:{message_id}` | pipeline-engine | `finalize_pipeline` при терминале |
| `msgctx:{message_id}` | partner-rest-receiver | то же |
| `dlvsubmit:{stage_execution_id}` | delivery-service | **ИЗМЕНЕНО:** `UNLINK` после подтверждённого коммита офсета (было — только TTL 24ч) |
| `dlrcorr:{op}:{smsc_id}:{seg}` | delivery-service | TTL 15 минут |

TTL 24ч сохранён как страховка ровно для того, чем и должен быть: сообщений, не дошедших до терминала.

**PostgreSQL** — `dlr.dlr_correlation` (RANGE-партиции по часам), `reconciliation.reconciliation_cases`, **новое:** `reconciliation.early_evidence` (V032), `messaging.message_lifecycle_history`.

**ClickHouse** — `analytics.stage_events`. Важно для методики: `occurred_at` берётся из payload-таймстампа продюсера, а не времени вставки, поэтому буферизация analytics-writer латентность **не** искажает.

### 2.5 Языки

Rust: pipeline-engine, policy, routing, destination-resolution, partner-rest-receiver.
Java: billing, delivery, operator-smpp-session-manager, delivery-reconciliation, message-state-resolver, scheduler-background-lane.
Go: dlr-manager, dlr-correlation-writer, analytics-writer, lifecycle-writer.

## 3. Методика измерений

### 3.1 Как считается латентность

**ИЗМЕНЕНО, и это существенно.** Инструментирование сервисов не понадобилось: `analytics.stage_events` хранит `occurred_at DateTime64(3)` на каждую стадию, поэтому пофазная разбивка выводится одним SQL-запросом по разностям отметок одного `message_id`.

Фазы: `A incoming→DR`, `B DR→POLICY`, `C POLICY→BILLING`, `D BILLING→ROUTING`, `E ROUTING→DELIVERY`, `F DELIVERY→RECON`, плюс `Z1 TOTAL in→DELIVERY` и `Z2 TOTAL in→TERMINAL`.

**`Z2` — и есть настоящий e2e.** Прежние отчёты называли e2e величину `Z1`. Разница была 143 секунды против 13.

Оговорка по ClickHouse: он зажат `max_server_memory_usage` 768 МБ, а CTE в ClickHouse инлайнятся, поэтому запрос с восемью `UNION ALL` переисполняет агрегат восемь раз и падает по памяти. Промежуточный результат надо материализовать в `Memory`-таблицу (см. `mk_permsg.sql` в рабочих скриптах).

### 3.2 Генератор нагрузки

Открытый цикл, запуск контейнером внутри docker-сети (чтобы часы совпадали с VM). Профиль: `rate=300, duration=120s, warmup=30s, msisdns=100000`. Тело запроса и заголовки обязательны:

```
{"msisdn":"9989XXXXXXXX","sender_id":"Click","body":"..."}
X-Partner-Id: click_uz   X-Application-Id: click_uz_main
X-Api-Key: local-dev-test-key   X-Forwarded-For: 185.65.212.10
```

Пул msisdn обязан быть большим: при 8000 анти-спам policy-service отклонял ~17% трафика.

### 3.3 Критерий валидности прогона

Прогон засчитывается только если **`exec:*` вернулся к нулю** после схождения. Иначе часть сообщений не дошла до терминала, и квантили считаются по выжившим — то есть занижены. Половина прогонов этой серии этот критерий не прошла, и я едва не записал их результаты как валидные.

## 5. Исправленные дефекты

### 5.1 Порча финальных статусов в reconciliation (главное)

Две независимые причины, обе в `delivery-reconciliation-service/Main.java`.

**Причина 1: свидетельство, пришедшее раньше case'а, молча выбрасывалось.**

```java
store.loadByMessageId(messageId).ifPresent(initial -> { ... });  // нет case'а — нет получателя
```

Не экзотика: DLR приходит через 20–70 мс, а case создаётся длинным путём delivery-service → stage.completed → pipeline-engine → stage.delivery-reconciliation, и регулярно проигрывает гонку.

**Исправлено** таблицей `reconciliation.early_evidence` (V032) — durable «посадочная площадка», по колонке на вид свидетельства, чтобы накопление было атомарным на уровне строки (без read-modify-write, а значит без lost-update между репликами, где JVM-локи не помогают).

Ленивое создание case'а по DLR рассмотрено и **отвергнуто**: `stage_execution_id` в case'е `NOT NULL` и уезжает в `StageCompletedEvent`, по нему pipeline-engine сопоставляет ответ со своим ожиданием. Выдуманный id дал бы событие, которое некому сопоставить, а sweep по дедлайну успел бы его опубликовать.

**Причина 2: sweep выбирал только просроченные case'ы**, поэтому даже дошедшее свидетельство не закрывало case немедленно.

**Исправлено:** case закрывается сразу по терминальному свидетельству. Второго пути закрытия не появилось — решение принимает тот же `OutcomeResolver`, публикует тот же `sweepBatch`, просто на списке из одного case'а. Дедлайн остался ровно для случая «свидетельства не пришло».

Дополнительно в `sweepBatch` добавлен **сторож**: `CONFIRMED_NOT_SUBMITTED` при наличии любого положительного следа отправки не публикуется. Лучше громко не закрыть case, чем тихо соврать.

Тесты: `ReconciliationRaceTest` — свидетельство до case'а, немедленное закрытие по терминальному DLR, сохранение закрытия по дедлайну при отсутствии свидетельства, отсутствие досрочного закрытия по одному `submit_accepted`.

### 5.2 Инверсия графа пайплайна

См. §2.1. Одна строка JSON, но она и создавала 100% нагрузку на reconciliation, и двухминутное удержание состояния, и питала причину 5.1.

### 5.3 Batch-barrier в delivery-service

Было: `poll(N)` → раздать в пул → **дождаться каждого future** → `commitSync()` → следующий `poll`. Head-of-line blocking: латентность записи равна её позиции в дренаже, а не времени обработки.

Стало: непрерывный poll, `pause()`/`resume()` по счётчику in-flight (не отказ от `poll()` — это уронило бы группу по `max.poll.interval.ms`), коммит по contiguous watermark через `commitAsync` по таймеру, финальный синхронный коммит на shutdown.

Гарантия **не ослаблена**: офсет считается завершённым только когда получены ОБА подтверждения — Kafka-ack публикации `stage.completed` и запись исхода в Redis. Ожидание неблокирующее (`CompletableFuture.whenComplete`), коммитится только непрерывный префикс.

Результат — §4.3: фаза `E` с 233/9830 до 136/738.

### 5.4 Освобождение `dlvsubmit:*`

Ключ снимается `UNLINK`'ом в колбэке **подтверждённого** `commitAsync`, для записей строго до закоммиченной позиции.

**Разобранный и отвергнутый опасный вариант** (важно, чтобы следующий не «оптимизировал» обратно): удалять ключ в `finalize.lua` рядом с `msgctx`. `finalize` срабатывает через миллисекунды после публикации `stage.completed`, то есть практически всегда РАНЬШЕ коммита офсета delivery-service. Любая ошибка до коммита → передоставка → ключа нет → `claim` возвращает `Won` → **повторный SMS абоненту**. Плюс покрытие было бы частичным: `stage_execution_id` минтится заново на каждый диспатч, и ключи retry-попыток остались бы на TTL.

Три следствия того же рассуждения: при неудачном коммите не освобождается ничего; на poison-pill ключ остаётся (submit мог состояться); при ребалансе ключи отобранных партиций забываются, а не снимаются.

Тест: `ClaimReleaserTest` — 6 случаев, включая ребаланс и записи без claim.

### 5.5 Слой жизненного цикла не работал 4 суток

`message-state-resolver` и `lifecycle-writer` были остановлены; `lifecycle_status` пуст у **всех 1 133 808** событий за 6 часов. То есть партнёр-видимые статусы `SUBMITTED/DELIVERED/UNDELIVERABLE` не производились вообще.

Подняты. Оба зажаты по памяти (768 м и 256 м; у `lifecycle-writer` лимита не было **вовсе**) — на машине с переподпиской 96% безлимитный контейнер это отложенный OOM соседа.

### 5.6 Атомарность `claim`

`HSETNX` + `EXPIRE` были двумя round-trip'ами, и при падении между ними ключ оставался без TTL навсегда. Сведено в один Lua (`submit_claim.lua`), `EVALSHA` с фоллбэком на `EVAL` по `NOSCRIPT` (после рестарта Redis скрипт-кэш пуст — тест делает `SCRIPT FLUSH` и проверяет самовосстановление).

Побочно: в проигравшей ветке тоже было два round-trip'а (`HSETNX`+`HGETALL`), и закрыта TOCTOU-щель — теперь `HGETALL` читает ровно то состояние, которое видел `HSETNX`.

### 5.7 Калибратор пула в operator-smpp-session-manager

При истечении окна калибровки **без единого сэмпла** калибратор фиксировался с `bestP95 == Double.MAX_VALUE`. Тот же фикс уже стоял в delivery-service и billing-service, третья копия была пропущена; в живом логе значение наблюдалось. Теперь окно перезапускается.

Пятиаргументный конструктор с явным `floor` намеренно **не** добавлен: у него не было бы ни одного вызывающего, а `pool` и `semaphore` там создаются вызывающим кодом согласованно — параметр без правки `Main.java` молча рассинхронизировал бы их.

### 5.8 Оверфлоу окна партиций в dlr-correlation-writer

`time.Duration(retainHours) * time.Hour` переполняет int64 примерно на 2 562 047 часах и даёт **отрицательное** окно, при котором `PlanPartitions` отвергает всё и запись встаёт целиком. Это ровно тот отказ, что уже стоил сервису 18 суток простоя. Значение зажимается сверху с записью в лог (не отбрасывается молча — иначе поставивший число не узнает, что оно не применилось).

### 5.9 Ранее исправленное (контекст предыдущих итераций)

- **Poison-pill'ы** в `pipeline-engine` и `policy-service`: неисправимые условия трактовались как retryable, и одна запись пиннила contiguous-watermark навсегда. Накопленный лаг 1 140 208 записей ушёл в 0 за 45 секунд после исправления.
- **Разрыв пути DLR в трёх местах**: `delivery-reconciliation-service` вообще отсутствовал в compose; `dlr-correlation-writer` 18 суток стоял на `SQLSTATE 23514`; `scheduler-background-lane` лежал 3 суток после OOM (RocksDB вне heap не подчиняется `MaxRAMPercentage`).
- **Гонка корреляции DLR** 8% → 99.5% через быстрый путь `dlrcorr:*` в Redis тем же round-trip'ом, что уже делался.
- **Отставание sweep'а** 45/с → 100/с: соединение на поток (у pgJDBC `Connection` — канал под локом), публикация пачкой, интервал 30с → 2с.
- **`max.poll.records`** 1000 → 256: DELIVERY p50 1566 → 164 мс.
- **Память**: урезаны пулы ClickHouse, heap Kafka 2G → 1G, лимиты Java-сервисов.

## 6. Ловушки, которые реально сработали

Каждая молча превращала измерение в фикцию. Это самая полезная часть документа.

1. **`docker compose exec -T` съедает stdin.** Конструкция `... | while read t; do docker compose exec -T ... ; done` создаёт **один** элемент и молча обрывается. Так из 18 топиков создался один, pipeline-engine ругался `UnknownTopicOrPartition`, и первые 1776 сообщений прогона легли на 100%. Лечится `< /dev/null` на exec.

2. **`--renew-anon-volumes` применяется ко всему списку.** Я хотел свежий том Kafka, передал флаг всем сервисам и снёс схему ClickHouse. Из-за `set -e` скрипт оборвался и сервисы не стартовали.

3. **zsh применяет модификатор `:t` даже внутри двойных кавычек.** `"mpp/$s:test"` → `mpp/<имя>est`. Сборка отрабатывает успешно, тегирует чужое имя, compose поднимает старый образ, замер молча показывает неизменённую систему. Только `"mpp/${s}:test"`.

4. **Тесты reconciliation по умолчанию бьют в `localhost:5432`, а контейнер стенда слушает 5433.** Девять «падений» были против чужой базы. Нужен явный `DELIVERY_RECONCILIATION_TEST_JDBC_URL`.

5. **Автосоздание топиков не спасает.** `KAFKA_AUTO_CREATE_TOPICS_ENABLE=true` срабатывает по успешному обращению, а самый первый `produce` к несуществующему топику падает и сообщение теряется. На свежем томе топики надо предсоздавать явно из `infra/kafka/rendered-small/kafka-topics.yaml`.

6. **Порядок старта.** После сброса Redis первым поднимать `operator-smpp-session-manager` — он засевает `operator_route:*`. Иначе все доставки уходят в `SUBMISSION_OUTCOME_UNKNOWN`.

7. **Ни один сервис не переживает рестарт Redis** — закэшированные соединения отдают `broken pipe` вечно.

8. **Контекст сборки различается:** Go-сервисы собираются из каталога сервиса, Java и Rust — из корня репозитория. Смотреть шапку Dockerfile. Go-сервисам всё равно нужен `--secret id=extra_ca_cert`.

9. **Часы VM отстают после сна Mac** — наблюдалось ~26 минут, из-за чего работающая система выглядела сломанной.

10. **Образ может быть старше коммита.** Правка в git ≠ правка в контейнере.

11. **`docker compose logs` пуст ≠ ошибок не было.** `docker compose down` уничтожает логи; после сброса видно только текущий инстанс.

12. **Пайп через `tail` буферизует** — длинная фоновая серия не даёт промежуточного вывода вообще.

## 7. Открытые вопросы

### 7.1 Причина разброса между прогонами — НЕ УСТАНОВЛЕНА

Главный открытый вопрос. Валидные прогоны одной сборки дают p99 от 506 до 27 655 мс. Три гипотезы проверены и опровергнуты (§4.4). Что стоит попробовать следующему:

- Разделить измерение по времени внутри прогона: деградирует ли латентность монотонно в течение 120 секунд, или скачет.
- Посмотреть на `esme-simulator-*` — SMSC-симулятор живёт отдельным compose-проектом и в учёт ресурсов не входил ни разу.
- Проверить, не залипает ли `AdaptiveThreadPoolCalibrator` на плохом значении: наблюдались фиксации на `p95=29.0ms`, `79.0ms` и `430.0ms` в разных прогонах. Размер пула при этом всегда 32 (упирается в потолок), но сам факт разброса в 15 раз по наблюдаемой p95 требует объяснения.

### 7.2 Переподписка памяти — НЕ ИСПРАВЛЕНА

7650 МБ лимитов при 7936 МБ физической. Kafka зависит от страничного кеша, которого не остаётся. Прямой эксперимент — снизить сумму лимитов до ~5500 МБ и повторить замер — **не проводился**. Это самый дешёвый непроверенный рычаг.

### 7.3 Гонка `DELIVERED` без `SUBMITTED`

5 сообщений из 44 983 получили `DELIVERED`, не получив `SUBMITTED`. Тот же класс, что 5.1, но в `message-state-resolver`: `TransitionValidator` разрешает только `SUBMITTED → DELIVERED`, и обогнавший DLR делает последующий `SUBMITTED` регрессией. Финальный статус верный, теряется промежуточный — приоритет ниже.

### 7.4 Прочее

- Окно реконсиляции на стенде 2 минуты (было 30). Задаёт пол удержания памяти; в проде подбирать под реальную задержку DLR оператора.
- `delivered` в замере обычно меньше `submitted` на момент запроса — DLR продолжают приходить. Для корректного подсчёта доставки нужна пауза после схождения `exec`.

## 8. ОТРИЦАТЕЛЬНЫЕ РЕЗУЛЬТАТЫ — не повторять

| попытка | результат |
|---|---|
| Пол пула 32 → 128 (калибратор дорос до 192) | p50 134 → 429 мс |
| Пул delivery 32 → 64 | p99 554/571 → 809/732 мс |
| `max.poll.records` 256 → 64 | p99 617-1192 → 2860-5162 мс |
| Kafka heap 1G + `MaxGCPauseMillis=20` | e2e p50 ~1.5с → 78с |

Про `max.poll.records` 64 — **важное уточнение**. Этот результат опровергал не идею снятия барьера, а конкретный способ: в тех прогонах оставался `commitSync` на КАЖДЫЙ батч, и при вчетверо более частых батчах доминировать начинал синхронный round-trip коммита. После правильного снятия барьера (§5.3) размер пачки перестал определять латентность, и `KAFKA_MAX_POLL_RECORDS` оставлен 256.

Про GC: уменьшение heap Kafka 2G → 1G **само по себе полезно** (young GC p50 72.8 → 12.9, p99 337.8 → 90.7 мс). Вредил именно `MaxGCPauseMillis=20`. Я один раз откатил обе переменные разом и списал вину не на ту.

## 9. Отозванный вывод предыдущей итерации

Предыдущая версия документа утверждала: JFR показывает ~25 мс на park+wakeup на каждый блокирующий хоп, отсюда «186 мс блокировки на сообщение» и «ёмкость 32 / 0.186 = 172 сообщ/с», отсюда вывод «железо, вероятно, не тянет».

**Этот вывод снят.** Проверка агрегата по `d3.jfr`:

```
МИНИМАЛЬНАЯ зафиксированная park-длительность: 10.0 мс
медиана: 26.8 мс;  всего событий: 59513
```

Жёсткий пол ровно на 10.0 мс доказывает, что настройка `profile` в JFR записывает только парковки дольше порога. Значит «25 мс» — среднее по выборке, **уже отфильтрованной по медленным**, и выводить из него стоимость среднего хопа нельзя. Производная оценка ёмкости 172/с не обоснована.

Качественный вывод «платить надо за число блокирующих хопов, а не за их содержание» сам по себе устоял — убранные хопы дали измеримый эффект. Но количественная база под ним была неверной, и тезис «железо не тянет» на ней держаться не может.

## 10. Итог

**Достигнуто и подтверждено на всех девяти прогонах, включая деградировавшие:**

```
доля сообщений в reconciliation:              0     (было 100%)
DELIVERY=SUCCEEDED + CONFIRMED_NOT_SUBMITTED: 0     (было 16 187)
msgctx / dlvsubmit после терминала:           0     (жили до 24ч TTL)
```

Эти результаты не зависят ни от нагрузки, ни от памяти, ни от прогрева.

**Не достигнуто:** p99 < 350 мс. Воспроизводимое значение — **2696 мс** при p50 480 мс, 300 TPS, ноль потерь, полное схождение.

**Главное для оценки:** узкое место больше не локализовано в одном сервисе. Прежде `ROUTING→DELIVERY` стоила больше всех остальных стадий вместе; теперь пять фаз дают 63/60/103/45/136 мс по медиане — почти поровну. Это подпись общесистемного ограничения, а не плохого кода в конкретном месте. Дальнейшая оптимизация отдельных сервисов, вероятно, бесполезна; смотреть надо на ресурс — и §7.2 (переподписка памяти) остаётся самым дешёвым непроверенным рычагом.

**Тесты:** delivery-service 83, delivery-reconciliation-service 41, pipeline-engine 54, operator-smpp-session-manager 70, configuration-service и dlr-correlation-writer — зелёные.

**Коммиты итерации:** `b23892e` (корректность reconciliation + снятие batch-barrier + освобождение ключей + Lua claim + калибратор + оверфлоу), `1d63496` (лимиты памяти двух поднятых сервисов).
