## `development_plan.md` 4.3/4.4 закрыты

**4.3 — приоритизация при реальной неоднозначности шаблонов.** До этой правки при нескольких шаблонах, технически проходящих фазу 2 для одного текста, побеждал первый по порядку РЕГИСТРАЦИИ — случайность, не осмысленный выбор (`policy_matching/README.md` изначально флагует это текстом: "точная приоритизация при конфликте остаётся отдельным вопросом"). Найдено при реализации: старый тест `multiple_candidates_resolved_deterministically` даже не проверял, КАКОЙ шаблон побеждает для генуинно неоднозначного случая (`"code: 1234"` реально проходит фазу 2 и для `code: %w`, и для `code: %d{4,4}`) — просто утверждал "что-то нашлось". Реализовано настоящее правило специфичности: `%d{n,m}` строже `%w` (ограничивает и алфавит, и длину, не только "непустой непробельный") — вес 2 против 1 на плейсхолдер; суммарная длина литеральных фрагментов — вторичный критерий (разрывает ничью между шаблонами с одинаковым профилем плейсхолдеров, не переопределяет его); порядок регистрации — финальный tie-break, если оба критерия совпали. Доказано `specificity_prefers_digit_over_word_for_same_literal_length` (специально в ОБРАТНОМ порядке регистрации, чтобы отличить "правило работает" от "совпало с порядком случайно") и `specificity_breaks_ties_by_literal_length_when_placeholder_profile_is_identical`.

**4.4 — расширение таблицы гомоглифов.** Было 11 задокументированных Cyrillic/Latin пар. Добавлено: 2 недостающие Cyrillic/Latin пары (к→k, м→m) и полноценная Greek/Latin категория (α/ο/ι/κ/ν/ρ/υ/τ/χ) — отдельный от кириллицы, реальный класс визуальной подмены (греческая omicron для латинской "o" — самый частый вектор в реальных IDN-homograph атаках), не выдуманный заново: все добавленные пары — задокументированные записи из Unicode `confusables.txt`, того же канонического справочника, на который опирается вся анти-фишинг индустрия. Доказано `missing_cyrillic_pairs_ka_and_em_are_detected`, `greek_omicron_evasion_detected`, `greek_alpha_and_iota_evasion_detected`, и `mixed_greek_and_cyrillic_in_same_word_still_detected` — последний доказывает, что подмена работает даже при смешении алфавитов ВНУТРИ одного слова (реальный, не гипотетический вектор обхода), не только при использовании одного алфавита целиком. Всё ещё не исчерпывающий юникод-справочник — расширяется по мере необходимости, не разовое закрытие вопроса навсегда (см. комментарий в `banwords.rs`).

**Исправлено (найдено при реализации `dlr-manager`, полный разбор — его README, "Реальная находка (систематическая...)"):** `main.rs` раньше читал единственную `REDIS_RUNTIME_URL`, которую k8s никогда не установит — реальный секрет инжектится дискретными `REDIS_RUNTIME_HOST`/`PORT`/`PASSWORD` (`envFrom: secretRef`). `redis_url::build_redis_runtime_url()` теперь собирает connection string из них, `REDIS_RUNTIME_URL` оставлена как явный override для локальной разработки/тестов. 3 новых теста.

## Что добавлено сверх Python-версии (там, где Python не заходил до Kafka/Redis)

`policy_matching/policy_engine.py` тестировал только чистую функцию `evaluate_policy` — Kafka и Runtime Redis были явно вне скоупа того шага. Здесь (`kafka_io.rs`, `main.rs`) — то, чего не было:

* **`MessageContextStore`** — трейт `fetch(message_id) -> MessageContext`, реальная `RedisMessageContextStore` (компилируется против `redis` крейта, `HGETALL msgctx:{message_id}`). Нужен, потому что `PolicyExtension` в `stage.policy`-команде несёт только `resolved_operator_id` — `body`/`msisdn`/`sender_id` НЕ дублируются в stage-командах (`service_internal_methods.md` §0), Policy обязан прочитать их из Runtime Redis по `message_id`.
* Kafka-обвязка (`stage.policy` -> `stage.completed`, `PolicyResult{category}`) — тот же паттерн, что `destination-resolution-service/src/kafka_io.rs`: `handle_command` — чистая функция (тестируется без сети), `run_loop` — реальный `rdkafka`-цикл, не интеграционно проверенный.

## Тесты — что доказано

27 тестов, три группы:
* `template_matching.rs` (7) — та же матрица случаев, что в Python: реальный пример из чата матчится, счётчик цифр вне `{1,6}` не матчится, `%w` не допускает внутренний пробел, отсутствующий литеральный фрагмент не матчится, разделители между цифрами игнорируются, неоднозначность двух кандидатов разрешается детерминированно, ведущий/замыкающий плейсхолдер работает.
* `banwords.rs` (7) — включая гомоглиф-обход (кириллическая "о" вместо латинской в `qоtaq`) и letter-spacing обход (`т е р р о р и з м`, ловится только despaced-проходом), и **осознанный false-positive** despaced-прохода как задокументированный компромисс, не баг.
* `policy_engine.rs` (9) + `kafka_io.rs` (3) — полная оркестрация 8 проверок на реальном `config_schemas/examples/policy_ruleset.valid.json` (та же кросс-артефактная сверка, что в Python-версии), включая `banword_blocks_even_though_template_matches` (permissive `%w` не создаёт обход контентной модерации) и `spam_throttled_after_limit_and_counter_not_incremented_on_rejects`.

## Исправлено по итогам независимого кодревью (`CODE_REVIEW.md`)

* **High — `parse_pattern` паниковал на любом многобайтовом UTF-8 символе в литеральном фрагменте паттерна.** `template_matching.rs` шагал по индексу `i` побайтово (`i += 1` в ветке `else`), но каждую итерацию слайсил `pattern[i..]` для проверки `starts_with("%w"/"%d{")` — `str`-слайс по не-граничному байту паникует. На чисто ASCII паттернах из тестового фикстура это никогда не срабатывало, но это многоязычная SMS-платформа: кириллица и узбекская латиница с апострофом ʻ/ʼ (U+02BB/U+02BC, 2 байта) уже используются в тестовых данных этого сервиса **между** плейсхолдерами ("bo'yicha", "so'm") — тот же класс символа внутри самого литерала реально встречается в регистрируемых операторами шаблонах и крашил бы сервис при их загрузке. Исправлено: `i` теперь продвигается на всю длину символа (`char::len_utf8`) в ветке `else`, оставаясь на границе символа перед следующим слайсингом. Доказано тремя новыми тестами: `cyrillic_literal_fragment_does_not_panic`, `uzbek_latin_apostrophe_literal_fragment_does_not_panic`, `emoji_literal_fragment_does_not_panic` (4-байтовый символ — самый жёсткий случай для границ).
* **Medium, compliance-значимо — `check_time_of_day` сравнивал UTC напрямую с конфигом, задокументированным как Asia/Tashkent local time.** `kafka_io.rs` передавал в `evaluate_policy` чистый `Utc::now().naive_utc()`, а `policy_ruleset.valid.json` документирует окна вида "ADVERTISING разрешена 09:00-20:00 Asia/Tashkent" — сдвиг на 5 часов реально блокировал легитимный дневной трафик у границы UTC/Tashkent и пропускал ночной трафик, который должен был быть заблокирован. Исправлено: новая `now_tashkent()` конвертирует через `FixedOffset::east_opt(5*3600)` — Asia/Tashkent имеет постоянное смещение UTC+5 без перехода на летнее время с 1992 года, так что фиксированного смещения достаточно и корректно навсегда, полноценная tz-база (`chrono-tz`) не нужна. `handle_command` перестал сам вызывать `Utc::now()` и теперь принимает `now` параметром (как уже делает `evaluate_policy`) — стал чище тестируемым, реальный вызов времени вынесен в `run_loop`. Постоянное смещение не меняет разницу между двумя моментами времени, так что окно анти-спама (которое использует тот же `now`) этим изменением не затронуто. Доказано `now_tashkent_is_five_hours_ahead_of_utc`.

## Что НЕ реализовано на этом шаге (честно, не спрятано)

* **ОБНОВЛЕНО 2026-08-06:** `docker build` реально прогнан и провалидирован для этого сервиса (найдены и исправлены реальные баги по пути, где применимо — см. `development_plan.md` "Координация" п.5 и `infra/docker/README.md`). Формулировка ниже — из более раннего состояния сессии, оставлена для истории.
* **`docker build` не выполнялся** — недоступен Docker daemon в этом окружении (см. `services/destination-resolution-service/README.md` — та же причина).
* **Ни разу не запущено против реального Kafka-брокера или Runtime Redis** — `RedisMessageContextStore`/`run_loop` компилируются против настоящих клиентских крейтов, но live не проверены.
* **`RuntimeState` (consent-блэклисты, spam-счётчик) остаётся in-memory**, не перенесён на Runtime Redis — в реальном проде это разделяемое между репликами состояние (как `MessageContextStore`), перенос не сделан в этом срезе ради объёма. Один инстанс Policy Service, развёрнутый как задумано (`k8s/generate_manifests.py`: 3 реплики), с in-memory `RuntimeState` даст **неверный** spam-throttling (каждая реплика считает свою историю) — это реальное ограничение, не мелочь, зафиксировано как первоочередной технический долг перед Фазой 2.3/2.4.
* **Кодревью также отметило (LOW/MEDIUM, осознанно не исправлено здесь): `spam_history` растёт без ограничения** — ключ на каждый когда-либо виденный `(msisdn, category)` никогда не удаляется, даже когда его записи полностью устарели; и **двойной инкремент счётчика при повторной доставке** `StageExecuteCommand` (Kafka at-least-once) — коммит offset происходит только после успешной публикации, так что редоставленная команда повторно прогоняет `evaluate_policy` и инкрементирует spam-счётчик за одно и то же реальное сообщение. Оба это те же классы проблем, что и `processedChargeIds`/TOCTOU в billing-service (см. `services/billing-service/README.md`) — правильное решение то же: перенос `RuntimeState` на Runtime Redis с TTL/дедупликацией по `stage_execution_id`, не точечный патч в in-memory структуре — не сделано в этом срезе ради объёма, зафиксировано как технический долг вместе с пунктом выше.
* Таблица гомоглифов всё ещё не исчерпывающий юникод-справочник (армянский, кириллица нестандартных языков и т.д. не добавлены — нет обоснованной причины ожидать их в реальном трафике этой платформы) — `development_plan.md` 4.4 закрыт в объёме реально обоснованных категорий (Cyrillic+Greek), не "навсегда".
* `ArcSwap` (заявлен в `services_specifictaion.md` §2.5 для hot-reload ruleset/шаблонов из `config.changes`) — снапшот грузится один раз при старте, hot-reload не реализован (тот же паттерн, что у Destination Resolution).
