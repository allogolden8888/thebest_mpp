## `development_plan.md` 4.2 закрыт: `cas_transition_and_track_deadline` — реальный Redis CAS, снят блокер многорепличности

`ExecutionState` до этой правки жил в `Arc<Mutex<HashMap>>` — **единственное серьёзное ограничение всей этой сессии**, задокументированное как приоритетный блокер: при нескольких репликах (`k8s/generate_manifests.py` планирует 17 инстансов) состояние не разделялось между ними вообще, сообщение, обработанное одной репликой, было невидимо для другой. Закрыто настоящим Redis-бэкендом (`src/redis_cas.rs`, `lua/cas_transition.lua`, `lua/finalize.lua`) — `exec:{message_id}` в Runtime Redis теперь общее состояние, видимое любой реплике, CAS-guard (`expected_awaiting_stage_execution_id`) защищает от двух реплик, одновременно продвигающих один и тот же `message_id`.

**Ключевое архитектурное решение — что осталось Rust, что стало Lua.** Сама бизнес-логика (`resolve_next_stage`/`handle_stage_completed` в `execution_state.rs`) **не изменилась ни на строку** — это by design, не недоделка: порт всей логики графового обхода в Lua задублировал бы её на двух языках и резко увеличил бы риск рассинхрона, а сам метод в документе описан как "CAS Execution State + ZADD/ZREM" — атомарна именно ЗАПИСЬ результата, не вычисление решения. Поток теперь: `load()` (обычный `HGETALL`, не атомарно, только чтение) → чистая Rust-функция `advance`/`handle_stage_completed` вычисляет новое состояние → `cas_advance()` атомарно записывает его, только если `awaiting_stage_execution_id` в Redis всё ещё совпадает с тем, что было прочитано (иначе `CasOutcome::Conflict` — кто-то другой уже продвинул это состояние, событие безопасно игнорируется, не применяется поверх чужого прогресса).

**Идемпотентность на входе теперь тоже реальная, не in-memory карта.** Раньше `run_incoming_loop` делал отдельную (потенциально гоняющуюся) проверку `contains_key` перед `handle_incoming`. Теперь идемпотентность обеспечивает сам CAS-вызов: `cas_advance(None, ...)` буквально означает "ожидаем, что состояния для этого `message_id` ещё нет" — если это не так (redelivery активного пайплайна), Lua-скрипт вернёт `CONFLICT`, не создаст второе состояние. Доказано `concurrent_initial_cas_only_one_replica_wins` — два "реплики" (два конкурентных вызова с `expected=None`) гоняются за создание одного и того же начального состояния, ровно один побеждает.

**`DEADLINE_BUCKETS = 16`** — не выбрано произвольно: независимый код-ревью уже нашло, что `scheduler-critical-sweep` (Субагент 1) жёстко использует `DEADLINE_BUCKETS=16` без проверки, что это число совпадает с реальным числом бакетов Pipeline Engine — несовпадение тихо теряло бы часть дедлайнов. Здесь используется то же число, чтобы не воспроизвести ровно ту находку.

**Честно задокументированный, не новый пробел.** Если CAS в `run_completed_loop` проходит успешно, но последующая публикация `StageExecuteCommand` для новой стадии проваливается — откат небезопасен (в отличие от `run_incoming_loop`, где CAS создаёт состояние с нуля и откат тривиален и однозначен — реализован, `store.finalize(...)` вызывается при неудачной публикации первой команды). В `run_completed_loop` между CAS и публикацией другая реплика теоретически могла уже опереться на новое состояние, поэтому откат туда не добавлен; редоставленное исходное событие на повторной обработке не совпадёт с новым `awaiting_stage_execution_id` и будет проигнорировано как устаревшее. **Это тот же класс пробела, что уже был в in-memory версии** (там мутация HashMap происходила так же безусловно до публикации) — не новый регресс от переноса на Redis, просто не исправлен заодно (за пределами скоупа `development_plan.md` 4.2).

**Пост-кодревью находка (не из `CODE_REVIEW.md`, найдена при реализации `delivery-service`):** `DeliveryExtension` не нёс `resolved_operator_id` вообще — Delivery не может резолвить Operator Route Registry (`operator_route:{operator_id}:{route_id}`) без него. Добавлено полем 4 в `platform-contracts/common/stage_contract.proto` (см. комментарий там); `ExecutionState` уже накапливал значение с этапа DestinationResolution, только не прокидывал его в `DeliveryExtension` — см. `delivery_command_carries_resolved_operator_id_accumulated_since_destination_resolution`.

## Реальная находка компилятора: два protobuf package и относительные пути prost

`mpp.events.v1` (`IncomingMessage`) ссылается на типы `mpp.common.v1` (`SmsPayload`, `Channel`) — prost-build генерирует эти ссылки как относительные Rust-пути (`super::super::common::v1::Channel`), которые жёстко предполагают, что итоговая структура модулей в точности повторяет точки в имени package (`mpp.common.v1` → `mod mpp { mod common { mod v1 } } }`). Первая версия `proto.rs` оборачивала сгенерированный код в плоские `pub mod common`/`pub mod events` (тот же паттерн, что у сервисов с одним package) — не собралась: `cannot find common in super`. Все предыдущие сервисы этой сессии (Destination Resolution, Policy, Billing, Routing) использовали только один package (`mpp.common.v1`), поэтому эта проблема физически не могла проявиться раньше — Pipeline Engine первый, кому нужен `IncomingMessage` из `mpp.events.v1`. Исправлено точной вложенностью `pub mod mpp { pub mod common { pub mod v1 {...} } pub mod events { pub mod v1 {...} } }` + короткие `pub use`-алиасы для остального кода.

## Ключевой тест — правило, которое существует НЕЗАВИСИМО от графа

`service_internal_methods.md` §1.4 формулирует особый случай текстом: "если завершилась Billing, а сохранённая category == BLOCKED — Terminal, **независимо от того, что граф конфигурации мог бы предписать** для обычного SUCCEEDED от Billing". Это не то же самое, что "граф правильно разводит два случая отдельными узлами" (так уже сделано в `pipeline.valid.json` — REJECTED от Policy ведёт в отдельный `n_billing_blocked`) — это **defense-in-depth поверх графа**, страховка на случай, если граф сконфигурирован неправильно.

`billing_blocked_override_fires_even_if_graph_would_route_onward` доказывает именно это: тест конструирует **патологический граф**, где узел `n_billing_blocked` с `SUCCEEDED` ведёт в `n4_routing` (как будто граф ошибочно НЕ развёл случаи), но `category` в состоянии — `BLOCKED`. Override обязан сработать и привести к `Terminal`, несмотря на то, что граф прямым текстом предписывает `ROUTING`. Без этого теста было бы легко реализовать только "правильный граф + обычный traversal" и упустить, что документ требует отдельной, независимой проверки.

## Тесты — что ещё доказано

* **`full_happy_path_walks_entire_real_graph_to_terminal`** — весь путь `n1_destination_resolution → n2_policy → n3_billing → n4_routing → n5_delivery → n6_reconciliation → Terminal` на настоящем `config_schemas/examples/pipeline.valid.json`, с накоплением `resolved_operator_id`/`category`/`route_id` в `ExecutionState` на каждом шаге и передачей их в команду следующей стадии.
* **`policy_rejected_routes_to_billing_blocked_node_then_terminates`** — то же графовое правило, что уже провалидировано структурно в `config_schemas/validate_all.py`, здесь проверено через реальный обход рантайм-кодом.
* **`billing_command_carries_accumulated_operator_and_category`** — `BillingExtension.segment_count` не пересчитывается, а несётся из значения, посчитанного один раз при `handle_incoming` (HLD: "посчитано один раз Pipeline Engine при кэшировании контекста").

## Исправлено по итогам независимого кодревью (`CODE_REVIEW.md`)

* **High — редоставленный `incoming.messages` мог привести к двойному списанию.** `handle_incoming` всегда строил свежий `ExecutionState` с нуля и генерировал новый `stage_execution_id` через `Uuid::new_v4()` — единственный ключ идемпотентности, на который дедуплицирует Billing. При at-least-once редоставке `incoming.messages` (ретрай продюсера, гонка publish/commit) пайплайн откатывался на `DestinationResolution` со свежим id, и Billing видел это как новое списание. Исправлено: `run_incoming_loop` проверяет наличие состояния для `message_id` в сторе ДО обработки — активный (ещё не завершённый) пайплайн для этого сообщения не запускается повторно. **Остаточный пробел, не скрыт:** если пайплайн уже успел завершиться и его состояние удалено (`finalize_pipeline`), эта проверка не сработает — нужен персистентный журнал "уже обработано" (Runtime Redis с TTL), не только in-memory карта активных, см. ниже.
* **High — `stage.completed` применялся без проверки, что событие относится к стадии, которую пайплайн реально сейчас ждёт.** `resolve_next_stage` резолвил состояние по одному `message_id`, не сверяя `stage_name`/`stage_execution_id` события с тем, что было реально диспетчеризовано. Устаревший/дублирующийся `StageCompletedEvent` (гарантирован Kafka at-least-once, не гипотетичен) для уже пройденной стадии мог продвинуть пайплайн повторно, минуя реальную следующую стадию целиком (например, минуя все проверки Policy). Исправлено: `ExecutionState.awaiting_stage_execution_id` фиксирует, чего мы реально ждём; `handle_stage_completed` сверяет и `stage_name`, и `stage_execution_id` события, несовпадение → `Decision::Ignored` (не `Terminal` — пайплайн не завершён, просто это конкретное событие — шум). Доказано `stale_duplicate_event_for_already_advanced_stage_is_ignored_not_applied` и `mismatched_stage_execution_id_for_same_stage_is_ignored`.
* **Medium/High — `Delivery`/`DeliveryReconciliation` получали `RoutingExtension` вместо своего варианта oneof.** Реально достижимо через настоящий граф и проходило собственный happy-path тест сервиса незамеченным, потому что тест проверял факт продвижения по графу, не какой именно вариант `stage_extension` при этом строился. Исправлено: `DeliveryExtension` строится из `route_id`/`protocol`/`route_version`, реально накопленных в `ExecutionState` из `RoutingResult`; если Routing ещё не завершился (данных нет) — явная ошибка, не пустые/заглушечные поля (`delivery_command_without_route_in_state_is_rejected_not_built_with_empty_fields`). `DeliveryReconciliationExtension.triggering_outcome` — константа `SUBMISSION_OUTCOME_UNKNOWN` (тот же выбор, что документирует сам proto-комментарий: "сегодня всегда SUBMISSION_OUTCOME_UNKNOWN") — реальный триггер лежит вне Pipeline Engine (Scheduler Background Lane), не источник для этого поля в текущей архитектуре.
* **Low — `redis`/`async-trait`/`arc-swap` были объявлены в `Cargo.toml`, но нигде не использовались** — заявлены под функциональность, которой в этом срезе ещё не было (Runtime Redis CAS, hot-reload). `redis` с тех пор реально используется (`redis_cas.rs`, см. выше) — вернулся в `Cargo.toml` вместе с реальным кодом, не заранее; `async-trait`/`arc-swap` по-прежнему не добавлены, hot-reload графа всё ещё не реализован.
* **Panics на неизвестном `stage_name` заменены на `Result`** — `build_stage_execute`/`stage_topic` больше не `panic!()`, возвращают ошибку, которую вызывающая сторона логирует и пропускает (одно повреждённое сообщение больше не обязано ронять процесс целиком — `tokio::join!` без `spawn`/`JoinHandle` всё ещё не изолирует паники внутри самих циклов, это осталось нерешённым, см. ниже).

## Что НЕ реализовано на этом шаге (честно, не спрятано)

* **`check_admission`/`publish_hold_command` не реализованы** — Execution Control (Фаза 3.1, владелец Субагент 1) публикует `execution.control`, которое Pipeline Engine должен проверять перед каждой диспетчеризацией; здесь это отсутствует полностью, не заглушка "всегда Admit" (даже такой заглушки нет).
* **Откат при неудачной публикации после успешного CAS в `run_completed_loop` не реализован** — см. раздел про Redis CAS выше, тот же класс пробела, что уже был в in-memory версии, не новый.
* **`StageExecuteCommand.deadline`/`message_ttl` (wire-поля) по-прежнему не заполняются** (`build_stage_execute.rs`) — отдельный, не тронутый этой правкой пробел: внутренний `deadline_ms` в `ExecutionState`/Redis (для Critical Sweep) — самостоятельный механизм, не связан с этим wire-полем, которое видят downstream-стадии.
* **Паники внутри `run_incoming_loop`/`run_completed_loop` не изолированы по сообщениям** — оба цикла запускаются через `tokio::join!`, не `tokio::spawn`+`JoinHandle` с перехватом паники на уровне задачи; сама бизнес-логика теперь не паникует на данных (см. выше), но общая изоляция "одно плохое сообщение не должно уронить весь процесс" не реализована как отдельный защитный слой.
