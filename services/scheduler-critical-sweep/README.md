# Scheduler — Critical Sweep

**Основание:** `development_plan.md` — Субагент 1, Фаза 3.2. Пересмотрен в `services_specifictaion.md` §3.1: больше не Kafka Streams-группа со своим changelog — раз в ~1с опрашивает шардированный Redis sorted set `deadlines:{bucket}` (Pipeline Engine пишет дедлайн туда атомарно вместе с CAS-переходом, `cas_transition_and_track_deadline`), публикует retry/timeout/DLQ.

**Статус:** реально компилируется и тестируется — `go build ./... && go vet ./... && go test ./...` (и `go test -race ./...`) чистые. Redis-путь протестирован против реального протокола Redis (`miniredis`, встроенный сервер, не мок транспорта).

```bash
cd services/scheduler-critical-sweep
go build ./...
go vet ./...
go test ./...
go test -race ./...
```

## CODE_REVIEW.md — что исправлено в этом срезе

Этот сервис был помечен ревью как источник "самых серьёзных проблем корректности в ветке subagent-1". Ниже — что было реально исправлено, находка за находкой (нумерация — как в `CODE_REVIEW.md`).

### Critical

**#1 — republish без `stage_extension`/`payload_ref`, гарантированный REJECTED.** Проверено против `destination-resolution-service/src/kafka_io.rs`: команда без `stage_extension` детерминированно отклоняется как `REJECTED, retryable=false` — терминальная, не повторяемая ошибка. Исправлено в `internal/kafkaio/builders.go`:
* `payload_ref` теперь **всегда** заполняется — это не требует дополнительных данных, `StagePayloadRef{message_id, "msgctx:"+message_id}` детерминированно строится из уже известного `message_id` (`platform-contracts/common/types.proto::StagePayloadRef`).
* `stage_extension` теперь собирается функцией `buildStageExtension` из накопленных результатов предыдущих стадий (`sweep.ExecutionState.DestinationAddress/ResolvedOperatorID/Category/SegmentCount/RouteID/Protocol/RouteVersion` — новые поля, читаются оппортунистически в `redisio.LoadExecutionState`). `BuildRetryCommand` теперь возвращает `(*commonv1.StageExecuteCommand, bool)` — `ok=false`, если данных для конкретного `stage_name` недостаточно.
* `main.go::processEntry`: если `BuildRetryCommand` вернула `ok=false`, retry **не публикуется** — вместо трёх заведомо неверных попыток (каждая уходит в `REJECTED` с неверной причиной) сразу публикуется `DlqRecord` с честным `error_detail` ("insufficient runtime state to rebuild stage_extension for retry").

  **Почему это до сих пор не полный фикс, а не спрятанное допущение.** `data_infrastructure_spec.md` §2.1 сегодня документирует `exec:{message_id}` как `pipeline_version, node_id, stage_execution_id, current_state, attempt, deadline, last_applied_event_id` — без единого поля, из которого можно восстановить `stage_extension`. Это межсервисный контракт, которым владеет Pipeline Engine ("Главный агент", `development_plan.md` "Координация" п.2), а не Critical Sweep. Инфраструктура для правильной сборки **готова и протестирована** (`buildStageExtension`, per-stage switch, `builders_test.go`) — как только Pipeline Engine начнёт писать эти поля в `exec:{message_id}` той же CAS-транзакцией, что и остальное состояние, republish автоматически заработает корректно, без дальнейших изменений в Critical Sweep. До этого момента — сервис безопасно уходит в честный DLQ вместо гарантированно неверного `REJECTED` (строго лучше исходного поведения, не притворяется, что проблема решена полностью).

  **Независимое подтверждение направления, не то же самое, что подтверждённый контракт**: реальная (этой же сессии, другой агент, другой репозиторий/worktree) реализация `services/pipeline-engine/src/redis_cas.rs` + `lua/cas_transition.lua` уже атомарно пишет в `exec:{message_id}` поля `resolved_operator_id/category/segment_count/route_id/protocol/route_version/destination_address` — те же имена, что использованы здесь. Это сильный сигнал, что направление верное, но НЕ смёрженный, не подтверждённый контракт — сам этот код на момент написания ещё не синхронизирован даже с собственной `data_infrastructure_spec.md` (там, где я его читал, схема ещё не обновлена), поэтому здесь я не стал молча менять схему чтения `LoadExecutionState` под предположение, что чужая незамёрженная ветка — это финальный контракт. Если/когда контракт зафиксируют, `LoadExecutionState` уже готов его прочитать (те же имена полей).

**#2 — `Attempt` в `DlqRecord.original_command` был на 1 больше реально исчерпанной попытки.** `BuildRetryCommand` раньше сама считала `state.Attempt+1` и переиспользовалась для DLQ-снимка. Теперь `attempt` — явный параметр `BuildRetryCommand(state, eventID, attempt, deadline, traceparent)`: `main.go` передаёт `state.Attempt+1` для настоящего retry и `state.Attempt` для DLQ/insufficient-extension снимка. `builders_test.go::TestBuildDlqRecordOriginalCommandUsesExhaustedAttemptNotAttemptPlusOne` и `main_test.go::TestProcessEntryDlqOriginalCommandUsesExhaustedAttempt` фиксируют это регрессионным тестом на обоих уровнях.

### Severe

**#3 — 4+ реплики без координации, гарантированные дубликаты.** `internal/redisio/client.go::ClaimDeadline` — атомарный Lua-скрипт (`ZSCORE`-проверка + `ZREM` одним вызовом): из N конкурентных попыток забрать одну и ту же просроченную запись ровно одна получает `claimed=true`. Порядок в `main.go::processEntry` изменён: клэйм — **до** публикации (`ClaimDeadline`), не после (`ClearDeadline` после publish, как было). `redisio/client_test.go::TestClaimDeadlineOnlyOneOfTwoConcurrentCallersWins` — прямое доказательство.

**#4/#5 — `execution.control` консьюмер был partitioned consumer group вместо full local mirror; плюс тот же group id, что у `scheduler.critical.commands`.** `service_io_contracts.md` документирует `execution.control` как "Kafka (compacted, local snapshot)" — каждая реплика обязана зеркалировать ВЕСЬ топик. Исправлено в `internal/kafkaio/consumer.go::NewControlSnapshotConsumer`: **без `kgo.ConsumerGroup()`** (без группы franz-go назначает клиенту все партиции напрямую) + `kgo.ConsumeResetOffset(kgo.NewOffset().AtStart())` (пересобрать снапшот с нуля при каждом старте пода — нет committed offset, который можно было бы унаследовать). Добавлен `ParseRecordKey` — разбор ключа `"<ExecutionControlScope proto string>:<scope_id>"` (формат, реально производимый единственным продюсером — `execution-control-service/internal/kafkaio/publisher.go::RecordKey`) для обработки **tombstone**-записей (`value=nil`), у которых `scope`/`scope_id` есть только в ключе, не в value. `controlsnapshot.Snapshot.Delete` — новый метод, применяет tombstone (снимает override целиком, не оставляет "залипшим"). После этого коллизия group id (#5) естественно снимается: `execution.control` вообще без группы, `scheduler.critical.commands` получил собственный явный id `"scheduler-critical-sweep-manual-commands"`.

**#6 — readiness флипался раньше, чем control snapshot успевал хоть раз опросить брокер; ошибка создания консьюмера — тихий возврат навсегда.** `main.go`: `runControlSnapshotConsumer` теперь (а) retry с экспоненциальным backoff (1с → 30с потолок) и на ошибке создания клиента, и на неожиданном обрыве `Run()` — раньше и то, и другое просто логировалось и горутина завершалась насовсем; (б) сигнализирует через закрытие канала `controlWarm` после **первого успешного** прохода `PollFetches` (колбэк `polled`, вызывается независимо от того, были ли в этом проходе записи). `main()` не вызывает `SetReady(true)`, пока не получит сигнал из `controlWarm` — но остаётся отзывчивым к `SIGINT`/`SIGTERM` во время прогрева (не блокирует shutdown, если стоп пришёл раньше warm-up).

### Moderate

**#7 — publish успешен, `ClearDeadline` не удался → дубликат на следующем тике.** Снято тем же изменением порядка, что #3: клэйм (=удаление) происходит **до** публикации, поэтому "успешный publish, но неудачный ZREM" как отдельный сценарий больше не существует. Взамен появился симметричный случай — успешный клэйм, неудачная публикация — обработан явно: `redisio.Client.RestoreDeadline` возвращает запись обратно в ZSET с тем же дедлайном (`main.go::processEntry`, `redisio/client_test.go::TestRestoreDeadlineReAddsEntry`, `main_test.go::TestProcessEntryRestoresDeadlineWhenPublishFails`). Остаточная неоднозначность — как во всех at-least-once системах этой кодовой базы (см. `destination-resolution-service`: "не коммитим offset — at-least-once, сообщение будет переобработано") — крах ровно между успешной публикацией на брокер и подтверждением `ProduceSync` может привести к повторной публикации после `RestoreDeadline`; не решается без transactional outbox, не изобретался здесь.

**#8 — записи с нерезолвящимся `stage_exec_index`/отсутствующим `exec:{message_id}` ретраились каждый тик без backoff (тайт-луп).** `main.go::processEntry`: обе ветки отказа (`ResolveMessageID`, `LoadExecutionState`) теперь вызывают `redisio.Client.DeferDeadline(entry, now+30s)` вместо `continue` — запись сдвигается в ZSET на будущее вместо немедленной повторной выборки на следующем тике. Честно **не** реализовано: настоящее dead-lettering для этих записей невозможно без `message_id` (нужен для `DlqRecord.message_id`) — при неудачном `ResolveMessageID` его физически нет. Настоящий фикс — писать `stage_exec_index:{stage_execution_id} → message_id` со стороны Pipeline Engine (см. "Открытый вопрос" ниже, было верно и до этой сессии) — не выдумывался.

**#9 — held (paused)-записи не откладывались, пересчитывались каждый тик всё время инцидента.** `main.go::processEntry`: `ActionHold` теперь вызывает `DeferDeadline(entry, now+5s)` вместо `continue`. `main_test.go::TestProcessEntryHoldDefersWithoutClaimingOrPublishing`, `redisio/client_test.go::TestDeferDeadlinePushesScoreForward`.

**#10 — `FORCE_TIMEOUT`/`FORCE_RETRY` декодируются, но не исполняются.** Перепроверено — по-прежнему честно задокументировано (докстринг `runManualCommandConsumer` в `main.go`), не притворяется реализованным. Не в объёме этой правки (требует переиспользуемого пути `processEntry`-по-`stage_execution_id`, минуя обычный sweep — механически возможно, но отдельная задача).

**#11 — нет `sync.WaitGroup` вокруг фоновых циклов перед `Close()`.** `main.go`: `sync.WaitGroup` вокруг всех трёх горутин (`runManualCommandConsumer`, `runControlSnapshotConsumer`, `runSweepLoop`), `wg.Wait()` вызывается после `cancel()` и до того, как отработают отложенные `redisClient.Close()`/`publisher.Close()`.

**#12/#13 — локальные wall-clock/`DEADLINE_BUCKETS` без проверки согласованности с Pipeline Engine.** Не реализовано намеренно — настоящее решение (Redis `TIME`-based skew detection; сверка числа бакетов через shared config/registry) требует межсервисного протокола, которого сегодня не существует ни в одном документе этой сессии, придумывать его в одностороннем порядке здесь не стал. `DEADLINE_BUCKETS=16` по умолчанию совпадает с тем, что использует `pipeline-engine/src/redis_cas.rs` (независимо, но по тем же причинам, см. его собственный докстринг) — совпадение задокументировано, не проверяется программно.

### Test quality

Раньше `processTick` принимал конкретные `*redisio.Client`/`*kafkaio.Publisher` и не мог тестироваться без реального Redis/Kafka. `cmd/scheduler-critical-sweep/main.go` теперь определяет `deadlineStore`/`commandPublisher` (минимальные интерфейсы под то, что реально используется) — `*redisio.Client`/`*kafkaio.Publisher` продолжают реализовывать их структурно, без изменений в своих сигнатурах. `cmd/scheduler-critical-sweep/main_test.go` — фейки обоих интерфейсов, 11 тестов покрывают: Hold→defer без клэйма, успешный retry, retry без extension→DLQ, проигранный клэйм→ничего не публикуем, публикация не удалась→RestoreDeadline, DLQ несёт исчерпанный attempt (не +1), обе ветки "не резолвится"→defer вместо busy-loop, `processTick` обходит все записи, ранний выход при ошибке `TickSweep`. `builders_test.go` теперь явно проверяет присутствие `payload_ref`/`stage_extension` (не проверялось раньше — ревью отмечало это прямо).

## Три исхода retry policy, не два

`service_internal_methods.md` §2.1 перечисляет `publish_timeout_result` ("ExpiredEntry без retry") и `publish_dlq` ("Exhausted") как **два разных метода на два разных исхода** — не один и тот же путь. Поэтому `RetryDecision` в `internal/sweep/types.go` — три состояния, не два: `NotRetryable` (стадия вообще не ретраится по таймауту, `MaxAttempts=0` → `TIMED_OUT` сразу) отдельно от `Exhausted` (ретраится, но попытки кончились → DLQ). В этом первом срезе все стадии используют единый `defaultRetryPolicy{MaxAttempts: 3}` (`cmd/.../main.go`) — `pipeline.schema.json` не специфицирует retry-параметры per-stage (только граф переходов по `Outcome`), различный профиль per-stage не реализован. Практическое следствие: с `MaxAttempts` всегда `3` (никогда `0`) путь `ActionTimeout` сегодня в `processEntry` недостижим на практике — код и тесты на него оставлены (для будущего per-stage профиля), но текущая конфигурация всегда идёт по Retry/Dlq/Hold.

## Открытый вопрос — reverse index stage_execution_id → message_id (для Главного агента)

`data_infrastructure_spec.md` §2.1 документирует `deadlines:{bucket}` (ZSET, member = `stage_execution_id`) и `exec:{message_id}` (HASH, ключ по `message_id`) — но не документирует, как получить `message_id` по `stage_execution_id` из просроченной записи. Это генеральный разрыв: Critical Sweep физически не может дойти от `ExpiredEntry` до `LoadExecutionState` без этого шага.

**Решение в этом срезе** (`internal/redisio/client.go::ResolveMessageID`, `stageExecIndexKey`): предполагается дополнительный `STRING`-ключ `stage_exec_index:{stage_execution_id} → message_id`, который должен писать Pipeline Engine той же Lua-транзакцией, что и `cas_transition_and_track_deadline` (симметрично уже существующему `ZADD` в `deadlines:{bucket}`). **Это не тихо принятое решение** — Pipeline Engine и схема Runtime Redis принадлежат Главному агенту (`development_plan.md` "Координация" п.2); нужно либо подтвердить этот ключ, либо изменить member ZSET на составной (`message_id:stage_execution_id`), что потребует правки на стороне Pipeline Engine в любом случае. До тех пор `ResolveMessageID` в проде будет возвращать ошибку почти всегда — обработано backoff'ом (`DeferDeadline`, finding #8), не тайт-лупом, но не решает первопричину.

**Второй, отдельный от первого разрыв — `payload_ref`/`stage_extension` при republish** (CODE_REVIEW.md finding #1/#2, разобрано выше подробно): `exec:{message_id}` не хранит накопленные результаты предыдущих стадий, из которых собирается `stage_extension`. Инфраструктура на стороне Critical Sweep готова (`buildStageExtension`, `sweep.ExecutionState` расширен полями, `LoadExecutionState` их читает оппортунистически) — недостающая часть целиком на стороне Pipeline Engine: начать писать `destination_address/resolved_operator_id/category/segment_count/route_id/protocol/route_version` в `exec:{message_id}` той же CAS-транзакцией.

**Третий разрыв, обнаруженный при расследовании находки #1, но НЕ входящий в scope этой правки** (out of scope для Go-сервиса Critical Sweep, требует координации с владельцем Pipeline Engine, задокументирован здесь честно, а не тихо проигнорирован): ни `data_infrastructure_spec.md`, ни реально проверенная реализация `pipeline-engine/src/redis_cas.rs`/`lua/cas_transition.lua` не показывают, кто перезаписывает `deadlines:{bucket}` новым дедлайном **при retry** (не при переходе на следующий узел графа — только тогда `cas_transition_and_track_deadline` вызывается). Critical Sweep после клэйма (`ClaimDeadline`) удаляет старую запись и публикует retry-команду с новым `deadline` в самом сообщении, но **ничто не добавляет новую запись обратно в `deadlines:{bucket}`** для этой повторной попытки — если ретраенная стадия снова зависнет, Critical Sweep об этом никогда не узнает (запись просто больше не существует в ZSET). Это архитектурный вопрос "кто владеет `deadlines:{bucket}` на retry-пути" — не то же самое, что уже описанный `stage_exec_index`, и не то, что Critical Sweep должен решать в одностороннем порядке (может означать, что сам Critical Sweep обязан сам себе делать `ZADD` при публикации retry — но это меняет модель "Pipeline Engine — единственный писатель `deadlines:{bucket}`", задокументированную в `data_infrastructure_spec.md` §283, и должно обсуждаться, а не молча внедряться здесь).

## Что НЕ реализовано на этом шаге (честно, не спрятано)

* **`docker build` не выполнялся** — недоступный Docker daemon в этой песочнице.
* **Ни разу не запущено против реального Kafka-брокера** — `internal/kafkaio.Publisher`/`ManualCommandConsumer`/`ControlSnapshotConsumer` используют настоящий `franz-go`, компилируются, но не проверялись против `kind`+Strimzi.
* **`on_manual_command` не выполняет принудительную обработку** (finding #10, см. выше) — консьюмер `scheduler.critical.commands` только логирует `FORCE_TIMEOUT`/`FORCE_RETRY`.
* **Reverse index `stage_exec_index`** и **накопленные результаты стадий для `stage_extension`** — см. "Открытый вопрос" выше: обе зависят от изменений на стороне Pipeline Engine, которых у Critical Sweep нет полномочий вносить в одностороннем порядке.
* **`deadlines:{bucket}` не перезаписывается на retry-пути** — третий пункт "Открытого вопроса" выше, обнаружено при расследовании finding #1, не исправлялось (архитектурный вопрос владения ключом, требует координации).
