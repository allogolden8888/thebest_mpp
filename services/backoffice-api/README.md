## RBAC-расширение (luminous-hugging-charm.md Фаза 0 — Identity/RBAC/Audit)

**Что изменилось.** Единственный бинарный gate `auth.RequireRole(auth.AdminRole)` (роль `backoffice-admin` из `realm_access.roles`, см. CODE_REVIEW.md CRITICAL пункт выше — временная мера, явно ждавшая "отдельного LLD Backoffice API") заменён на гранулярные права, проверяемые через новый `services/iam-service` (`platform-contracts/grpc/iam.proto`, `migrations/V025__iam.sql`/`V026__iam_manage_permission.sql`). `auth.RequireRole`/`auth.AdminRole` физически удалены из `internal/auth/jwt.go` — не оставлены как мёртвый код, т.к. `router.go` целиком перешёл на `auth.RequirePermission`.

* **`internal/auth/permission.go`** — новый `auth.RequirePermission(permission string, client grpcv1.IamServiceClient) func(http.Handler) http.Handler`. На каждый запрос синхронно вызывает `IamService.CheckPermission(claims.Subject, permission)` с таймаутом 3с (`checkPermissionTimeout`).
* **Fail-closed — не стилистическая деталь, а требование контракта** (см. `CheckPermission` docstring в `platform-contracts/grpc/iam.proto` и `iam-service/README.md`): если сам gRPC-вызов к IAM Service завершается ошибкой (сервис недоступен, таймаут, TLS/сеть) — ответ **503**, запрос НЕ пропускается дальше. Backoffice API способен поставить на паузу весь трафик платформы (`execution-control override`) и мутировать production-конфиг — сервис с такой властью не может по умолчанию проваливаться в "открыто" из-за недоступности собственной зависимости. Обратная сторона: отказ IAM Service временно блокирует ВСЕ деструктивные операции backoffice-api — осознанный компромисс в пользу безопасности, не забытый краевой случай. `internal/auth/permission_test.go` `TestRequirePermissionFailsClosedWith503OnGRPCError` — регрессионный тест именно на это (не 200/pass-through).
* Если `CheckPermission` отвечает `allowed=false` — 403 с сообщением, называющим требуемое право (не просто "forbidden").
* **Маршрут → право** (`router.go`): `POST /config/versions` и `/config/versions/archive` → `config:write`; `POST /execution-control/override[/clear]` → `execution-control:write`; `POST /scheduler/force-command` → `scheduler:force`; `POST /replay` → `replay:request`; `GET /audit` → `audit:read`; все `/iam/*` → `iam:manage`. В отличие от прежнего единого `r.Group(auth.RequireRole(...))` на все 6 маршрутов разом, здесь у каждого маршрута своё право, смонтированное точечно через `r.With(...)`.
* **`GET /v1/me`** — без gate прав (любой валидный токен realm'а видит СВОЙ ЖЕ эффективный доступ): `ListStaffAssignments(external_id=sub)` → активные роли, `ListRoles()` → права каждой роли, объединение без дублей. `{"external_id", "roles", "permissions"}`.
* **`GET /v1/audit?source=&limit=&offset=`** (право `audit:read`) — объединённый Audit Log из ЧЕТЫРЁХ источников ПРЯМЫМ SQL (`internal/store/postgres.go` `AuditBrowse`, `internal/httpapi/audit.go`), не через gRPC — тот же принцип, что `DlqBrowse`/`ReconciliationBrowse` (административный обзор чужой схемы, не транзакционная граница сервиса-владельца): `messaging.replay_audit`, `control.execution_control_audit`, `billing.reconciliation_audit`, `iam.identity_audit`. Нормализованный вид — `{source, actor, action, target, created_at}`; маппинг колонок у каждого источника СВОЙ (задокументирован в docstring `AuditBrowse`, самый нетривиальный случай — `billing.reconciliation_audit`, у которой в схеме вообще нет колонки-актёра: это полностью автоматический процесс billing-reconciliation-service, actor — литерал `"billing-reconciliation-service"`, не NULL). `source`-фильтр — во внешнем `WHERE` поверх `UNION ALL` четырёх простых веток без собственных фильтров (проще проверить на корректность, чем динамически собирать подмножество веток; planner исключает непрошенные ветки по константному предикату). Пагинация — `limit`/`offset`, `next_offset` присутствует в ответе только когда есть ещё строки (запрашивается `limit+1`, без отдельного `COUNT(*)` по четырём таблицам — тот же облегчённый подход, что у "без `total_count`" остальных Browse-методов).
* **`/v1/iam/roles`, `/v1/iam/staff-assignments` (GET/POST/DELETE)** (право `iam:manage`) — тонкий gRPC-прокси в `IamService` (`internal/httpapi/iam.go`). `granted_by`/`revoked_by` ВСЕГДА берутся из `claims.Subject`, никогда из тела запроса (POST/DELETE body не несёт этих полей вообще — вызывающий структурно не может подделать, кто выдал/отозвал доступ, тот же принцип, что `requested_by` у config/execution-control/replay). `codes.NotFound`/`codes.AlreadyExists` от IAM Service маппятся в 404/409 (`writeIamGRPCError`), `DELETE` возвращает `{"revoked": false}` при отсутствии активного назначения — НЕ ошибка, тот же идемпотентный контракт, что и сам `IamService.RevokeStaffRole`.
* **Тесты.** `internal/auth/permission_test.go` — `RequirePermission` с прямой (не bufconn) реализацией `grpcv1.IamServiceClient`: pass-through при `allowed=true`, 403 при `allowed=false`, **503 при ошибке gRPC-вызова** (fail-closed), 500 если смонтирован до `Validator.Middleware`. `internal/httpapi/router_test.go` — `fakeIamServer` (bufconn, полноценный `IamServiceServer`, не только `CheckPermission`) покрывает permission-gating всех новых и старых деструктивных маршрутов (`TestNonPrivilegedTokenRejectedOnDestructiveRoutes`), `/v1/me` (объединение прав по ролям), `/v1/audit` (форма ответа, против реального Postgres), `/v1/iam/*` (roles/assign/conflict-409/list-filter/revoke/idempotent-revoke, `granted_by`/`revoked_by` реально из JWT). `internal/store/postgres_test.go` `TestAuditBrowseMergesAndSortsAcrossSources` — реальный round-trip: вставка в `iam.identity_audit` и `control.execution_control_audit`, проверка маппинга колонок, `source`-фильтра и сортировки `created_at DESC` по РЕАЛЬНЫМ строкам (не только по мокам).

## Rotate credential (luminous-hugging-charm.md Фаза 1 — живой выпуск/ротация partner credentials)

Тонкий gRPC-прокси в новый `services/credential-issuer-service` (`platform-contracts/grpc/credentials.proto`, `internal/httpapi/credentials.go`) — backoffice-ui "Rotate credential" (`ConfigView.vue`).

* **`POST /v1/partners/{partner_id}/applications/{application_id}/credentials/rotate`** (право `credentials:issue`) — без тела запроса вообще, `partner_id`/`application_id` из пути, `issued_by` ВСЕГДА из `claims.Subject` (тот же принцип, что `granted_by`/`revoked_by` в `/v1/iam/*`). Проксирует `CredentialIssuerService.RotateCredential`. Ответ несёт `plaintext_secret` — присутствует РОВНО в этом одном ответе (show-once), нигде не логируется/не сохраняется этим сервисом.
* **`GET /v1/partners/{partner_id}/credentials`** (тот же `credentials:issue` — просмотр истории выпуска и сама ротация одного уровня чувствительности, не разделены на read/write права) — проксирует `ListIssuedSecrets`, метаданные (`secret_version`/`status`/`issued_by`/`issued_at`), никогда сам секрет.
* **Маппинг ошибок** (`writeCredentialIssuerGRPCError`) — `codes.NotFound` → 404 (партнёр/приложение не существует в PARTNER-конфиге), `codes.FailedPrecondition` → **422** (не 400 — не ошибка формы запроса вызывающего: `credential_ref`, уже сохранённый в `config.config_versions`, не парсится ожидаемой формой `vault://path/property`, реальная, хоть и редкая, проблема состояния данных на сервере, не входных данных этого запроса), `codes.Unavailable` → 503 (запись в Vault не удалась).

## Кросс-партнёрский поиск для саппорта (luminous-hugging-charm.md Фаза 9)

**`GET /v1/support/messages/search?message_id=&trace_id=&limit=&offset=`** (право `support:trace`) — прямое чтение `messaging.message_read_model` (`internal/store/postgres.go` `SupportMessageSearch`, `internal/httpapi/support.go`), тот же источник данных, что уже читает `partner-api`, но БЕЗ фильтра по `partner_id` — партнёрский `Search` намертво зашивает `partner_id` из JWT (многотенантность), здесь его сознательно нет: весь смысл фазы — саппорт видит сообщение независимо от того, какому партнёру оно принадлежит. Требует хотя бы `message_id` ИЛИ `trace_id` — оба пустых → 400, не "верни всю таблицу кросс-партнёрски" (по факту это была бы полная выгрузка `message_read_model`, ничем не ограниченная).

**Поиск по `msisdn`, названный в плане Фазы 9 буквально, НЕ реализован — честно, не молчаливый пробел.** `msisdn` не персистится ни в одном queryable месте этой платформы: ни в `messaging.message_read_model`/`message_lifecycle_history` (проверено прямым чтением обеих миграций), ни в ClickHouse `analytics.stage_events` (`services/analytics-writer/internal/store/store.go` — колонок нет). Единственное место, где `msisdn` вообще существует — `msgctx:{message_id}` в Runtime Redis, ключ по `message_id`, TTL 24ч, НЕ reverse-searchable по значению без полного `SCAN` по всем живым ключам — на заявленном масштабе платформы (27-40к сообщений/с, `capacity_model.md` §6.2) это не "неоптимально", а физически неосуществимо за разумное время: число живых `msgctx`-ключей в 24-часовом окне при таком трафике — миллиарды. Правильное решение (добавить индексируемую `msisdn`-колонку в `message_read_model`, либо отдельный поисковый индекс) — реальная, отдельно оцениваемая работа с собственными вопросами (retention/PII), не точечное расширение этого эндпоинта — не начато в этом срезе.

## Config preview/diff (luminous-hugging-charm.md Фаза 10)

## Аутентификация/аудит

`internal/auth/jwt.go` — тот же RS256-валидатор, что `partner-api` (см. его README для деталей проверки), но здесь claim — стандартный `sub` (Keycloak OIDC subject), не кастомный `partner_id`: Backoffice API административный, не многотенантный. `sub` используется как `requested_by` в каждой аудируемой мутации (`CreateVersion`/`ArchiveVersion`/`ApplyOverride`/`ClearOverride`/`SchedulerCriticalCommand.requested_by`/`RequestReplay.requested_by`) — сервер, принимающий запрос, не может доверять `requested_by` в теле, поэтому все proxy-методы всегда перезаписывают его значением из проверенного токена.

## gRPC-проксирование — реально протестировано через bufconn, не только описание

`internal/httpapi/router_test.go` поднимает **реальные gRPC-серверы** через `google.golang.org/grpc/test/bufconn` (in-process транспорт, официальный пакет grpc-go для тестов — тот же принцип, что `InProcessServerBuilder` в Java-сервисах этой сессии) с фейковыми реализациями `ConfigServiceServer`/`ExecutionControlServiceServer`/`ReplayServiceServer`/`IamServiceServer` (`fakeIamServer` — in-memory, но семантически верный CRUD над ролями/назначениями, включая `codes.AlreadyExists`/`codes.NotFound`, те же коды, что и настоящий `iam-service`), и настоящими сгенерированными gRPC-клиентами (`grpcv1.NewConfigServiceClient` и т.д.) поверх них. Это первое использование bufconn в Go-сервисах этой сессии (остальные Go gRPC-тесты этой сессии — на стороне сервера, не клиента).

## Что НЕ реализовано на этом шаге (честно, не спрятано)

* **ОБНОВЛЕНО 2026-08-06:** `docker build` реально прогнан и провалидирован для этого сервиса (найдены и исправлены реальные баги по пути, где применимо — см. `development_plan.md` "Координация" п.5 и `infra/docker/README.md`). Формулировка ниже — из более раннего состояния сессии, оставлена для истории.
* **`docker build` не выполнялся** — недоступный Docker daemon.
* **`k8s/generate_manifests.py` резервирует `internal_grpc_port=9000` для `backoffice-api`**, но ни один документ (`service_internal_methods.md` §7.3, `service_io_contracts.md`) не специфицирует, какой gRPC-сервис должен слушать на этом порту — Backoffice API в этой реализации только вызывает чужие gRPC-сервисы (клиент), собственного gRPC-сервера не поднимает. Не реализовано — находка, не молчаливое решение; возможно порт зарезервирован для будущего внутреннего API (например, health/debug gRPC) или это шаблонное значение генератора манифестов, применённое по инерции ко всем сервисам "Мелкого Go control-plane" пула.
* **JWKS/ротация ключей** — статический RSA public key из `JWT_PUBLIC_KEY_PEM`, как и в Partner API.
* **Полная RBAC-модель** — РЕАЛИЗОВАНА в Фазе 0 (см. "RBAC-расширение" выше): `iam-service` + `migrations/V025__iam.sql` заменили заглушку `backoffice.users` (`V017__backoffice_stub.sql`, которая никем не читалась в коде). Оставлено ниже для истории конкретно того, что было НЕ сделано на этом шаге:
  * **Нет in-proc кеширования `CheckPermission`** — КАЖДЫЙ мутирующий запрос (и `GET /v1/me`/`/v1/audit`/`/v1/iam/*`) синхронно round-trip'ит в IAM Service (который сам синхронно идёт в Postgres). Тот же принцип минимализма, что `ExecutionControlService.ApplyOverride` — "без кеширования на этом шаге" явно зафиксировано в `iam.proto`. Под нагрузкой это отдельная, отдельно оцениваемая оптимизация (TTL-кеш на стороне `auth.RequirePermission`, с понятным вопросом инвалидации при отзыве роли — не тривиально сделать безопасно, поэтому не сделано наспех).
  * **`/v1/audit` без общего `total_count`** — как и остальные Browse-методы этого сервиса, только `next_offset` (есть ли ещё страница), без числа "всего строк по фильтру" (стоило бы отдельного `COUNT(*)` по `UNION ALL` четырёх таблиц).
  * **Keycloak realm-роли `iam.roles` не синхронизируются автоматически** — обратная совместимость обеспечена только тем, что `backoffice-admin` заведена в `iam.roles` как суперроль с полным набором прав (см. `iam-service/README.md`); реальное сопоставление "кому в Keycloak назначить какую `iam`-роль" — координация вне кода, тот же явный вынос ответственности, что и раньше.
* **`GET /v1/support/messages/search` (Фаза 9) без экрана в `backoffice-ui`** — план не называл раздел UI для этой фазы явно (в отличие от Ф0/Ф7/Ф8/Ф10, у каждой из которых есть свой пункт "backoffice-ui"), эндпоинт реализован и протестирован, но сегодня используется только напрямую (curl/Postman) — саппорту без доступа к API это недоступно. Не забыто, буквально не входило в скоуп фазы как она сформулирована; тривиально добавить экран позже по тому же паттерну, что `AuditLogView.vue`.
  * **`backoffice-ui` "Access Control" экран** — отдельная работа параллельного агента (`services/backoffice-ui/`), эндпоинты (`/v1/iam/*`) готовы под него, но сам UI не в этом сервисе.
* **Live Kafka не проверялся** — `internal/kafkaio.Publisher` использует реальный `franz-go`, но публикация в `scheduler.critical.commands` не проверена против живого брокера (тот же общесессионный пробел).
* **OpenTelemetry-экспорт** — span'ы создаются (`internal/telemetry`, тот же паттерн, что Partner API), никуда не отправляются (`noopExporter`).
* **`ListVersions`/`DlqBrowse`/`ReconciliationBrowse`/`Report` без `total_count`** — только страница результатов, без общего количества строк по фильтру.
* **`/metrics`** — плейсхолдер Prometheus exposition format (валидный 200), без реальных счётчиков.
