# A2P MPP — 1500 TPS push on second hardware (продолжение LATENCY_INVESTIGATION.md)

**Основание:** прямое продолжение `LATENCY_INVESTIGATION.md` — тот документ закончился выводом "естественный следующий эксперимент — прогнать тот же тест на железе с большим количеством RAM/CPU". Эта сессия — именно этот эксперимент, плюс попытка пойти дальше исходной цели 300 TPS (5×, до 1500 TPS) и найти реальные узкие места кодом/профилированием, а не только железом.

**Железо:** AMD Ryzen 5 7600X, Docker Desktop: 12 CPU / 15.16GB (vs Mac M1 Pro в предыдущей сессии: 8 vCPU, 7.75GB Docker VM, общий с другими проектами).

**Методология:** тот же локальный docker-compose walking skeleton (12 из 32 сервисов платформы — см. "Чего не хватает" ниже), `loadgen`/`smsc-simulator` с прошлой сессии не сохранились в репозитории (были на Mac) — написаны заново под ту же методологию: `rate`/`concurrency`/`duration`/`msisdns` HTTP-нагрузка на `POST /v1/messages`, latency измерена по собственному Kafka broker timestamp записи `stage.completed` (не по `completed_at` в payload — он в этом срезе кода не заполняется сервисами, `completed_at: None` в `kafka_io.rs`), не интеграционные тестовые инструменты, не закоммичены в этот репозиторий.

## Часть 1 — 300 TPS воспроизведение: подтверждает вывод прошлой сессии

Тот же профиль нагрузки (`rate=300, concurrency=100, duration=60s, msisdns=8000`), без единой правки кода:

| Метрика | Mac M1 Pro | Этот ПК | Ускорение |
|---|---|---|---|
| p50 | 1660 ms | 105 ms | 15.8× |
| p95 | 5100 ms | 119 ms | 42.9× |
| p99 | 5700 ms | 129 ms | 44.2× |
| max | 6300 ms | 159 ms | 39.6× |
| DELIVERY success | 100% | 100% | — |

SLA (p50 ≤300ms) впервые пройден. На обеих машинах узким местом при 300 TPS была Kafka (Mac — ~1 ядро, здесь — до ~3 ядер при полной загрузке) — на этой машине запаса хватило с большим избытком. Подтверждает вывод прошлой сессии: это был потолок конкретной локальной машины, не остаточный дефект кода.

## Часть 2 — разгон до 1500 TPS: три реальных бага, найденных профилированием

Первая попытка (1500 TPS, конфигурация без изменений) обвалила систему — не из-за нехватки CPU (пиковая суммарная загрузка ядер не превышала ~560% из 1200% доступных), а из-за трёх реальных находок.

### Находка #1 — `partner-rest-receiver`: новое TCP+Redis-соединение на каждый HTTP-запрос

`strace -c` на живом процессе под нагрузкой (300 req/s, 10с окно): **~90% времени в syscall'ах уходило на `socket`/`connect`/`setsockopt`/`close`** (6045 `connect`, 9063 `close` за ~3000 запросов — ~2 новых TCP-соединения на запрос), не в бизнес-логике.

Причина: `msgctx.rs::write()` и `idempotency.rs::claim()` делали `redis::Client::open(url)` + `get_multiplexed_async_connection()` заново на КАЖДЫЙ вызов вместо переиспользуемого соединения — `AppState` хранил голую `redis_runtime_url: String`, не готовое соединение (тот же класс упрощения, что уже был осознанно задокументирован для фонового `redis_sync.rs`, но там это тикало раз в секунду, а не на полной скорости запросов). Для сравнения — `FutureProducer` (Kafka) в этом же файле уже был реализован правильно: создан один раз при старте, живёт в `AppState`.

**Фикс:** `AppState.redis_conn: MultiplexedConnection`, создан один раз в `main.rs`, клонируется (дёшево — общий TCP-хендл) на каждый запрос. `msgctx::write`/`idempotency::claim`/`redis_sync::sync_rate_limit_counters` больше не открывают соединение сами.

**Результат:** CPU `partner-rest-receiver` **578-684% → 36%** (в простое — 0.04%).

### Находка #2 — все 6 stage-сервисов: искусственно заниженные лимиты конкурентности

После фикса #1 latency при 1500 TPS ВЫРОСЛА (p50 21.2s → 35.2s) — не регрессия: раньше неоптимизированный ресивер сам себя тормозил и невольно работал как admission control, не пуская в систему больше ~900 msg/s. Убрав это узкое место, честные 1500/s начали реально доходить до Kafka → pipeline-engine → остальных стадий — а там у каждой стадии свой конкурентный пул задач, ограниченный дефолтом (`*_CONCURRENCY` env var — реально существующий, просто заниженный: 256 у Rust-сервисов, 128 у Java).

Подняли: `PIPELINE_INCOMING/COMPLETED_CONCURRENCY` 256→1024, `DESTINATION_RESOLUTION/POLICY/ROUTING_CONCURRENCY` 256→1024, `BILLING/DELIVERY_CONCURRENCY` 128→512.

**Результат:** p50 21.2s → 12.9s — лучше, но выявило находку #3 (success rate упал до 73.3%).

### Находка #3 — `operator-smpp-session-manager`: `TPS_LIMIT` смоделирован как реальный контракт оператора

`TPS_LIMIT` (дефолт 500) — намеренная бизнес-логика ("сколько реально может принять оператор связи по контракту"), не узкое место инфраструктуры. Под нашей нагрузкой (1500/s к единственному wired-оператору beeline_uz) 26.7% DELIVERY-стадий стабильно получали `TPS_THROTTLED`.

**Фикс (только для этого синтетического теста):** `TPS_LIMIT` 500→3000, `MAX_CONCURRENT_SUBMITS` 100→500 — уместно только потому, что на другом конце нашего теста собственный одноразовый `smsc-simulator`, не настоящий оператор с контрактным TPS.

**Итог после всех трёх находок (1500 TPS, 5× исходной цели):** p50=135ms, p95=336ms, p99=477ms, max=598ms, success=100%, 89227/89988 (99.15%) доставлены практически в реальном времени.

## Часть 3 — почему policy/billing/pipeline "жрут" ресурсы (по запросу пользователя)

### policy-service: матчинг шаблонов НЕ виноват — виноват один общий Mutex

Алгоритм в `template_matching.rs` — Aho-Corasick двухфазный префильтр, `O(длина текста)`, не `O(число шаблонов)` (доказано собственным тестом сервиса с 20 000 нерелевантных шаблонов). Настоящая причина: `evaluate_policy()` (матчинг + банворды + блэклисты + anti-spam) выполнялся под ОДНИМ `std::sync::Mutex<RuntimeState>`, расшаренным на все `POLICY_CONCURRENCY` (1024) конкурентных задач — под такой конкуренцией даже микросекундная критическая секция превращается в очередь + futex-контеншен (тот же класс находки, что и futex-доминированный `strace` у pipeline-engine).

**Фикс:** `ShardedRuntimeState` — пул из 32 (`POLICY_RUNTIME_STATE_SHARDS`, tunable) независимых `Mutex<RuntimeState>`, шардирование по `hash(msisdn) % 32` — все проверки одного msisdn идут в один шард консистентно, разные msisdn обычно не мешают друг другу.

**Результат:** CPU policy-service **98-150% → 21%** (в простое — 0.1-0.13%), задержка не пострадала (чистый выигрыш, единственная находка без побочных эффектов).

### billing-service / delivery-service / operator-smpp-session-manager: реальные ОС-потоки JVM, не лёгкие таски

`Executors.newFixedThreadPool(N, ...)` — **N означает N настоящих ОС-потоков** (видно в `docker stats` как PID-count), каждый со своим стеком, синхронно блокирующийся на `producer.send().get()`/gRPC-вызове. Rust-сервисы дают то же самое число "воркеров" почти бесплатно (async-таски поверх горстки реальных потоков) — числа `*_CONCURRENCY` не одинаковы по цене между Rust и Java-сервисами, хотя названы одинаково.

Наивное снижение до 200 (billing/delivery) дало РЕЗКО худший хвост задержки (p95 336ms → 1811ms) при том же p50 — не линейная деградация, а порог. JFR-профилирование (`-XX:StartFlightRecording`, уже был включён в образе, `jfr print --events jdk.JavaMonitorEnter`) исключило GC (все паузы <2ms) и указало на `RecordAccumulator.append` (Kafka-продюсер, внутренний батчинг **на партицию** — у нас все топики с 1 партицией) + у delivery-service ещё и `io.grpc...UncommittedRetriableStreamsRegistry`. Природа порога — не сам лок (он контендится пропорционально числу конкурентных `send()`, не размеру пула), а недостаточный запас потоков для поглощения всплесков трафика (Little's Law) при малом пуле.

Бинарный поиск (200 → 350 → 450 → откат к 512 для сравнения):

| `*_CONCURRENCY` | Потоков (billing) | p50 | p95 | p99 | max |
|---|---|---|---|---|---|
| 200 | ~240 | 120ms | 1811ms | 1939ms | 2038ms |
| 350 | ~360 | 117ms | 1876ms | 2037ms | 2163ms |
| **450** | **~490** | **112ms** | **254ms** | 960ms | 1158ms |
| 512 (исходное) | ~552 | 135ms | 336ms | 477ms | 598ms |

450 — по другую сторону порога, не хуже 512 при ~12% меньшем числе потоков.

`operator-smpp-session-manager` использует тот же паттерн (`MAX_CONCURRENT_SUBMITS`, был поднят 100→500 в находке #3, но не откалиброван) — путь к оператору здесь короче (один локальный gRPC + локальный `smsc-simulator`, latency ниже, чем у billing/delivery), калибровка 500→300 дала **лучший результат всего расследования**: p50=111ms, **p95=168ms**, p99=235ms, max=415ms, PID-count 546→344.

### pipeline-engine: структурно самый "разговорчивый" узел, не баг

На одно сообщение делает ~11 Redis Lua EVAL (CAS-переход `ExecutionState` на каждой из 5 стадий + `load` перед каждым) и до 5 Kafka produce — против 1-2 у любой другой стадии, по дизайну оркестратора. `ExecutionState` осознанно вынесен в Redis (CAS), не в `Mutex` в процессе — той же ловушки, что у policy, здесь нет. `redis-runtime` при этом отдельно измерен на ~5% CPU при ~6000 ops/s под нагрузкой — не бутылочное горлышко, запас большой. `PIPELINE_*_CONCURRENCY` снижен 1024→384 без потери качества (Rust async — не настоящие ОС-потоки, снижение не давало измеримой экономии ресурсов, оставлено на 384 как разумный запас).

## Часть 4 — что НЕ сработало: партиционирование Kafka

Гипотеза: Kafka-продюсеры контендятся на `RecordAccumulator` per-partition локе (находка выше) — больше партиций должно снять контеншен. Пересоздали 7 горячих топиков с 8 партициями вместо 1.

**Результат — резко хуже:** p50 120ms → **28 701ms** (в 239× хуже), p95 → 37 179ms. `pipeline-engine`'s консьюмер `stage.completed` отставал на ~10 500 сообщений на КАЖДОЙ из 8 партиций одновременно, Kafka CPU вырос с ~150-180% до 274%. Совпадает с уже задокументированной в этом репозитории находкой (см. `LATENCY_INVESTIGATION.md`, находка о 365 партициях из production-формул): **на одном локальном брокере без реплик количество партиций само по себе — реальный источник задержки**, независимо от того, что теоретически продюсерский лок мог бы выиграть. Откачено обратно на 1 партицию.

## Часть 5 — систематический аудит: единичный баг или паттерн?

После находки #1 проверены ВСЕ остальные Redis/клиентские подключения во всех 12 сервисах (Rust `redis` crate, Java Lettuce, Go `go-redis`) на тот же класс бага (новое соединение на каждый вызов). **Нигде больше не найдено** — везде уже был правильный паттерн "клиент создан один раз при старте, передан как разделяемое состояние". Находка #1 была единичным случаем, не системным паттерном в этой кодовой базе.

## Финальный результат (1500 TPS, все находки применены)

p50=111ms, p95=168ms, p99=235ms, max=415ms, success=100%, ~99% сообщений доставлены практически в реальном времени. Совокупная загрузка CPU при этом всё ещё не приближается к потолку машины.

## Что осталось не сделано (честно, не скрыто)

1. **`exec:{message_id}` (pipeline-engine, Runtime Redis) без TTL** — реальная находка при разборе "почему только 99%, не 100%, доставлено": накопилось 344 918 зависших ключей за сессию тестирования (данные вычищены вручную через Lua `UNLINK`-скрипт, код НЕ исправлен — нужен `EXPIRE` рядом с остальными полями в `cas_transition.lua`, тот же `DEFAULT_MESSAGE_TTL`, что уже используется для `msgctx`/`dlvsubmit`).
2. **`delivery-reconciliation-service` не поднят** в этом локальном walking skeleton (12 из 32 сервисов платформы) — сообщения с `SUBMISSION_OUTCOME_UNKNOWN` (ambiguous SMPP submit — таймаут/гонка повторной попытки, `DeliveryService.java:38-51`) корректно роутятся pipeline-engine на стадию reconciliation, но обработчика для неё нет — отсюда постоянные ~0.1-1% "unmatched" в каждом прогоне. Не баг пайплайна, отсутствующий сервис.
3. **Партиционирование Kafka не масштабируется на этом стенде** — задокументировано как тупиковая ветка (часть 4), не пытаться повторно без multi-broker кластера.
4. Число ОС-потоков `*_CONCURRENCY` калибровалось эмпирически (бинарный поиск по p95), не выведено аналитически — при существенном изменении профиля нагрузки (не 1500 TPS/8000-60000 msisdn) может потребовать новой калибровки.
