# Дальнейшая оптимизация — что не успели, куда смотреть дальше

**Основание:** прямое продолжение `LATENCY_INVESTIGATION_1500TPS.md` (1500 TPS push, финал: p50=111ms/p95=168ms/p99=235ms/max=415ms, success=100%). На момент написания этого документа CPU всей системы под нагрузкой всё ещё далёк от потолка машины (пиковая суммарная загрузка ~560% из 1200% доступных ядер) — то есть дальнейшая оптимизация **возможна на том же железе**, часть узких мест ещё не тронута. Ничего из этого не реализовано и не протестировано — только направления, приоритезированные по риску/цене.

## Уровень 1 — дёшево, тот же класс риска, что уже сделанные фиксы

### 1.1 Батчинг Kafka-продюсеров (`linger.ms`/`batch.size`)

Ни разу не трогали — судя по поведению (каждый `produce()` выглядит как отдельный round trip), сейчас, вероятно, дефолт (`linger.ms=0`). Небольшой linger (5-10мс) даст брокеру собирать сообщения в пачки вместо тысяч мелких запросов, разгрузив брокер без единой новой партиции (партиционирование мы уже попробовали и откатили — см. `LATENCY_INVESTIGATION_1500TPS.md` часть 4).

Где смотреть:
- Rust: `build_producer()` в `kafka_io.rs` каждого Rust-сервиса (`pipeline-engine`, `destination-resolution-service`, `policy-service`, `routing-service`, `partner-rest-receiver`) — уже есть явные `queue.buffering.max.messages`/`.max.kbytes`, `linger.ms` рядом не выставлен.
- Java: `KafkaIo.java` в `billing-service`/`delivery-service`/`operator-smpp-session-manager` — `Properties` для `KafkaProducer`, `linger.ms`/`batch.size` не выставлены явно.

Риск: низкий (чисто параметр продюсера, не меняет семантику). Ожидаемый эффект: снижение CPU брокера под нагрузкой, возможно небольшой рост latency отдельных сообщений (компромисс батчинга) — стоит измерить, не просто включить.

### 1.2 Fetch-тюнинг Java-консьюмеров (`max.poll.records`/`fetch.min.bytes`)

Не трогали вообще. Если консьюмер вытаскивает мало записей за один `poll()`, это лишние round trips к брокеру при высоком throughput. Смотреть в `KafkaIo.java` (`billing-service`, `delivery-service`) — `ConsumerConfig`/`Properties` при создании `KafkaConsumer`.

### 1.3 Проверить `DESTINATION_RESOLUTION_CONCURRENCY`/`POLICY_CONCURRENCY`/`ROUTING_CONCURRENCY` на 1024

Подняли 256→1024 в третьем раунде (находка #2) и больше не трогали — в отличие от billing/delivery/operator, для этих Rust-сервисов НЕ делали бинарный поиск вниз. У `pipeline-engine` на похожей высокой конкурентности находили futex-доминирование в `strace` (scheduler/semaphore overhead токио, не полезная работа) — возможно, у этих трёх сервисов та же картина, просто не смотрели. Метод — тот же, что для billing/delivery: `strace -c` под нагрузкой + бинарный поиск по p95 (200→350→450→...).

Риск: низкий, это Rust async-таски (не настоящие ОС-потоки), снижение вряд ли повредит, но и выигрыш не гарантирован — стоит именно измерить, не менять вслепую.

## Уровень 2 — требует аккуратности, но не меняет архитектуру

### 2.1 `exec:{message_id}` в Runtime Redis без TTL (pipeline-engine)

Найдено при разборе "почему только 99%, не 100%, доставлено" — 344 918 зависших ключей накопилось за сессию тестирования (данные вычищены вручную, код не тронут). Нужен `EXPIRE`/`PEXPIRE` рядом с остальными полями в `services/pipeline-engine/lua/cas_transition.lua` (и `finalize.lua`?), тот же `DEFAULT_MESSAGE_TTL`, что уже используется для `msgctx`/`dlvsubmit` (`msgctx.rs`, `SubmitIdempotencyStore.java`). Это не throughput-оптимизация, а утечка памяти при долгих прогонах — стоит закрыть до следующего длинного теста, не только "по вдохновению".

Риск: низкий, изолированное добавление TTL к уже существующей записи, не меняет логику CAS.

### 2.2 Слияние Redis round-trips в pipeline-engine (`load` + `cas_advance`)

`services/pipeline-engine/src/redis_cas.rs`: `load()` (HGETALL, ~строка 81) и `cas_advance()` (EVAL Lua-скрипта, ~строка 114) — два отдельных round trip на КАЖДЫЙ переход стадии (сначала читаем текущее состояние в Rust, чистая функция `resolve_next_stage`/`handle_stage_completed` решает, что дальше, потом пишем). На сообщение таких переходов 6 (1 dispatch + 5 stage-завершений) — то есть потенциально 6 round trips можно было бы сэкономить, слив read+decide+write в один Lua-вызов.

**Важная оговорка, не просто техническая деталь:** этот двухшаговый паттерн — не случайность, а осознанный архитектурный выбор всего репозитория ("чистое ядро + тонкая обвязка" — `resolve_next_stage`/`handle_stage_completed` тестируются как чистые функции в Rust, без сети). Слияние в один Lua-скрипт означает перенос ЛОГИКИ РЕШЕНИЯ (не только I/O) в Lua — тестируемость этой логики в Rust пропадает, придётся тестировать через реальный Redis. Не мехническая правка "просто объединить два вызова" — нужно осознанное решение, стоит ли этот компромисс выигрыша в round trips. Не начинать без обсуждения.

### 2.3 Billing-service: "два Redis round-trip на запись, не один"

Уже задокументировано в ОРИГИНАЛЬНОМ `LATENCY_INVESTIGATION.md` (не новая находка этой сессии) — `check_account_state` (pre-check, read) + `apply_atomic_charge` (сам атомарный Lua-скрипт, `BillingAccountStore.java:108`) — раздельные вызовы. Та же оговорка, что в 2.2: `check_account_state` существует отдельно не просто так — возможно, стоит сначала перечитать код и понять, почему это два вызова, а не просто "слить их", прежде чем трогать.

## Уровень 3 — реальный рефактор, не конфиг

### 3.1 Асинхронный Kafka-producer API вместо блокирующего `.get()` в Java-сервисах

`billing-service`/`delivery-service`/`operator-smpp-session-manager` используют `producer.send(record).get()` — блокирует РЕАЛЬНЫЙ ОС-поток пула на весь Kafka round trip. Переход на `producer.send(record, callback)` (без `.get()`) убрал бы саму привязку "число потоков = число конкурентных операций" — это то, что делает Rust/tokio дешёвым, а JVM-thread-pool дорогим (см. находки этой сессии про `Executors.newFixedThreadPool`). Настоящий рефактор архитектуры обработки записи в каждом из трёх сервисов, не однострочная правка — нужно продумать, как коммитить offset при асинхронном ack (сейчас commit синхронно завязан на завершение обработки записи).

Риск: высокий относительно уровней 1-2 — трогает основной путь обработки сообщений в трёх сервисах разом. Не начинать без отдельного код-ревью плана.

### 3.2 gRPC-контеншен в delivery-service

JFR нашёл `io.grpc.internal.ManagedChannelImpl$UncommittedRetriableStreamsRegistry.add(...)` под контеншеном (34 события в записи, см. `LATENCY_INVESTIGATION_1500TPS.md` часть 3) — не исследовали глубже, не пытались чинить. Возможно, несколько gRPC-каналов вместо одного разделяемого снизили бы контеншен, но обычно multiplexing одного канала — это то, ради чего gRPC вообще так спроектирован; нужно сначала понять, оправдан ли отход от одного канала, не бросаться менять.

## Где потолок именно архитектурный, не решается тюнингом на этой машине

**Один Kafka-брокер без реплик и один инстанс Redis — оба принципиально не масштабируются вбок от добавления ядер на этой же машине.** Partition-эксперимент в `LATENCY_INVESTIGATION_1500TPS.md` (часть 4) это прямо показал: больше партиций одному брокеру не помогает, а вредит. Если когда-нибудь понадобится расти существенно выше 1500 TPS — упрётесь не в CPU, а в то, что single-broker/single-instance топология сама по себе имеет потолок пропускной способности. Решается не "железкой побольше", а horizontal scaling (несколько Kafka-брокеров в кластере, шардированный/кластерный Redis) — это уже вопрос архитектуры прод-деплоя (см. `infra/kafka/generate_kafka_topics.py` — там уже заложены production replica-counts, просто не подходящие для одного локального брокера), не апгрейда одной машины.

## С чего начать на другой машине

Порядок по цене/риску: **1.1 → 1.2 → 1.3 → 2.1**, затем остановиться и оценить, стоит ли идти в уровень 2.2/2.3/3 — там уже архитектурные компромиссы, не механические правки.
